# T5 coherent seed through the original-grant object and persistent read provenance

## Can the exact original-grant FILE_OBJECT supply seed bytes and prove read authority without changing sharing or grants?

### Takeaway

The original checked object is the appropriate identity and sharing anchor, but Microsoft does not document that `FltReadFile` is guaranteed to read from write/append-only objects. Seed I/O success and permission to disclose old bytes are separate facts; a native original-subject read-authorization check remains necessary, and neither a write-only request nor a sharing failure proves read denial. [Repository correction](/home/victor/Work/safeupload-staging/driver/docs/design/publication-and-namespace/T5-NATIVE-PUBLIC-OPENS.md:609)

### Cited Findings

- `FltReadFile` requires a currently open FILE_OBJECT, runs at PASSIVE_LEVEL, sends the request below the initiating instance, and returns the file-system status. Explicit offsets work independently of current position; `DO_NOT_UPDATE_BYTE_OFFSET` restores synchronous position after the lower stack sees its update. The function does not serialize concurrent calls even on synchronous objects. Its contract contains no write-only access-bypass or snapshot guarantee. [Microsoft FltReadFile](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltreadfile)
- By contrast, `NtReadFile` expressly requires the preceding CREATE to request FILE_READ_DATA or GENERIC_READ. Therefore a user-mode read-handle control is not a substitute for the exact kernel `FltReadFile` experiment. [Microsoft NtReadFile](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntreadfile)
- The FILE_OBJECT's ReadAccess/WriteAccess/DeleteAccess and SharedRead/SharedWrite/SharedDelete members are read-only sharing bookkeeping; they must not be rewritten to make seeding work. [Microsoft FILE_OBJECT](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ns-wdm-_file_object)
- Current `AllocateV23Async` uses a held private predecessor, or, for public OPEN/OPEN_IF, calls `OpenPublicSource`; that method requests `0x100081` (READ_DATA, READ_ATTRIBUTES, SYNCHRONIZE), ShareRead, FILE_OPEN, then checks full ID. This is still a second service data open, so full-ID checking does not correct its extra sharing demand. [Allocator](/home/victor/Work/safeupload-staging/agente/SafeUpload.Agent.Service/Interception/StagedBoundTransferAllocator.cs:49), [Public-source open](/home/victor/Work/safeupload-staging/agente/SafeUpload.Agent.Service/Interception/StagedDestinationDirectory.cs:68)
- `SeAccessCheck` accepts the captured subject, descriptor, generic mapping, UserMode/KernelMode, desired mask, and previously granted mask; its output reports the access status and granted mask. It does not document itself as an entire NTFS CREATE, traversal, label, or audit-equivalence mechanism. [Microsoft SeAccessCheck](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-seaccesscheck)
- Mandatory Integrity Control is additional to DACL access checks, evaluated first; the SACL mandatory-label ACE can include NO_READ_UP. An owner/group/DACL-only calculation is insufficient to establish label-sensitive read permission. [Microsoft MIC](https://learn.microsoft.com/en-us/windows/win32/secauthz/mandatory-integrity-control)
- Subject capture refers to the calling thread and retained token references can change; locking provides consistent token queries. The effective token is the client/impersonation token when present, otherwise the process primary token. Microsoft requires authorization validation before querying that token for security decisions. [SeCaptureSubjectContext](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-secapturesubjectcontext), [SeQuerySubjectContextToken](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-sequerysubjectcontexttoken)
- Existing 980 native comparisons establish initial status/projected grant, and the subsequent 90 split-check rows establish the tested sharing lifetime. They do not exercise kernel FltReadFile on the retained object or establish read/export authorization. [Repository control outcomes](/home/victor/Work/safeupload-staging/driver/docs/design/publication-and-namespace/T5-NATIVE-PUBLIC-OPENS.md:548), [Split control implementation](/home/victor/Work/safeupload-staging/driver/scripts/t5/writer-permission-native-control.ps1:182)

### Inferences

- Keep the original-rights/share-checked object alive through seeding and the required per-app cleanup lease. Never add READ_DATA to the application's grant, replace the object, or issue the service's old public-source read open. A kernel read that succeeds is an internal transport observation; it must not itself set affirmative read/export authorization. This follows the reviewed correction and the differing FltReadFile/NtReadFile contracts. [Correction](/home/victor/Work/safeupload-staging/driver/docs/design/publication-and-namespace/T5-NATIVE-PUBLIC-OPENS.md:609), [FltReadFile](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltreadfile), [NtReadFile](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntreadfile)
- A descriptor-and-retained-subject calculation avoids a second data open and hence avoids extra share reservations. It is a candidate authorization component, not a completed native proof. Use the immutable exact-source descriptor and original traversal/label/subject facts; do not reuse cached view security or give a read check credit for unrelated previous write grants. Compare its decision to native READ_DATA controls before it can produce affirmative export authority. [Reviewed writer prerequisites](/home/victor/Work/safeupload-staging/driver/docs/design/publication-and-namespace/T5-NATIVE-PUBLIC-OPENS.md:516), [SeAccessCheck](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-seaccesscheck), [MIC](https://learn.microsoft.com/en-us/windows/win32/secauthz/mandatory-integrity-control)
- A native READ_DATA probe can qualify the authorization component on an otherwise identical, privately owned fixture with a controlled sharing window. A probe performed against the live source must retain its real status, exact identity and oplock/audit effects; a sharing failure remains indeterminate. Adding read to the supplemental writer check would reintroduce sharing incompatibilities and cannot silently replace the original grant. [Correction](/home/victor/Work/safeupload-staging/driver/docs/design/publication-and-namespace/T5-NATIVE-PUBLIC-OPENS.md:626), [Supplemental lifetime correction](/home/victor/Work/safeupload-staging/driver/docs/design/publication-and-namespace/T5-NATIVE-PUBLIC-OPENS.md:586)

### Gaps

- No primary source found guarantees ordinary nonpaging FltReadFile success on a write-only or append-only original object. This needs a kernel control, including sync/async objects and explicit READ_DATA denial; no such run was performed in this research pass.
- No complete public WDK recipe found here proves all NTFS read authorization, labels, traversal, restricted/impersonation subjects and audit behavior using only the retained object/descriptor, without a read open. The current StageSecurity helper is owner/group/DACL oriented. Do not promote that helper to a native-equivalent read proof without the finite comparison gate. [Current helper](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageSecurity.c:18)

## What establishes a coherent full-file seed under byte locks, oplocks and compatible concurrent writes?

### Takeaway

Bounded aligned copying, exact EOF and flush are implementable mechanics; they do not establish a whole-file snapshot. A supported synchronization mechanism must protect the entire source interval, including size changes and existing writable mappings; this pass found no documented universally applicable mechanism on every original sync/async grant, so coherent-seed admission remains an explicit native gate. [Reviewed coherence requirement](/home/victor/Work/safeupload-staging/driver/docs/design/publication-and-namespace/T5-NATIVE-PUBLIC-OPENS.md:538)

### Cited Findings

- MS-FSA's read algorithm checks oplock breaks and byte-range conflicts, returns FILE_LOCK_CONFLICT for conflicting locks, handles EOF and truncates a request spanning EOF. Unbuffered reads write out and remove cached data for the requested range. These are per-operation/range rules, not a multi-read full-file transaction. [MS-FSA Server Requests a Read](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/aa57e052-40d4-4d9f-837d-2b0ce7c87cf4)
- Range-lock conflict identity includes the owning Open and lock Key. An exclusive lock blocks another Open/key, and shared locks block exclusive-intent accesses. `FltReadFileEx` exposes an optional byte-lock Key that plain FltReadFile lacks. [MS-FSA range conflicts](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/124bb289-eeef-4653-b9c6-4fb93dd07a21), [Microsoft FltReadFileEx](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltreadfileex)
- Byte locks can extend beyond EOF, but memory-mapped I/O ignores them. A shared byte lock denies ordinary writes even by its holder; introducing it changes other writers' observable behavior. [Microsoft byte-range locking](https://learn.microsoft.com/en-us/windows/win32/fileio/locking-and-unlocking-byte-ranges-in-files)
- R/RH oplocks describe multiple readers and no writers; exclusive RW/RWH oplocks serve buffering/coherency purposes. Their existence must not be assumed just because the retained source has a full ID. [Microsoft oplock types](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/oplock-types)
- The user-facing FSCTL_REQUEST_OPLOCK contract fails synchronous opens; its RH comparison explains that the current oplock notification can be advisory and permit writes without acknowledgement, unlike a filter oplock. Therefore an R/RH notification alone cannot serve as a blocking copy fence. [Microsoft FSCTL_REQUEST_OPLOCK](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_request_oplock)
- The current backing helper uses bounded 64 KiB copying, aligned noncached/write-through output, zero-filled final padding, exact EOF, and flush. It also rejects source length/growth above `MaximumSeedBytes`, currently 16 MiB. `StageOpenBacking` has a matching limit and expects allocator-completed bytes before initializing size/VDL; its writable backing is exclusive and rejects existing cache/data/image sections rather than purging them. [Backing helper](/home/victor/Work/safeupload-staging/agente/SafeUpload.Agent.Service/Interception/StagedBackingFile.cs:23), [Allocator limit](/home/victor/Work/safeupload-staging/agente/SafeUpload.Agent.Service/Interception/StagedTransferAllocator.cs:14), [Kernel backing](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:1545)
- StageStream.c's current FltReadFile occurrence is `StageZeroGrowth` reading a partial sector of private backing; it is not an original-public-object seed. The old seed-limit test proves oversized rejection/exact-16-MiB behavior, and explicitly does not qualify parser/publication of that fixture. [Private tail read](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:3843), [Old limit control](/home/victor/Work/safeupload-staging/driver/scripts/Test-StagedSeedLimit.ps1:38)

### Inferences

- The next kernel copy helper should operate only after the prescribed post-RPC source/anchor/security revalidation, on the original currently open object and exact exclusive backing. Use checked 64-bit offsets/EOF, a bounded buffer aligned for both volumes, nonpaging reads with explicit offsets and offset preservation, aligned noncached backing writes, zeroed padding, exact output EOF, completed flush and exact completion receipt before app exposure. Kernel allocation/namespace locks must not span disk waits. The loop covers the full file; the old 16-MiB proof is not full-surface qualification, and this research proposes no limit/assertion changes. [Seed correction](/home/victor/Work/safeupload-staging/driver/docs/design/publication-and-namespace/T5-NATIVE-PUBLIC-OPENS.md:609), [Bound publication authority](/home/victor/Work/safeupload-staging/driver/docs/design/publication-and-namespace/T5-BOUND-PUBLICATION.md:19)
- Short-read handling must distinguish an expected partial final sector from conflict, unexpected EOF, cancellation or error. Microsoft FltReadFile's beyond-EOF warning and MS-FSA's EOF-span truncation make the aligned tail a specific native control, not permission to assume a padded read always succeeds. Never use paging flags to evade ordinary byte-lock semantics. [FltReadFile](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltreadfile), [MS-FSA read](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/aa57e052-40d4-4d9f-837d-2b0ce7c87cf4)
- Full-ID equality prevents source substitution; stable EOF prevents one size mismatch; digests describe observed bytes. None rules out a source alternating fixed-size contents between chunks. Per-chunk locking also leaves a cross-chunk gap. Adding a whole-file byte lock or an unavailable oplock and rejecting otherwise native-compatible callers would narrow the supported surface; treat these as candidate-control questions, not a ready design. [MS-FSA read](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/aa57e052-40d4-4d9f-837d-2b0ce7c87cf4), [Byte locks](https://learn.microsoft.com/en-us/windows/win32/fileio/locking-and-unlocking-byte-ranges-in-files), [FSCTL_REQUEST_OPLOCK](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_request_oplock)

### Gaps

- A whole-copy linearization point against compatible existing writers, truncation/extension, writable mappings and hard-link access remains unproved. Locks alone miss mappings; advisory oplocks are insufficient; user-mode oplock restrictions cannot simply be ignored for kernel controls. No undocumented NTFS-resource acquisition, cache purge/reclamation, privileged second open or volume snapshot is proposed.
- Required kernel controls must test the actual original FILE_OBJECT with 0/7 sharing; READ_DATA, WRITE_DATA and APPEND_DATA; sync/async/no-buffering variants; ordinary and explicit read-denied subjects; sizes 0, 1, sector-minus/at/plus-one, chunk-minus/at/plus-one, and multiple chunks. Include a full-file case beyond 16 MiB in an isolated transport fixture without changing product thresholds.
- Deterministic barriers between first/middle/final chunks must schedule fixed-size alternate-version writes, append, truncate-and-regrow, cached/noncached writes, an existing writable mapping, and a hard-link writer. Include foreign and same-object keyed byte locks, cancellation and oplock breaks. Accept only a seed proven to belong to one synchronized source version; unchanged ID/EOF or a matching reread digest is insufficient. The mechanism also must preserve native status/sharing and release every transient reservation exactly. No VM runs were performed.

## What typed provenance and recipient facts persist through private predecessors, and what work is independent of the owner decision?

### Takeaway

Persist immutable source lineage and affirmative authorization bound to the intended recipient and exact allocated stage/version, carry it through every preserving predecessor, and validate it before any readable hand-back. These metadata/control changes can be prepared while admission stays disabled; choosing whether unreadable seeded edits are admitted remains the pending owner decision. [Reviewed provenance/policy](/home/victor/Work/safeupload-staging/driver/docs/design/publication-and-namespace/T5-NATIVE-PUBLIC-OPENS.md:632)

### Cited Findings

- V23's packed 124-byte allocation carrier contains source ID/destination anchors and reference/disposition, but no assigned descriptor, original effective recipient or read/seed provenance. The managed binding and journal retain this binding and exact predecessor version; replay compares those tuples. [Wire carrier](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageBoundAllocation.h:11), [Managed binding](/home/victor/Work/safeupload-staging/agente/SafeUpload.Agent.Service/Interception/StagedAllocationBindingV23.cs:5), [Journal](/home/victor/Work/safeupload-staging/agente/SafeUpload.Agent.Service/Interception/StagedBoundAllocationJournal.cs:31)
- Current bound allocation captures/checks the process SID/session/creation time. `RequireBoundSessionUser` returns that stored process-token SID, not an original impersonated thread identity. Hand-back copies the entire snapshot and creates a SYSTEM-owned protected DACL granting FR to that SID and FA to SYSTEM. [Bound request handling](/home/victor/Work/safeupload-staging/agente/SafeUpload.Agent.Service/Interception/MinifilterBoundAllocation.cs:65), [Recipient resolution](/home/victor/Work/safeupload-staging/agente/SafeUpload.Agent.Service/Interception/StagedHandbackCopier.cs:238), [Hand-back ACL](/home/victor/Work/safeupload-staging/agente/SafeUpload.Agent.Service/Interception/StagedHandbackCopier.cs:916)
- The reviewed requirement says new/absent and truncating/superseding allocations begin without prior public bytes, preserving allocations propagate provenance, later writes/length do not erase it, and neither denied nor indeterminate read authority permits full-file export. Existing Blocked + HandbackState.Failed can retain an unreadable version under one proposed owner policy, while the other refuses preserving edits; neither is approved. [Pending owner choice](/home/victor/Work/safeupload-staging/driver/docs/design/publication-and-namespace/T5-NATIVE-PUBLIC-OPENS.md:619)
- Bound publication must reject uncertain seeding and lost original subject. The feature's readiness boolean is currently false, and the contract keeps publication disabled until the separate writer/security/recovery prerequisites are complete. [Publication gate](/home/victor/Work/safeupload-staging/driver/docs/design/publication-and-namespace/T5-BOUND-PUBLICATION.md:27), [Current readiness](/home/victor/Work/safeupload-staging/agente/SafeUpload.Agent.Service/Interception/MinifilterBoundAllocation.cs:13)

### Inferences

- Prepare an immutable typed metadata record, using existing allocation/attachment lifecycle rather than new persisted protocol states: exact original driver/request/reservation and destination source identity; whether old public seed exists; seed EOF/completion facts bound to the exact private stage/version; retained-source complete descriptor reference/equality binding; original effective subject/recipient identity facts; affirmative READ_DATA/export authorization with actual native status and explicit denial-versus-indeterminate diagnostic; exact predecessor version/provenance reference. Persistent facts are evidence, not serialized tokens or authority reconstructed from a PID/path. The dedicated transport must be reviewed separately because V23 has no space/fields for it. [Missing transport prerequisite](/home/victor/Work/safeupload-staging/driver/docs/design/publication-and-namespace/T5-NATIVE-PUBLIC-OPENS.md:532), [Carrier](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageBoundAllocation.h:11)
- For OPEN/OPEN_IF from a sealed private predecessor, retain its old-public lineage and its source-bound affirmative authorization, then require authorization for the eventual recipient. A successor's process-SID equality is not effective-subject equality and cannot upgrade denied/unknown provenance. Truncating/new allocations explicitly clear old-public lineage by disposition, never by observed final length or a changed write mask. Conservative provenance persists after later partial writes. [Reviewed provenance](/home/victor/Work/safeupload-staging/driver/docs/design/publication-and-namespace/T5-NATIVE-PUBLIC-OPENS.md:632), [Current ancestry check](/home/victor/Work/safeupload-staging/agente/SafeUpload.Agent.Service/Interception/StagedBoundAllocationJournal.cs:156)
- Before copy, existing-copy recovery and justification, validate the stage/version/digest and affirmative recipient-bound export receipt. Original effective user identity must be derived from the retained subject, not guessed from process primary SID or current session. Recipient/profile/ACL verification is still required at hand-back. Receipt loss, changed recipient, unknown legacy metadata or changed retry tuple cannot create affirmative export permission. Existing typed replay and failed-hand-back retention mechanisms can carry these facts without adding journal lifecycle enums. [Recipient requirement](/home/victor/Work/safeupload-staging/driver/docs/design/publication-and-namespace/T5-NATIVE-PUBLIC-OPENS.md:626), [Effective-token API](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-sequerysubjectcontexttoken), [Existing hand-back flow](/home/victor/Work/safeupload-staging/agente/SafeUpload.Agent.Service/Interception/StagedTransferPublisher.cs:693)
- Independent work: define/validate metadata and replay equality; propagate predecessor provenance; capture intended effective recipient facts in the reviewed original-subject path; write isolated native-control fixtures; implement bounded copy mechanics behind disabled admission; remove the public-source read dependency only when the exact-object transport is integrated; preserve existing teardown/receipts/recovery. None authorizes activation or chooses unreadable-seed failure policy. [Correction and pending choice](/home/victor/Work/safeupload-staging/driver/docs/design/publication-and-namespace/T5-NATIVE-PUBLIC-OPENS.md:609)

### Gaps

- Native read-authorization comparison must cover DACL allow/deny, write-only requested but read-authorized, append-allowed/read-denied, NO_READ_UP, traversal checks, restricted tokens and primary-A/impersonated-B combinations, with unchanged privileges. Sharing-conflict probes must remain indeterminate. No privilege enabling or native public mutation is part of this plan.
- Provenance controls must cover preserving child/grandchild versions, truncating/new successors, later partial/all-byte writes, changed effective subject with same process SID, changed recipient, replay retries, source replacement after RPC, crash/recovery before/after seed completion, and missing legacy metadata. Ordinary read-authorized hand-back/justification and full-replacement behavior must continue; unreadable blocked outcomes remain pending owner selection.
- Pre-admission sequence: isolated authorization comparison; exact-object kernel read/tail/lock tests; proven whole-copy synchronization with deterministic writer/mapping controls; integrated typed receipt and recipient validation; one integrated lifetime/lock/retirement review before the first revised protected boot; then the existing WDK/PREfast/ApiValidator and agent gates. Current 980/90 controls and the old limit test do not discharge these gates. No product source, VM state, thresholds, assertions, privileges, host configuration or persisted protocol states were changed during this pass.
