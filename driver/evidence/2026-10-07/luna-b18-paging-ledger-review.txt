## ACCEPT WITH CONDITIONS

For the documented standard-user threat model on trusted, boot-attached fixed NTFS volumes, the edit fits the ledger model: it removes a paging-write denial while retaining W accounting. I found no status, completion-context, or IRQL defect in the edit itself.

The condition is that **Free(F) must be a reliable barrier against a paging write that has not yet reached this filter**. The source checks support that model, but do not by themselves prove that NTFS and the memory manager can never issue such a write after the final section/cache observations.

### P1 — Free(F) still depends on an unproven quiescence boundary

Promotion samples `MmDoesFileHaveUserWritableReferences`, section count, and both SOP pointers, then rechecks counters and SOP pointers before the CAS. The final CAS also serializes W and C:

```c
sopEmpty = sop->DataSectionObject == NULL && sop->SharedCacheMap == NULL;
...
if (InterlockedCompareExchange(&Entry->W, 0, 0) != 0 ||
    ...
    sop->DataSectionObject != NULL || sop->SharedCacheMap != NULL) goto Exit;
...
StageRegistryTryPromoteEntry(...)
```

See [StageWriters.c:5429](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:5429), [StageWriters.c:5457](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:5457), and [StageWriters.c:4880](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:4880).

**Concrete interleaving, conditional hypothesis:** an old Cc or modified-page write remains queued above this minifilter; the last user view/section is released; promotion observes S=NO, C=0, W=0 and null SOP pointers, then changes Activating to Protected. The queued write subsequently enters `StageDispatchCore`. W is acquired then, but the new path sends it down with `FLT_PREOP_SUCCESS_WITH_CALLBACK`, so the bytes reach the lower stack after Protected. The edit makes that previously refused write succeed.

I found **no evidence that this interleaving occurs**. The code’s stated premise is that an old source cannot produce another paging write once the data-section and cache-map pointers are absent. The proof gap is that the filter reads those fields directly; Microsoft documents them as opaque and says they can change at any time. `MmDoesFileHaveUserWritableReferences` detects user-mapped sections, including when handles and section handles are closed, but it does not document a barrier for pending paging I/O. [Microsoft’s SOP documentation](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ns-wdm-_section_object_pointers), [MmDoes documentation](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-mmdoesfilehaveuserwritablereferences)

**Condition:** before relying on the invariant across supported NTFS builds, qualify the final-release boundary with a lower-held paging-write/promotion test and a trace showing that promotion waits for W to drain. The plan still lists the cleanup-versus-pending-write case as pending in [MVP-PLAN.md:648](/home/victor/Work/safeupload-staging/driver/MVP-PLAN.md:648). The supplied b17r3 A03 run observed `FlushViewOfFile` failure, but its captured result is inconclusive; it predates this commit and does not qualify the new path.

### What the source accounts for

- **Pre-existing writable sections and views:** `MmDoesFileHaveUserWritableReferences` supplies S; `SafeUploadStageSectionAcquired` reserves C before the section admission check, and C is retired only on matching release or failed acquire. [StageStream.c:3557](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:3557), [StageWriters.c:5954](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:5954), [StageWriters.c:6052](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:6052). This covers an unscoped-created section retained across activation, including a view mapped later from that section. A03’s intended timeline explicitly exercises that case.
- **Cc lazy writes and modified-page writes after handle cleanup:** cleanup can lower H, while `SharedCacheMap`, `DataSectionObject`, S, or C still blocks promotion. Once a paging write enters the filter, exact-FO or exact-SOP accounting increments W; post-operation retires W after lower completion. [StageWriters.c:2810](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:2810), [StageWriters.c:2873](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:2873), [StageStream.c:3689](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:3689). These mechanisms cover writes already dispatched; the P1 condition concerns whether a source can be queued before dispatch after the other observations have gone clear.
- **Sections created by kernel components:** the filter registers `IRP_MJ_ACQUIRE_FOR_SECTION_SYNCHRONIZATION`; the callback reserves C before checking policy. Microsoft identifies this as the file-system section-create callback. [Filter.c:161](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Filter.c:161), [StageStream.c:3560](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:3560), [Microsoft callback docs](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/flt-parameters-for-irp-mj-acquire-for-section-synchronization). This assumes the kernel component uses the normal file-system section path and is within the documented trusted-kernel boundary.
- **New writable opens and new writable sections after activation:** writable creates consult Activating/current policy; section creates check exact SOP and current/pending scope. Section C is reserved before that check, closing the check-versus-promotion race. [StageStream.c:2722](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:2722), [StageStream.c:3173](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:3173), [StageStream.c:3183](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:3183).
- **TxF:** tracked transactions hold T through commit/rollback notifications; new in-scope transacted mutations are refused. [StageWriters.c:2424](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:2424), [Txf.c:84](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Txf.c:84), [StageWriters.c:7005](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:7005).
- **Defrag and move-file FSCTLs:** `FSCTL_MOVE_FILE` is absent from the selected mutating-FSCTL list. Its documented effect is relocating a file’s clusters for defragmentation; it preserves the logical file contents and requires a privileged volume operation. [StageStream.c:3028](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:3028), [Microsoft FSCTL_MOVE_FILE docs](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/file-system-control-processing). `FSCTL_DUPLICATE_EXTENTS_TO_FILE` and related listed data-mutating controls are covered by the FSCTL gate.
- **Image/COW sections:** the section-admission code targets writable shared protections (`PAGE_READWRITE` and `PAGE_EXECUTE_READWRITE`) and skips `SEC_IMAGE`; these are not ordinary shared writes to the backing file.

### Other findings

**P1 boundary — only within the documented threat model.** The design explicitly trusts administrators/SYSTEM and accepts physical-drive writes that bypass the file-system stack. If the invariant includes malicious privileged callers or raw-device writes, the overall product claim must be **REJECTED** regardless of this edit. See [writer-state-design-v2.txt:64](/home/victor/Work/safeupload-staging/driver/evidence/2026-10-03/writer-state-design-v2.txt:64).

The C01 publisher remains non-cached and write-through, so it does not rely on that refusal; the implementation at lines 51–97 still avoids cached publication writes.

### Boot safety and edit mechanics

**Paging writes are no longer refused by the registry on the public physical-file path.** In the prototype, `IRP_MJ_WRITE` with `IRP_PAGING_IO` calls `SafeUploadStageWritersBeginPagingIo`; a context gets a completion callback, and no context falls through to success. [StageStream.c:3423](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:3423). The mutation and FSCTL helpers also pass paging I/O, and the normal registration skips paging writes entirely. [StageStream.c:2790](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:2790), [StageStream.c:3080](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:3080), [Filter.c:176](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Filter.c:176). An owned staging stream may have its own routing/error behavior; that is outside the registry refusal path.

The edit preserves the lower-completion context and W rundown. `exactSopTracked` is still passed as an output parameter, so it is not an unused local. I found no lost-status or obvious PREfast/IRQL issue in the four-line behavior change. **I did not build or run tests** in this read-only review.
