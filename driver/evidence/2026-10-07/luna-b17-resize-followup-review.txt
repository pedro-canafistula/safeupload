## ACCEPT WITH CONDITIONS

The reported C02 retry path is cut at the status boundary. Acceptance assumes the prototype intends these statuses to fail fast during any non-null top-level IRP; that can make a genuine transient conflict fail once instead of being retried. The supplied retry evidence is for a specific Windows build, so it does not establish Mm’s behavior across all supported builds.

### P1: upper flush and worker status mapping

At [StageStream.c:1606](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:1606), the conversion runs after both `StageFlushUpper` and `StagePostResizeBacking`:

```c
if (IoGetTopLevelIrp() != NULL &&
    (status == STATUS_FILE_LOCK_CONFLICT || status == (NTSTATUS)0xC0000476L))
    status = STATUS_UNEXPECTED_IO_ERROR;
```

The flush path propagates its backing paging-write status: [StagePagingComplete at StageStream.c:1932](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:1932) copies the child I/O status to the original request, and `StageFlushUpper` returns `CcFlushCache`’s final status. Microsoft documents that `CcFlushCache` waits for the flush and reports its final completion status in `IoStatus` ([CcFlushCache](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ccflushcache)). The worker result likewise returns through `work.Status` before this check. On either error, `StageResize` returns before updating the upper header at [StageStream.c:1609](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:1609).

**Interleaving:** section creation enters `FsRtlSetFileSize` with a top-level marker; dirty upper pages flush through `CcFlushCache` and `StageRoutePaging`; the backing write returns one of the two statuses. The new code converts it before Mm receives it. If the upper flush succeeds but the worker’s backing resize returns one of those statuses, the same conversion applies.

Keeping the flush on the caller is a plausible precaution: the caller is in the section-creation path, and a worker flush on the same control area could wait on that path. The supplied evidence supports the caller-side path, but does not prove that a worker would deadlock. That part remains a hypothesis.

The conversion also has a real tradeoff. `IoGetTopLevelIrp() != NULL` includes special Cache Manager and modified-page-writer markers, not only the observed recursive FSP marker ([IoGetTopLevelIrp](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-iogettoplevelirp)). If a genuine transient lock conflict reaches this branch, a section operation can fail where a retry might later succeed. `StageResize` itself does not commit the upper size on that failure; availability and error reporting are the concern.

### P2: allocation and other flush paths

I found no concrete in-repository caller that sends `FileAllocationInformation`, `IRP_MJ_FLUSH_BUFFERS`, or cleanup to an owned upper stream under a non-null top-level IRP. The known C02 path is section extension through `FsRtlSetFileSize` into `StageResize`. The direct `StageFlush` callers are explicit flush, cleanup, write-through, and the stage drain worker ([StageStream.c:1684](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:1684), [StageStream.c:2147](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:2147), [StageStream.c:2154](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:2154), [StageStream.c:2294](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:2294)). I found no internal call that targets the upper stream with those operations. The backing flush is issued below the selected instance, so it does not re-enter this filter ([generated minifilter I/O](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/i-o-requests-generated-by-the-minifilter-driver)).

There is a **conditional** gap at [StageStream.c:2125](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:2125): if an internal recursive `FileAllocationInformation` shrink exists, `StageResize` can complete its EOF change on the worker, then the caller-side allocation request at line 2127 can fail under the top-level marker. The operation then reports failure after the logical EOF changed; a recursive allocation request that fails with a retry status could also bypass the new mapping. I found no concrete caller for this sequence, so it is not a proven finding for the reported C02 path. If such a caller exists, this remains a P2.

### Cleanup synchronization and StageWriters

The cleanup change is sound. The prototype registers `SafeUploadStagePostOperation` for cleanup ([Filter.c:146](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Filter.c:146)), and `FLT_PREOP_SYNCHRONIZE` keeps the post-op in the pre-op thread context at IRQL ≤ APC_LEVEL, except during draining ([Microsoft synchronization guidance](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/returning-flt-preop-synchronize)). No resource is held across the pre/post pair.

One nuance: cleanup is not an epoch operation, so it takes the dispatch core’s early path and has no admission token to wrap. The general wrapper preserves `FLT_PREOP_SYNCHRONIZE` and its tagged completion context when a token is present; cleanup’s result passes through directly. Owned streams are handled before the cleanup switch and complete in `StagePreOperation`, so this change does not alter their cleanup path. Cleanup is IRP-based, so fast I/O is not a concern.

The nonpaged SOP snapshot allocation at [StageWriters.c:3551](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:3551) matches its copy under `SectionLock` at DISPATCH_LEVEL. No issue found there.
