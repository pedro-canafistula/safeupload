## Verdict: valid P1 race

The successful hard-link branch enters a shared alias-probe path with a stale-result gap. This is a **P1** source issue: after a scope change, a completed classification from the old scope can clear a newer protection gate. Under the stated conditions, that can let a pre-scope holder write through a newly protected alias and can allow coverage to report Ready once the stale result has settled.

The all-link classifier checks rename and transaction versions while publishing its scan state under `RegistryLock` ([StageWriters.c:4754](/tmp/safeupload-mvp-continuation/driver/SafeUpload.Minifilter/StageWriters.c:4754), [StageWriters.c:4762](/tmp/safeupload-mvp-continuation/driver/SafeUpload.Minifilter/StageWriters.c:4762)). It then releases that lock before returning `UnionScoped` to the activation worker ([StageWriters.c:4775](/tmp/safeupload-mvp-continuation/driver/SafeUpload.Minifilter/StageWriters.c:4775)). The worker resolves the alias probe later ([StageWriters.c:5532](/tmp/safeupload-mvp-continuation/driver/SafeUpload.Minifilter/StageWriters.c:5532)).

Between those steps, a new rename or scope apply can start a probe. The resolver’s successful path checks the rename-loss generation and transaction version, but does not validate the classified `RenameVersion`, current policy generation, activation stamp, or scope-publication sequence ([StageWriters.c:5222](/tmp/safeupload-mvp-continuation/driver/SafeUpload.Minifilter/StageWriters.c:5222), [StageWriters.c:5317](/tmp/safeupload-mvp-continuation/driver/SafeUpload.Minifilter/StageWriters.c:5317)). If the old result is Outside, it publishes `OUTSIDE` and clears `AliasProbePending`; it can also clear activation enforcement and set an activating or protected entry to unscoped ([StageWriters.c:5252](/tmp/safeupload-mvp-continuation/driver/SafeUpload.Minifilter/StageWriters.c:5252)).

A concrete schedule is: an old worker publishes Outside; a link operation changes the file’s alias set, or policy publication adds a protected prefix; Apply/Reconcile starts a fresh probe and stamps it; then the old worker consumes its result. Pending-policy publication advances `SafeUploadPolicyCoverageSequence` while the live generation can remain unchanged ([Policy.c:531](/tmp/safeupload-mvp-continuation/driver/SafeUpload.Minifilter/Policy.c:531)). Apply stamps `G+1` and Reconcile stamps the live generation, but the resolver does not compare either stamp ([StageWriters.c:6657](/tmp/safeupload-mvp-continuation/driver/SafeUpload.Minifilter/StageWriters.c:6657), [StageWriters.c:6733](/tmp/safeupload-mvp-continuation/driver/SafeUpload.Minifilter/StageWriters.c:6733)). The promotion CAS cannot help: the Outside path skips promotion.

After the stale result clears the gate, `SopMatchesPolicy` can return immediately on `ScopeNameClassification == OUTSIDE`, once alias-pending, rename-in-flight, and unknown checks pass ([StageWriters.c:6547](/tmp/safeupload-mvp-continuation/driver/SafeUpload.Minifilter/StageWriters.c:6547)). For a pre-scope holder whose file-object name remains outside the policy, the later name check need not discover the protected hard-link alias. Coverage can also miss the entry: with activation enforcement, alias-pending, and rename-in-flight all cleared, the registry coverage walk skips it ([StageWriters.c:6967](/tmp/safeupload-mvp-continuation/driver/SafeUpload.Minifilter/StageWriters.c:6967)). A later, stable coverage query can therefore be Ready if its other checks pass.

## Why the apparent blockers do not close it

- Destination refusal blocks a link or rename whose destination is already current or pending protected scope. It cannot prevent an alias created before that scope was published from becoming protected by a later policy update.
- The epoch lease covers the outer mutating operation through post-operation completion. It does not cover the asynchronous reclaim/classification worker queued by that completion.
- Finalization’s admission barrier does not join that worker. Apply/Reconcile can end the transition based on rename-loss stability, without waiting for alias probes to finish ([Policy.c:1183](/tmp/safeupload-mvp-continuation/driver/Policy.c:1183)).
- Complete enumeration proves all links for the versions and policy view it scanned. It does not make the later consumer atomic with that proof. Partial continuation is also keyed only by policy generation ([StageWriters.c:4537](/tmp/safeupload-mvp-continuation/driver/SafeUpload.Minifilter/StageWriters.c:4537)); a pending-union change with unchanged live generation can reuse stale accumulated scope results.

## Minimal coherent fix

Carry a completed-classification receipt containing rename and transaction versions, scope-publication sequence, current generation, and activation stamp. At consumption, under `RegistryLock`, the policy cache lock, and `StateLock`, validate the receipt and atomically publish the classification and clear the pending gate. If it is stale, leave the probe pending and requeue it; normal version or scope churn should not become Unknown. Keep genuine classification failures and existing sticky rename-loss tracking behavior unchanged.

Also persist the scope-publication sequence with partial scan state and discard accumulated link results when the scope union changes, even if the live generation does not.

This gap is present in the shared pipeline used by ordinary rename and by Apply/Reconcile probes; commit `c56ead4` makes successful hard-link additions another caller of that pipeline. This is independent of the recorded gen2 rename-loss site, and I’m not attributing that runtime failure to this interleaving. Source review only; no files were changed, and no builds or VMs were run.
