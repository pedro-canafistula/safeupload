## Verdict: REJECT for VM use until the status capture is corrected

The main blocker is harness evidence integrity: the status waiter can discard a `Ready` report and later return `Pending`, allowing a readiness violation to pass. The kernel and agent production sources are unchanged in these commits, and I found no product weakening.

### Blocking findings

- **A `Ready` violation can be hidden by a later `Pending`.** The stream reader keeps only the last status it consumes ([Test-StagedInvariantSuite.ps1](/home/victor/Work/safeupload-wt-sol/driver/scripts/Test-StagedInvariantSuite.ps1:852)). While waiting for `Pending`, a `Ready` status only changes a reason string; the loop continues and returns success if a later `Pending` arrives ([Test-StagedInvariantSuite.ps1](/home/victor/Work/safeupload-wt-sol/driver/scripts/Test-StagedInvariantSuite.ps1:870)). If both frames are queued, the drain also retains only the final one. Preserve and evaluate every frame; a `Ready` report at the accepted generation while the holder lives must remain a failure even if `Pending` follows.

- **Retained status is treated as current status.** `Get-ActivationProductStatus` returns `Status='OK'` whenever any prior status exists, even if this call consumed no update. It exposes `RetainedStreamState` and `WholeIntervalLossFree=false`, but the assertion call sites do not use those limits ([Test-StagedInvariantSuite.ps1](/home/victor/Work/safeupload-wt-sol/driver/scripts/Test-StagedInvariantSuite.ps1:845), [Test-StagedInvariantSuite.ps1](/home/victor/Work/safeupload-wt-sol/driver/scripts/Test-StagedInvariantSuite.ps1:860)). A retained event can support “last status observed,” but it cannot prove the service’s current state at a later checkpoint: the receipt QPC is when the client consumed the frame, not when the service published it, and the stream has no loss-detecting server sequence. Use a current snapshot or publication sequence/timestamp, or make retained observations inconclusive for current-status assertions.

- **The failure path also ignores generation.** After a Pending wait times out, `knownReady` checks only `admissionCoverage`, not the accepted generation or `protectionActive` ([Test-StagedInvariantSuite.ps1](/home/victor/Work/safeupload-wt-sol/driver/scripts/Test-StagedInvariantSuite.ps1:2731)). The held-interval `readyWhileHeld` check likewise treats any Ready frame as a failure before checking generation ([Test-StagedInvariantSuite.ps1](/home/victor/Work/safeupload-wt-sol/driver/scripts/Test-StagedInvariantSuite.ps1:2843)). Filter both failure and success decisions against the exact accepted generation and active-protection state.

### Other reviewed changes

- **Private-stage fallback:** Accepting the normalized FSCTL cache representation does not undermine the *narrow retention* proof. The decoder checks record structure and identity while explicitly disavowing raw-sector fixup integrity ([StagedInvariantObserver.psm1](/home/victor/Work/safeupload-wt-sol/driver/scripts/StagedInvariantObserver.psm1:317)). The fallback binds the kernel-enumerated file reference to the cached record sequence, FILE_NAME parent, one Win32 name and optional DOS alias, then repeats identity checks and data reads ([StagedInvariantObserver.psm1](/home/victor/Work/safeupload-wt-sol/driver/scripts/StagedInvariantObserver.psm1:476)). The original cache response and failed raw attempt are retained with explicit source labels ([StagedInvariantObserver.psm1](/home/victor/Work/safeupload-wt-sol/driver/scripts/StagedInvariantObserver.psm1:662)). A successful fallback can satisfy the private-retention assertion after a raw attempt error; that is acceptable only for this bounded live-retention claim. It must not count as raw on-disk metadata proof or replace the separate public-scope raw privacy proof.

- **Inspector reconnect:** The retry loop is fail-closed: it retries only connection-establishment `ERROR_FILE_NOT_FOUND`/`ERROR_PIPE_BUSY`, shares the original deadline, authenticates the opened server as SYSTEM, and does not resend a delivered request or fall back to the driver port ([StagedProofProxy.h](/home/victor/Work/safeupload-wt-sol/driver/SafeUpload.Inspector/StagedProofProxy.h:105)). There is a small strict-deadline edge: after `Sleep(10)` or a successful `WaitNamedPipeW`, the next `CreateFileW` occurs before another expiry check. `SuProofIo` prevents sending once the deadline has expired, so this does not deliver a late request, but it does not strictly bound connection/authentication. Check the deadline before each create and after a successful open.

- The earlier relay review’s synchronous native-send limitation remains: the Inspector’s I/O timeout cannot cancel a service-side `FilterSendMessage`; the service must retain its lease until that call actually returns. This is still incomplete diagnostic evidence on timeout, not a whole-request bound.
