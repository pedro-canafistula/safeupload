# Verdict: REJECT

The worker moves the backing flush, zeroing, and EOF update off the recursive caller. The boundary is incomplete: on a growth, the caller first flushes the upper cache, and that flush can route paging writes to the backing file before any worker is queued.

## Proven code findings

**P1 — The upper-cache flush can still send backing I/O through the recursive caller.**  
[StageStream.c:1598](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:1598)

```c
if (Size.QuadPart > Stream->Header.FileSize.QuadPart) {
    status = StageFlushUpper(Stream);
    if (!NT_SUCCESS(status)) return status;
}
status = IoGetTopLevelIrp() == NULL ? StageResizeBacking(Stream, Size) :
    StagePostResizeBacking(Stream, Size);
```

`StageFlushUpper` calls `CcFlushCache` at [StageStream.c:1074](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:1074). Dirty upper pages route through `StageRoutePaging`, which issues backing I/O with `FltPerformAsynchronousIo` at [StageStream.c:1997](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:1997). Thus, a growth under `FSRTL_FSP_TOP_LEVEL_IRP` can reach the backing filesystem during the caller-side cache flush, before `StagePostResizeBacking` runs. `CcFlushCache` waits for the flush to finish, and the generated I/O can complete synchronously; the API documentation does not promise to clear the caller’s top-level IRP. [CcFlushCache](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ccflushcache), [FltPerformAsynchronousIo](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltperformasynchronousio)

**Concrete interleaving:** section creation enters `FsRtlSetFileSize` with a non-NULL top-level marker; growth finds dirty upper pages; `CcFlushCache` routes their paging writes to the backing file; if NTFS returns `STATUS_FILE_LOCK_CONFLICT`, `StageFlushUpper` returns that status and `StageResize` exits before queueing the worker. This can preserve the reported section-creation retry. The route is code-proven; the NTFS response in this exact paging-write path is a hypothesis.

**Minimal fix:** ensure both the upper-cache drain and its routed backing paging writes execute in a context that avoids the recursive top-level condition, while preserving the flush-before-zero-before-EOF order.

**P2 — `FileAllocationInformation` continues backing I/O after a posted resize.**  
[StageStream.c:2120](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:2120)

```c
if (allocation->AllocationSize.QuadPart < stream->Header.FileSize.QuadPart)
    status = StageResize(stream, file, allocation->AllocationSize);
if (NT_SUCCESS(status)) status = FltSetInformationFile(stream->BackingInstance,
    stream->BackingObject, allocation, sizeof(*allocation), FileAllocationInformation);
if (NT_SUCCESS(status)) status = FltQueryInformationFile(stream->BackingInstance,
    stream->BackingObject, &standard, sizeof(standard), FileStandardInformation, NULL);
```

If a recursive `FileAllocationInformation` request shrinks allocation below the current EOF, `StageResize` may post the EOF change and update the upper header, but the allocation change and query still run on the original caller. If that backing set fails, the request fails after the logical EOF was already changed.

**Minimal fix:** when the top-level IRP is non-NULL, run the entire allocation operation—including resize, set-allocation, query, and upper-size update—in the worker.

**P2 — Other flush paths still call backing `FltFlushBuffers` on the caller.**  
[StageStream.c:1081](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:1081)

```c
static NTSTATUS StageFlush(PSTAGE_STREAM Stream)
{
    NTSTATUS status = StageFlushUpper(Stream);
    if (!NT_SUCCESS(status)) return status;
    return Stream->ReadOnly ? STATUS_SUCCESS :
        FltFlushBuffers(Stream->BackingInstance, Stream->BackingObject);
}
```

This remains reachable from flush-buffer, cleanup, and write-through paths ([StageStream.c:1679](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:1679), [StageStream.c:2142](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:2142), [StageStream.c:2149](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:2149)). Those paths are not top-level-aware. If one runs under a recursive marker and backing flush is refused, the flush can still fail or block in that context.

**Minimal fix:** apply the top-level-aware backing-flush handling to `StageFlush` too, and address its caller-side upper flush as in P1.

## Hypotheses and liveness risks

- The supplied disassembly says `MiCreateSection` also retries on `0xC0000476`. The worker returns raw `StageResizeBacking` status through `work.Status` ([StageStream.c:1539](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:1539), [StageStream.c:1585](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:1585)). So if a backing operation returns `0xC0000476`, it remains retryable by the reported path. I found no evidence that NTFS returns that status for these operations. Handle it with a bounded worker-side retry or convert it to a status that does not enter Mm’s retry loop.

- I found no direct lock cycle between the reported waiter and the worker. The waiter holds the upper stream resource, and some resize callers also hold the namespace resource; the worker uses the backing file and does not acquire those locks or the upper paging resource. The upper object has SafeUpload-owned FCB/cache state, and generated I/O goes below the initiating instance, so it does not reenter SafeUpload’s upper-stream callbacks. The paging and `AdvanceOnly` paths also bypass `StageResize`; I found no lazy-writer or MPW path that reenters `StageResize` and waits on this worker.

- Queue starvation remains a conditional risk. The worker can perform a flush and up to 16 MiB of synchronous zero writes ([StageStream.c:1559](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:1559)); concurrent resizes can occupy `DelayedWorkQueue` threads. Microsoft’s driver guidance calls the system worker pool limited and warns that long waits in work-item callbacks can deadlock. The public driver documentation I checked does not guarantee dynamic growth sufficient to prevent exhaustion on Windows 10. I found no proof that SafeUpload alone can exhaust the queue, or that this worker needs a resource held by its waiter. [System worker threads](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/system-worker-threads), [FltQueueGenericWorkItem](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltqueuegenericworkitem)

## Checks that passed

The worker’s stack context and event are initialized before queueing; status is set before signaling; the worker does not touch the context after `KeSetEvent`; and the item is freed on both queue-failure and worker paths. `FltQueueGenericWorkItem` protects filter unload while work is outstanding. The nonpaged SOP snapshot fix is complete: the copy occurs under `SectionLock` at DISPATCH_LEVEL, the snapshot is 48 bytes, and the allocation is **64 × 48 = 3,072 bytes**, which is reasonable. The resize ordering remains upper-cache drain, backing flush and zeroing, backing EOF update, then upper size/VDL update.
