## What H=1 proves—and does not

`H` is sampled from the registry entry’s aggregate counter at [StageWriters.c:6524](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:6524). The opener list contains process IDs, added by `StageRegistryAddOpener` at [StageWriters.c:965](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:965); it does not identify a `FILE_OBJECT`. Thus Control 26’s `H=1, openerPids=[5972]` strongly supports a live holder but does not prove the write callback used the same file object or instance. Control 26 itself is read-only: its status routine says it enumerates the in-memory registry without opening or mutating files at [StageWriters.c:6648](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:6648).

The normal insertion path puts the node in `WriterObjects` and increments `Entry->H` under the same `WriterLock` at [StageWriters.c:2307](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:2307) and [StageWriters.c:2308](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:2308). That rules out a simple insertion race where H increments before the node is visible. The concrete ways the write lookup can nevertheless miss are:

- The callback uses a different `FILE_OBJECT`, a different instance, or cannot get the stream context. The begin routine returns without tracking for null inputs or IRQL above APC at [StageWriters.c:2801](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:2801); otherwise it requires the exact pointer match at [StageWriters.c:2815](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:2815). A different instance matters because the lookup is instance-scoped.
- The context was explicitly detached while the old context remained referenced. `FltSetStreamContext` uses `FLT_SET_CONTEXT_KEEP_IF_EXISTS`, so ordinary creation does not replace an existing context ([Context.c:632](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Context.c:632), [Context.c:638](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Context.c:638)). The driver’s explicit deletion path is Control 16, `FltDeleteContext`, at [StageStream.c:796](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:796); Control 26 is command 26, not that deletion command ([Protocol.h:282](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Protocol.h:282), [Protocol.h:295](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Protocol.h:295)). The identity opens use `FILE_READ_ATTRIBUTES` and verify the same SOP at [StageAdmission.c:76](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageAdmission.c:76) and [StageAdmission.c:98](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageAdmission.c:98); they do not replace the writer context.
- Cleanup removes a node and decrements H under the writer lock at [StageWriters.c:2551](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:2551) and [StageWriters.c:2552](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:2552). Context teardown drains nodes and decrements H at [StageWriters.c:2594](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:2594) and [StageWriters.c:2607](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:2607). Those are the list-removal paths; policy activation does not move or remove nodes.
- An `Entry == NULL` overflow marker does **not** explain this by itself: it does not increment H at [StageWriters.c:3383](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:3383), and if the exact node is found, the ordinary nonpaging lookup still sets `TrackedWriter=TRUE` at [StageWriters.c:2828](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:2828).

## Contract and fix

The accepted product contract says existing writers finish under their granted rights: the design proposal says so at [writer-state-design-v2.txt:37](/home/victor/Work/safeupload-staging/driver/evidence/2026-10-03/writer-state-design-v2.txt:37), and the later MVP plan explicitly says existing handles, mappings, cached data and paging writes “are never refused” at [MVP-PLAN.md:502](/home/victor/Work/safeupload-staging/driver/MVP-PLAN.md:502). It also states paging I/O is never refused by the registry at [MVP-PLAN.md:505](/home/victor/Work/safeupload-staging/driver/MVP-PLAN.md:505).

**This is a product bug, not the intended A01 contract.** For the likely nonpaging path, the bug would be a failure to recognize the holder’s exact writer node (or an earlier actor call failure); for a paging IRP, it is the explicit denial at [StageStream.c:3441](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:3441), which contradicts the accepted paging-I/O contract. Do not change the harness to accept refusal. Keep the exact-file-object check—allowing any write merely because aggregate H is nonzero would be too broad. Separately, remove the paging policy-denial branch while retaining its W rundown accounting.
