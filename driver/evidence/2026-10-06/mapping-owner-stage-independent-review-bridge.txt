## Verdict

The addendum now uses the right boundary: the current synthetic upper-SOP path
is **unproven under the reviewed DDI contract**, not conclusively prohibited.
Microsoft recognizes that a filter may implement a layered filesystem by
owning file objects and issuing lower creates. That ECP-specific carveout does
not answer whether this minifilter may set the application's
`SectionObjectPointer`, allocate the per-stream SOP, set cache-support state,
or call Cache Manager APIs on that object. Do not extend or qualify the current
path until that exact question has an authoritative source-level answer.

The converse is also important: this evidence does not yet justify committing
to a WinFsp/native-FSD rewrite. A true filesystem owner is a valid fallback if
the layered-filter contract cannot be established, but its logical namespace
must still preserve every existing identity, access-control, privacy, raw
observer, and destination requirement. Neither path may narrow policy scope or
mark full readiness from a local-NTFS prototype.

## Contract and implementation comparison

The current `StageCreate` completes creates above NTFS and sets the
application `FILE_OBJECT`'s `FsContext`, `FsContext2`, `SectionObjectPointer`,
and `FO_CACHE_SUPPORTED`; `StageInitializeCache` calls
`CcInitializeCacheMap` on that file object. `StageOpenBacking` separately opens
the private NTFS stage. Microsoft documents that `FILE_OBJECT.SectionObjectPointer`
is set only by file systems, that a file system or redirector allocates one
SOP per stream and filter drivers treat its members as opaque, and that file
systems call `CcInitializeCacheMap`. These are the direct DDI statements to
resolve against the layered-filter category, not merely against ordinary
minifilter pass-through behavior.

The category is real: Microsoft’s system-defined ECP guidance describes a
filter that owns file objects and issues lower `IRP_MJ_CREATE` operations as a
layered filesystem. It says such a filter should propagate the original ECP
list to its lower creates. In the pinned current source, `StageOpenBacking`
calls `FltCreateFileEx2` with a null `DriverContext`; `StageStream.c` contains
no ECP-list retrieval or propagation. The DDI documents an `IO_DRIVER_CREATE_CONTEXT`
for passing ECPs to `FltCreateFileEx2`. Therefore, if the existing design is
reviewed as a layered filesystem, ECP propagation is a concrete source gap to
close, alongside the SOP/Cache Manager ownership question. The carveout does
not itself authorize SOP allocation or Cache Manager use.

No Microsoft sample located in this review demonstrates a minifilter owning
the application stream's SOP and initializing its cache map. The Microsoft
cache examples returned are CDFS/FAT filesystem implementations; this absence
is not evidence that a layered filter cannot do it. Microsoft primary pages
reviewed on 2026-10-06:

- [`FILE_OBJECT`](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ns-wdm-_file_object): `SectionObjectPointer` and `FO_CACHE_SUPPORTED` ownership wording.
- [`SECTION_OBJECT_POINTERS`](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ns-wdm-_section_object_pointers): one SOP per stream, allocation responsibilities, filter opacity.
- [`CcInitializeCacheMap`](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ccinitializecachemap): says file systems call it.
- [`System-defined ECPs`](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/system-defined-ecps): layered-filesystem carveout and ECP-list propagation.
- [`FltCreateFileEx2`](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltcreatefileex2): optional `IO_DRIVER_CREATE_CONTEXT` and ECP support.
- [Microsoft SimRep sample](https://learn.microsoft.com/en-us/samples/microsoft/windows-driver-samples/simrep-file-system-minifilter-driver/): create-time name redirection; it does not demonstrate private-section ownership or private backing ACL design.

## Upstream comparison and decision path

The required upstream reuse check was performed for the concrete question:
does WinFsp lifecycle evidence let this minifilter retire its mapped-stream
state on Cleanup/Close? The reviewed source/test is `winfsp/winfsp` commit
`fde790d8ea41283606d1c56b557608a17e455f59` (v2.2B4), recorded in the pinned
local study above. It shows a filesystem owning its FileNode/cache state,
separating Cleanup from Close, and retaining state for mapped views/write
behind. This supports retaining backing past Cleanup/Close; it does not show
NTFS or a minifilter's SOP behavior and does not establish the current
implementation's contract.

WinFsp documents mapped I/O, but also lists hard links, short names,
`FILE_OPEN_BY_FILE_ID`, volume read/write, and several NTFS-specific operations
as unsupported or incompatible. This changes the next action: treat WinFsp as
a candidate for a bounded architecture proof, not a compatible drop-in. Before
selecting it, demonstrate the original logical path, volume serial, full file
ID, parent/name-slot identity, aliases, ADS, rename/replacement, and required
native queries while the actual file object belongs to the logical owner.
Also show independent buffered/uncached observers see the approved public
generation, the raw original-volume observer sees unchanged bytes and extents,
and direct access to private backing remains denied across owner/filter
failure. Repeat across every already supported adapter; a local fixed-NTFS
success cannot enable USB, UNC/SMB, or sync paths.

Recommended next step is a written DDI review of the existing layered-filter
design covering: who allocates/initializes the app stream SOP; whether setting
that field and `FO_CACHE_SUPPORTED` is valid for this owned filter object;
Cache Manager callback/teardown obligations; ECP retrieval/propagation; and
whether section creation, paging flush, and close lifetimes obey those
contracts. If this cannot be established, select a true filesystem owner and
prove its identity and adapter compatibility before product implementation.
Keep early ownership separate from policy activation and publication, retain
`OwnerPendingPolicy`, and preserve taint/unsupported/default-off gates until
the complete DOD is met. No runtime or privacy pass is claimed here.
