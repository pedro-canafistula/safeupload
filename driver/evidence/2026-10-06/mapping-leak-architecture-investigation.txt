# Mapping leak architecture investigation (M1/M2)

Read-only architecture assessment completed 2026-10-06 against the current staged-write source and the exact mapping repros. This note does not change either repro and makes no Windows build or VM-runtime claim. The known-SOP paging-write guard in `StageStream.c` / `StageWriters.c` is a partial guard only; neither mapping leak is closed by it.

## Exact acceptance gates

M1 creates and flushes a 4096-byte fixture, records its allocated LCN and full raw baseline, creates a writable file mapping, closes the source file handle, and only then loads/attaches SafeUpload while that mapping remains live (`scripts/Test-StagedPreAttachmentMapping.ps1:237-281`). It then requires a successful mapped write and view flush, releases the view and section, successfully calls `FlushFileBuffers`, opens fresh buffered and uncached readers, verifies the original LCN is unchanged, and samples the full raw extent against baseline (`:283-335`). A denied write/flush or failed observer is inconclusive, not a privacy pass (`:6-12`).

M2 keeps writable sections from before candidate policy acceptance. After the expanded policy is accepted it writes and flushes through the old expansion view, then separately creates the first view from a retained section handle and measures its uncached and raw extent (`scripts/Test-StagedPolicyTransitionMapping.ps1:1158-1200,1202-1255,1257-1309`). Expansion is blocked only after successful write, view flush, file-buffer flush, mapping release, and a complete unchanged raw comparison (`:1356-1366`). The assertions deliberately require exercising the write path; denial does not satisfy the measurement.

## What an identity census could establish

The registry is populated by successful observed post-create callbacks. That code obtains `FileIdInformation` and associates the opened file object's exact section-object pointer (`SafeUpload.Minifilter/StageWriters.c:2233-2285`). `StageRegistryOpenIdentity` reopens an already registered object by file ID, retains the stream suffix for alternate data streams, rechecks volume serial and the full file ID, and verifies that the reopened file object's section-object pointer equals the recorded pointer (`:3935-4017`). This proves a useful reopen operation for a known entry; it is not namespace enumeration and cannot discover identities the registry never observed.

An identity-only census is technically plausible for a bounded NTFS namespace if it enumerates every candidate file and relevant alternate data stream, opens each candidate by a stable handle or file ID, checks the full volume/file/stream identity, verifies the SOP, inserts every entry before publishing the policy, and rejects the transition on any inaccessible subtree, unsupported reparse point, race, capacity overflow, or identity mismatch. Such a census can improve identity completeness. It does not prove that a stream is quiescent; `MmDoesFileHaveUserWritableReferences` and `MmCanFileBeTruncated` must still be applied to the exact SOP.

The current accepted plan is explicitly titled “policy changes without scans” (`MVP-PLAN.md:421`), removes the scan-based fence from admission (`:437-438`), and the owner-approved registry-pruning contract says “no timers and no file-system scan” (`SafeUpload.Minifilter/StageWriters.c:3697-3703`). These clauses make a candidate namespace census a plan change; they do not name an identity-only enumeration separately. The canonical goal does not itself prohibit scanning.

Even if that plan change were accepted, a census alone is not a privacy barrier. An already-live section can issue paging I/O while the census is in progress. A paging write from an unregistered file object carries no usable pathname; Filter Manager name lookup may be unavailable for paging I/O, and a cache-only name query can fail on a miss. Before its SOP is inserted, the write cannot be matched to the candidate namespace. Stopping it would require a volume-wide paging fence or a gate that existed before the section was created; the active plan rejects a volume-wide fence and the exact M1 requires successful write/flush evidence. Waiting to publish the candidate policy until the census finishes therefore leaves a write window, while publishing a pending policy does not make an unknown paging object identifiable.

## Why the current minifilter cannot turn the census into private mapped writes

The public mapped section already holds the NTFS file's section object and shared cache state. Its CPU stores update those mapped pages directly; paging writes are the persistence path that a filter can inspect. The current public paging path calls `SafeUploadStageWritersBeginPagingIo` and denies a write only if the exact SOP is tracked and matches current/pending policy (`SafeUpload.Minifilter/StageStream.c:3330-3353`). Denial cannot meet the repro's successful-write/flush gate. Reporting success after copying a paging buffer to private backing still leaves the modified page in the public file's resident section/cache. An already-existing reader of that same section can observe it; a new buffered reader can also see shared cache data unless the filter redirects that reader to a separate approved snapshot. The current source has no such per-SOP snapshot/read binding. The existing design review records the cache observer gap for a paging-write fence without read redirection (`STAGED-WRITES.md:582-590`).

The project has a private SOP for its owned `StageStream` file object: it opens an uncached private backing and installs `&stream->Sections` on the newly created StageStream file object (`SafeUpload.Minifilter/StageStream.c:1133-1151,1426-1450`). That changes the backing of file objects created through the owned-stream path. It does not change the `SectionObjectPointer` held by a section that NTFS created before attachment or before policy expansion. `FltCreateFileEx2` returns an opened file object; `FltCreateSectionForDataScan` creates a new section backed by the specified file object for scanning. Neither documented interface rebinds an application's existing section or view.

`MmCanFileBeTruncated(SOP, NULL)` can establish a useful no-user-reference/truncatability observation for a known SOP; it returns false for mapped views, outstanding write probes, image sections, or data-section references, and runs below DISPATCH_LEVEL. It is not an identity resolver or a section-rebind operation. `MmDoesFileHaveUserWritableReferences` can detect writable views even after file and section handles close, but also needs the exact SOP and has no API to revoke those views or change their backing.

Cache repair does not provide the missing routing layer. Microsoft documents that `CcPurgeCacheSection` “will not purge mapped files” and requires the caller to acquire the file exclusively and ensure no thread has mapped or pinned any byte. A minifilter over NTFS does not own NTFS's exclusive FCB/resource. `CcCoherencyFlushAndPurgeCache` is synchronous, requires exclusive file ownership, and has no purge-only mode; it flushes as part of ensuring coherency, which may commit the unapproved data before a purge. Neither DDI is a safe way for this minifilter to sanitize a still-live public cache.

The pinned WinFsp study was consulted first: `output/mvp-continuation/winfsp-cleanup-w01-question-review.txt:29-47` points to WinFsp commit `fde790d8ea41283606d1c56b557608a17e455f59`, where cleanup and close are separate and test mappings can outlive the source handle. That source is lifetime stimulus only; WinFsp owns its own file node/cache. It does not provide a mechanism for an NTFS minifilter to retarget an existing section.

## Required architecture change and exact unknowns

## Minimal minifilter design candidate for the scripted M1/M2 oracle

The exact post-write oracle does not require rebinding the old `SECTION_OBJECT_POINTERS`. It can be met by isolating lower persistence and independently redirecting public reads, provided the binding is prepared before any relevant paging write is sent to NTFS:

1. Pin a versioned mapping entry by `(instance, full 128-bit file ID, ADS suffix, exact SOP, generation)`. For M1, enumerate the current BootPolicy scope and bind candidate streams before `FltStartFiltering` starts dispatching I/O. For M2, publish a pending policy/epoch, use the existing since-boot writer/SOP registry for candidate entries, and complete any identity-only enumeration before publishing the new current policy. The census establishes candidate identity completeness only; never treat it as quiescence. The active “policy changes without scans” plan and the owner-approved no-filesystem-scan pruning comment must be revised for this step.
2. Before activation, create two durable private versions from the allowed baseline: a read-only approved snapshot for fresh public path opens, and a writable quarantine/stage version for writes from the extant public section. Keep the original NTFS file and its allocation untouched so M1's physical LCN/raw observer remains stable. A census is not an attach barrier for writes made before the filter starts; the exact M1 stimulus writes after `fltmc load`. Late attach with possible writes already persisted before binding remains untrusted and unqualified.
3. Replace the current matched-SOP paging-write denial with a private lower-write route. The existing `StageRoutePaging` child-I/O pattern (`StageStream.c:1880-1944`) already clones the paging MDL and completes the upper request from the private backing's actual lower completion. Extend it to a public SOP registry entry, retaining the W/reference through child completion. Do not pass a matched paging write to public NTFS. Intercept `IRP_MJ_FLUSH_BUFFERS` on the old physical file object and flush its private quarantine backing; this is necessary for M2's still-open pre-expansion file handle and its successful `FlushFileBuffers` call.
4. Route fresh buffered and uncached opens to the approved snapshot file object/cache, never to the old NTFS shared cache. The present `StageCreate` passes read-only opens through when no view exists (`StageStream.c:1317-1320`) and rejects `FILE_NO_INTERMEDIATE_BUFFERING` (`:1322-1327`), so both behaviors need deliberate implementation. Keep M1's `FSCTL_GET_RETRIEVAL_POINTERS` probe on the original physical stream so the test observes the stable NTFS LCN, while its fresh data reads use the approved snapshot. M2's retained-view uncached read occurs while the old view is still alive (`Test-StagedPolicyTransitionMapping.ps1:1252-1255`), so snapshot redirection must already be active before that read.
5. Retain the per-SOP shadow binding while a mapped section handle or mapped view can still issue paging I/O. Do not retire on Cleanup, Close, zero `MmDoesFileHaveUserWritableReferences`, or a completed flush. Drain W/other in-flight state, reopen and verify the exact SOP, use `MmCanFileBeTruncated(exactSOP, NULL)` only as the mapped-reference/quiescence predicate, and also wait until the relevant section/cache state is actually gone before allowing physical reads or retiring the mapping. A retained section handle therefore keeps routing installed and a view created from it later writes to the private version.

This candidate can in principle satisfy the current scripts' successful mapped-write/flush plus stable public raw extent and approved fresh-reader observations; it is not implemented or runtime-qualified. The successful `FlushFileBuffers` condition is not inherently incompatible with privacy if the filter flushes the private quarantine version and the independent readers use the approved snapshot. The candidate needs a new service allocation/copy operation, per-SOP shadow state, read and flush redirection, noncached read support, transactional policy publication, and source/build/runtime review. Do not mark the mapping DOD complete before both exact scripts pass.

This candidate does **not** split a public section already shared by multiple old views. CPU stores alter its resident pages before paging I/O. Any other process that already maps the same NTFS section may see those bytes, and a filter cannot rebind/revoke that extant view with the reviewed documented APIs. The current scripts do not include a second simultaneous preexisting mapped reader. If canonical privacy includes such a reader, the necessary design is stronger: all protected mappings must be created behind a pre-admission namespace/section owner, or the product must prove such old readers cannot exist at cutover. Treat this as an explicit privacy gate, not as a success implied by the raw/new-reader tests.

The broader architecture option is therefore a pre-admission file-system/namespace virtualization layer, or an equivalent storage design with distinct private-writer and approved-reader views, when protection must include simultaneous mapped readers. A boot-start minifilter and “untrusted until reboot” readiness policy narrows ordinary deployment exposure but does not prove late-attach safety. An identity census can complete bindings; it cannot prove quiescence or repair changes already persisted before attachment.

## Minimal architecture revision that can meet the full privacy contract

The supported protected namespace must be owned before the first application open or section creation. Each logical file needs an immutable approved backing and a separate transaction backing for unapproved writers. The owner assigns the writer a file object/section backed by its private transaction; approved readers get a distinct file object/section backed by the last approved generation. Paging writes and `FlushFileBuffers` from the old writer view succeed against the transaction backing, while the public approved view continues to resolve to the immutable generation. Approval atomically publishes a new generation. Because the two views have distinct backing streams and section pointers from their creation, isolation does not rely on revoking or rebinding an NTFS section after its views exist.

For a destination currently stored on NTFS, retain the existing base file as the approved generation and never issue the old writer section against that NTFS file object. The owner can keep the base file ID and physical extents stable, report or record those exact lower extents for the independent raw observer, and direct all unapproved mapped writes to a private overlay object. This preserves a same-base-inode/extent raw baseline while moving the mapped section to an owner-controlled namespace view. If acceptance instead requires the application mapping and raw observer to use the very same NTFS file object/SOP, that requirement conflicts with privacy from another view of the already-shared NTFS section; no reviewed supported minifilter API resolves that conflict.

M1 can remain a pre-SafeUpload-policy-attachment test if the namespace owner is already mounted before fixture creation: the fixture map predates the SafeUpload minifilter and policy, but it is created through the owner that already routes its section to a private writer generation. The test must still require mapped write and flush success, release all handles/views, read through independent approved buffered and uncached paths, compare the raw lower extent byte-for-byte, and verify stable base ID/extents. M2 similarly keeps its old section handle and tests a policy expansion while writes remain private. The ownership layer must preserve these exact independent gates; the path under test should be the protected namespace path and the raw observer should identify its immutable lower backing, rather than pretending a standard NTFS section can be retargeted.

This is a substantial product architecture change, not a local minifilter patch: namespace ownership has to cover every supported destination adapter (fixed NTFS, USB, SMB/UNC, and sync-client destinations) before exposure; branch identity, durable quarantine, crash/recovery, approval publication, and direct-alias bypass all need explicit handling. The regular build still compiles staging out. Until that owner exists, leave the current NTFS pre-attachment and policy-transition privacy gates open, keep taint and unsupported destinations disabled, and do not treat boot-start readiness or the narrower successful-script candidate as full privacy proof.

Do not mark M1/M2 complete, relabel a refused mapped flush as blocked, or weaken either repro. Taint and unsupported-capability disablement remain until the selected design is implemented and both scripts pass with their independent observers; any concurrent-old-reader privacy requirement must pass its own gate too. VM execution remains gated by the parent task's signed-artifact and guarded-harness condition.

## Primary contracts reviewed

- [`MmCanFileBeTruncated`](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-mmcanfilebetruncated) — exact SOP input, truncation result conditions, and IRQL `< DISPATCH_LEVEL`.
- [`MmDoesFileHaveUserWritableReferences`](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-mmdoesfilehaveuserwritablereferences) — exact SOP input and the documented closed-handle writable-view detection use.
- [`CcPurgeCacheSection`](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ccpurgecachesection) — does not purge mapped files; exclusive-file and no-mapped/pinned-byte preconditions.
- [`CcCoherencyFlushAndPurgeCache`](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-cccoherencyflushandpurgecache) — synchronous flush/purge, exclusive-file requirement, no purge-only option.
- [`FltCreateFileEx2`](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltcreatefileex2) — opens/creates a file and returns a file object; it does not describe rebinding a prior section.
- [`FltCreateSectionForDataScan`](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltcreatesectionfordatascan) — creates a new section backed by the supplied file object for data scanning.
- [Memory mapped files in a file-system filter](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/memory-mapped-files-in-a-file-system-filter-driver) — filters that handle memory-mapped I/O generally must filter paging I/O.
- [Pinned WinFsp cleanup/mapping review](../../../output/mvp-continuation/winfsp-cleanup-w01-question-review.txt) — pinned source comparison, not Windows NTFS runtime evidence.
