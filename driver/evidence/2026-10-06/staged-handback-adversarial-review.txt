Findings (highest severity first)
==================================

P0 — A recycled session ID rebinds another user's blocked version and justification

Files/lines: agente/SafeUpload.Agent.Service/Interception/MinifilterInterceptor.cs:448-453; StagedHandbackCopier.cs:83-86,258-280; StagedTransferPublisher.cs:344-407; Notifications/StagedJustifications.cs:8-34; Notifications/JustificationPipeServer.cs:100-103,181-186.

Sequence: Alice creates a blocked staged version in session N. The durable StagedTransfer stores the process ID and nullable session ID, but no SID. If the service stops before hand-back completes, Alice logs off and Windows reuses session N for Bob. Recovery calls WTSQueryUserToken(N), accepts Bob because the token's session number matches, resolves Bob's ProfileList entry, and copies Alice's staged bytes into Bob's profile. If the justification window remains open, recovery also registers the override for session N. The pipe server identifies its client by session number only; Bob can submit Alice's event ID and the callback can publish Alice's version after policy reinspection. This exposes one user's blocked bytes to another user and lets the wrong principal authorize release.

Minimal fix: persist the original requestor SID with the transfer when it is allocated, obtained from the requestor's authenticated process token. Require the WTS SID to equal that persisted SID before hand-back or recovery, and obtain/check the named-pipe client's SID before accepting a justification. On missing or mismatched identity, retain staging and do not route the hand-back notification to the session currently using that number.

P1 — Verified hand-back is mutable, but cleanup never re-verifies it

Files/lines: StagedHandbackCopier.cs:117-134,475-530,564-569; StagedTransferPublisher.cs:349-407,415-455; StagedTransferJournal.cs:622-659.

Sequence: the copier creates the returned file with FullControl for the target user and SYSTEM, verifies it, closes its handles, and journals HandbackState=Verified. While the justification window is open, that same user overwrites, deletes, or renames the file (the ACL explicitly permits it). At expiry, ProcessBlockedCleanupAsync rechecks only the staged file's digest, deletes staging, and records StageDeleted. On restart, RecoverBlockedAsync also trusts Verified and resends the stored path/digest without reopening the hand-back. The blocked version is then lost even though the returned copy is absent or no longer matches the digest.

Minimal fix: immediately before deleting staging, reopen the saved hand-back through the same verified handle-relative path walk and check its owner, protected ACL, single-link count, length, and digest. Hold the hand-back file and directory handles with sharing that denies writes and deletes through the stage deletion; if the file is absent, changed, or cannot be locked, retain staging and retry. A read-only user ACE and non-mutable service-owned hand-back directories would reduce the race surface, but the cleanup-time verification/lock is still needed for restart safety.

P1 — Protected/sync-root refusal compares path spellings, not the target directory identity

Files/lines: StagedHandbackCopier.cs:96-103,137-164,174-228,231-237.

Sequence: the target and every registered policy/sync root are reduced with Path.GetFullPath, then compared as strings. This does not resolve filesystem aliases such as a short 8.3 spelling or an extended-length spelling to the same directory. A standard user able to register a Cloud Files root for their profile can register the same physical SafeUpload/profile directory using an alternate spelling. If that spelling is retained in UserSyncRoots, the prefix test misses it, while OpenBlockedDirectory opens the ordinary spelling and creates the hand-back in the same physical synced tree. The blocked bytes can then be synchronized despite the refusal check. The same lexical comparison can miss a policy scope configured using an alias.

Minimal fix: compare resolved directory identities, not strings: open target and registered roots safely, establish volume/file IDs, and determine whether a registered root is an ancestor of the destination by walking directory handles. Fail closed if a registered root cannot be resolved. Keep the existing no-reparse checks for the actual destination walk.

P1 — Unknown requestor session makes the new blocked notification broadcast

Files/lines: MinifilterInterceptor.cs:448-453; StagedTransferPublisher.cs:217-223,399-407; Notifications/NotificationHub.cs:174-183.

Sequence: if ProcessIdToSessionId fails when the allocation request is handled (for example, the requestor exits during the service lookup), SessionId is null. The copier correctly fails closed, but the publisher still sends the Blocked notification with the file name, findings, and sealed-snapshot digest. NotificationHub treats a null target session as broadcast, and its pipe is readable by Builtin Users. Every connected user's agent can receive those details even though no owner session was established.

Minimal fix: do not broadcast staged Blocked notifications when owner identity is unknown. Persist and route by the transfer's verified owner SID; until it resolves, retain the event for that owner or suppress the sensitive notification. Keep broadcast behavior only for event types whose contract explicitly permits it.

P2 — Failed hand-back attempts leave service-created temporary files behind

Files/lines: StagedHandbackCopier.cs:115-128,532-545.

Sequence: after the initial final-name check, the copier creates a random .safeupload-<transfer-id>-<nonce>.tmp and writes the full snapshot. If verification or the no-replace rename fails, disposing the streams does not delete that name. A user watching the directory can learn the transfer ID from the temp name and race-create the final name; the rename then fails safely, staging is retained, but the completed temp remains. Repeated blocked transfers/retries can accumulate full-size files and consume profile disk space; crash leftovers are also not tracked for later cleanup.

Minimal fix: delete an uncommitted temp by its open handle in a finally path on every caught failure. For crash recovery, journal the temporary name or perform a constrained handle-relative cleanup of this service's temp prefix after verifying ownership, ACL, reparse state, and link count.

P2 — State-history validation does not validate the first history state

File/lines: StagedTransferJournal.cs:232-250.

Sequence: the validator checks each timestamp/state transition only from index 1 onward and only checks that the last item equals State. A manifest with State=Released and a one-item StateHistory=[Released] therefore passes despite Release having no valid predecessor in IsTransitionAllowed. The journal is service-protected, so this is not a standard-user forgery path, but malformed/corrupted history is accepted as valid evidence.

Minimal fix: distinguish a legacy seed from a newly created history and validate the first state accordingly; at minimum reject nonempty histories that cannot be a legitimate seed (including Released). Keep empty history readable for legacy manifests, as the current migration path intends.

Additional checks
=================

- Profile resolution: the copier reads HKLM\ProfileList for the SID returned by WTS, requires a fully qualified path on a ready local NTFS volume, opens each component from the volume handle with OPEN_REPARSE_POINT, rejects directory reparse attributes, and verifies the final profile directory owner equals that SID. A standard user cannot redirect ProfileImagePath in HKLM. The material identity weakness is that the SID is selected from the current owner of a reusable session number, rather than bound to the original transfer (P0 above).
- Path use/reparse checks: the actual SafeUpload/_bloqueados walk and final/temp file opens are relative to retained directory handles. Final and temp names use OPEN_REPARSE_POINT; temp creation uses FILE_CREATE; final rename is relative and no-replace. The written handle itself is checked for reparse attributes and LinkCount==1 before and after rename, then the committed name is reopened and checked. I found no direct pre-created-hard-link route to make the service write or ACL an existing file. The returned path is a lexical string, however, and the durable Verified marker does not prove that it still names the checked file later (P1).
- ACL: creation supplies a protected D:P DACL with exactly the target SID and SYSTEM before the first byte is written, and readback checks the ACEs, flags, owner class, length, digest, and link count. One Windows-specific detail remains implicit: the SDDL has no O: owner field, and verification accepts only the target SID or SYSTEM. If the LocalSystem token's default owner is another SID, creation fails closed at verification; set the intended owner explicitly and verify it on the Windows builder. The note's assumption that the default is SYSTEM was not exercised here.
- Cleanup gate: journal and publisher both gate StageDeleted on HandbackState=Verified and JustificationWindowClosed; the stage digest is rechecked before File.Delete, and cleanup progress is durable across restart. I found no path that deletes staging before those two journal conditions. The P1 issue is that Verified is treated as permanent even though the user can change the hand-back afterward.
- Restart/idempotency: Copying recovery adopts an existing final name only after read-only digest/ACL/link verification, and Verified recovery does not repeat the copy. This is reasonable for crash-after-rename, but it is not sufficient for the later mutable-copy case above. Legacy manifests with missing StateHistory remain readable and are seeded on a subsequent state transition.
- UI strings: the hand-back leaf is transfer-ID plus a sanitized extension, the service-generated path and digest are rendered as plain TextBlock text, and findings are masked by the scanner. The path/digest can nevertheless be stale after user replacement/rename or session reuse (P0/P1 above). The destination file name is user-derived; Windows file-name rules prevent newlines, but no separate bidi/control-character display normalization is evident.
- Sync/policy tests in the new test file cover ordinary matching path spellings, not filesystem aliases or a registered root changing during the check/use interval. The implementation note also says the Windows handle operations, effective ACL test as a second user, sync-provider registry layouts, and restart suite were not run. No build or tests were run as part of this read-only review.
