SafeUpload existing FILE_OPEN source-lease research (Luna)
Date: 2026-10-06
Scope: read-only API/source research. No product source, VM, key, store, or trust operation was changed or run for this review.

Finding
========

A retained original-file handle is a plausible narrow way to make NTFS perform a real caller-subject access check and share-access check for an existing FILE_OPEN, while application reads/writes use the private WinFsp object. It is not implemented or proven, and it does not qualify full Windows file behavior. Keep the route disabled until the preconditions, cleanup, per-open access-mask comparison, and runtime byte/section tests below are implemented and pass.

Potential FILE_OPEN contract
===========================

1. In the original create pre-operation, copy a client security context from
   `Data->Iopb->Parameters.Create.SecurityContext->AccessState->SubjectSecurityContext`
   with `SeCreateClientSecurityFromSubjectContext`, using local-server semantics
   and static token tracking. Do this while the original AccessState is live;
   do not capture the worker thread's current token or use PID as an identity.
   A trusted worker can impersonate this captured context with
   `SeImpersonateClientEx`; always pair success with `SeStopImpersonatingClient`
   and delete the client context. Missing or unimpersonable subjects fail closed.

2. Admit only an existing fixed-NTFS file with CreateDisposition exactly
   `FILE_OPEN`. Initially reject create/overwrite/supersede/delete, streams,
   directories, file-ID or relative-handle opens, open-reparse-point,
   delete-on-close, EAs, requested security descriptors, nonzero allocation
   size, transactions, unsupported create flags, and mismatched access state.
   In particular, do not silently reconstruct a nonzero
   `AccessState->PreviouslyGrantedAccess`: FltCreateFileEx2 has no AccessState
   parameter. A first profile should require the source request's prior grant
   to be zero and the raw remaining/requested masks to agree; all other cases
   remain unsupported.

3. Before service allocation or reparse, open the normalized source path with
   `FltCreateFileEx2` at PASSIVE_LEVEL, below SafeUpload's source instance,
   while impersonating the captured subject. Use the exact source
   RemainingDesiredAccess, ShareAccess, and accepted CreateOptions, with
   CreateDisposition `FILE_OPEN`; include `OBJ_KERNEL_HANDLE` and
   `OBJ_FORCE_ACCESS_CHECK` in OBJECT_ATTRIBUTES and `IO_FORCE_ACCESS_CHECK` in
   Flags. Never set `IO_IGNORE_SHARE_ACCESS_CHECK`. Also require normal kernel
   APCs enabled and `IoGetTopLevelIrp() == NULL`; Microsoft warns that
   FltCreateFileEx2/FltQueryInformationFile can deadlock with a non-null
   top-level IRP. If a safe worker/cancel-safe queue cannot process the request,
   deny it instead of clearing TopLevelIrp.

4. Query the retained handle for `FileAccessInformation` and full file identity
   (volume serial/GUID plus 128-bit FileIdInformation). Treat that open itself
   as the source identity used by the owner route; avoid an extra transient
   target probe before it. Bind path, parent/name slot, identity, access mask,
   scope, process reference, and one-use FSP grant before any stage allocation.
   Any path/identity change or sharing/access failure aborts before reparse.

5. Carry the source handle and actual access mask in the kernel's one-use
   grant. The FSP target create must not become successful unless its final
   GrantedAccess equals the source lease's queried access mask (or a separately
   reviewed exact mapping is defined). Pinned WinFsp `create.c` initializes the
   request from AccessState RemainingDesiredAccess/PreviouslyGrantedAccess at
   lines 306-307 and writes the final response mask back to
   `AccessState->PreviouslyGrantedAccess` at line 1134. A minifilter post-create
   can compare that result and cancel the FSP open on mismatch before exposing
   it. Only then attach the lease to a per-open stream-handle context.

6. Keep one retained source lease per FSP file object. Release it exactly once
   on the kernel-observed FSP `IRP_MJ_CLOSE` path (pre-close, PASSIVE_LEVEL),
   plus all failed/cancelled-create and teardown paths. Do not make a WinFsp
   user-mode Close callback the only release signal: the pinned kernel driver
   posts Close as best-effort and may drop it when the request queue is stopped.
   Minifilter contexts cannot be attached in pre-create; attach in post-create.
   Post-close cannot query contexts, so release from pre-close or a separately
   drained PASSIVE worker. Cleanup is earlier than final file-object close.

7. Preserve the independent source-byte observers. A FILE_OPEN lease does not
   write source data; user writes and mapped sections go to private WinFsp bytes.
   A passing observer must therefore show public NTFS buffered, uncached, and
   raw bytes unchanged while private bytes change and flush. This is an
   incremental staging behavior, not full source-file coherence: compatible
   external writers are allowed when the exact source ShareAccess allows them,
   and can change the public file while this process sees a private snapshot.
   If FILE_SHARE_DELETE is honored, rename/delete can move the path while the
   lease pins the old object; every future publication must revalidate full
   identity and refuse to replace a different object. Holding through FSP
   IRP_MJ_CLOSE can outlast the application's last handle/cleanup when a section
   keeps the FSP file object alive, so measure and qualify that stricter sharing
   interval.

8. FltCreateFileEx2 with the current instance sends the synthetic source open
   only to minifilter instances below SafeUpload and the file system. Higher
   filters saw the original request, which will return reparse, but do not see
   the synthetic successful source open. This is a documented observability
   difference and must not be described as full filter-stack equivalence.
