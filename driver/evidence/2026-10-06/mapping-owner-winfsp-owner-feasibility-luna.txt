# WinFsp filesystem-owner feasibility for mapping privacy

Read-only source and architecture review, 2026-10-06. This note extends the
frozen mapping-owner investigations without modifying them. No product source,
build, VM, trust store, or runtime state was changed. No WinFsp dependency was
installed and no runtime qualification is claimed.

## Finding

WinFsp is a concrete filesystem-owner candidate: its kernel filesystem driver
owns file nodes and their cache/section state, while a user-mode filesystem
service implements the file operations. It can provide the ownership boundary
the current minifilter-created application file object has not established.
WinFsp's API also makes an important constraint explicit: by default the same
file name must return the same file-node context while that name remains open
anywhere. Pinned `src/sys/create.c` inserts a new FileNode into a by-name table
and reuses the existing node when the name is already present. The API's
`UmFileContextIsUserContext2` changes the callback context to per-open
descriptors; it does not make a second SOP/cache map for the same name. Thus
two transactions cannot have independent mapped state behind the same
WinFsp-internal path. Separate writer generations need distinct internal
paths; the same writer's repeated opens intentionally resolve to that writer
generation's one path and node.

The smallest WinFsp route worth testing is the writer-only owner route:

1. Keep the physical destination on NTFS as the approved public generation.
   Non-writer processes, including the independent buffered and uncached
   observer processes, continue to open the real NTFS path. This preserves
   their normal destination volume, file ID, allocation, and raw-volume view.
2. For every candidate mounted source volume, route every write-capable open
   before the current `StageCreate` completion path, including opens before
   policy activation. M1/M2 require ownership from first open, so routing only
   names that the current policy already classifies would leave a retained
   public SOP behind for later policy expansion. Resolve and pin the original
   volume plus full file identity (or parent identity and serialized new-name
   slot), stream/ADS, target generation, owner epoch, and writer authority.
   Reparse the writer's logical open to a unique WinFsp internal name such as
   `\??\<owner-mount>\w\<entry>\<generation>`. Repeated opens and
   read-your-writes by that writer map to the same private generation name.
3. The WinFsp filesystem owns that writer node and its SOP/cache map. Its
   service writes the staged bytes into an ACL-protected NTFS transaction
   store that ordinary callers cannot open directly. Policy inspection,
   sealing, durable approval, and publication remain separate transitions;
   approval publishes to the real NTFS destination only after exact identity,
   owner epoch, scope, and generation validation. Before approval, the
   physical destination and raw observer remain unchanged.
4. A non-writer open continues on NTFS; a read by a process/owner group with
   an active private generation routes to that same generation. The original
   minifilter remains the early admission and bypass fence on every candidate
   source volume. Missing service, mount, grant, journal, or recovery
   readiness refuses a candidate-volume mutating open and leaves the volume
   NotReady. Privacy ownership/allocation is
   available before apps open files; policy and publication can still start
   later as authorized.

This variant is smaller than routing every reader through a second logical
public generation and directly preserves the M1/M2 independent-reader and raw
observer predicates. It does not automatically preserve every Windows file
operation's same-volume and identity behavior. A redirect into WinFsp produces
a file object owned by the WinFsp volume. `FSP_FSCTL_VOLUME_PARAMS` can choose
reported volume metadata and `FSP_FSCTL_FILE_INFO` has a 64-bit `IndexNumber`,
but that is not evidence that the resulting handle has the original NTFS
volume device identity or full `FILE_ID_128`. Existing M1 repro scripts do not
assert the writer handle's physical volume object or file ID; the broader
SafeUpload identity, rename, alias, and file-ID behavior still must be
qualified. A minifilter query/name translation may be possible, but it must use
documented callbacks and be tested against real applications rather than
assumed from a configurable volume serial or display path.

Broad ownership has a second consequence: all candidate-volume writable opens,
including those currently outside the protected policy, must remain associated
with an owner node so a later policy expansion needs no directory scan. The
owner journal must represent such entries as policy-pending/eligible and keep
the stream private. A policy transition while a mapped handle remains open
needs a serialized generation boundary: any old allowed generation must be
fully flushed/classified before its public commit, and post-transition writes
on the retained SOP must be routed to a new private backend generation. How
the FSD performs that boundary without losing successful-write/flush semantics
is part of the first proof slice, not something the minifilter can fix after
the application section exists.

## Exact integration points and security protocol

The candidate routing point is the feature-build create branch in
`StageDispatchCore` (`driver/SafeUpload.Minifilter/StageStream.c`), which calls
`StageAdmit` before legacy taint/policy callbacks. In owner mode, `StageAdmit`
must decide the source identity and route before `StageCreate` installs an
upper file object/SOP. The existing `StageCreate` path is not reused to graft
its SOP onto the WinFsp object. A documented minifilter create-time reparse
pattern (as in Microsoft's SimRep sample) is a possible namespace handoff;
name normalization, ECP handling, reparse loops, source-to-owner instance
attachment, and reopen behavior need explicit tests. The WinFsp callback then
implements the operations on its own node: create/open, read/write, flush,
set information, rename, cleanup/close, streams, security, and notifications.
SafeUpload currently has no registered name-provider callback, so preserving
logical opened/normalized names after reparse needs a new reviewed name-mapping
implementation or an explicitly qualified application-visible name change.

The route needs an authenticated, non-replayable owner grant from source
pre-create to the WinFsp Create/Open callback. Microsoft documents a
provenance carrier: a minifilter can create a driver-defined ECP, attach it to
the current create through `FltSetEcpListIntoCallbackData`, and dynamically
added ECPs are cleaned up at create completion and can propagate across
reparse points. On the WinFsp-volume pre-create, SafeUpload can require this
ECP, reject a caller-originated ECP with `FltIsEcpFromUserMode`, and bind the
opaque grant ID to the exact `FltGetRequestorProcess` object retained in its
grant table. The authenticated minifilter/service channel prepares the
matching one-use grant, binding source volume plus full identity (or parent
and new-name slot), stream, token, process-object lifetime, owner epoch, and
generation. The internal FSD path can carry the opaque ID to find that
prepared generation, but the path is a lookup key, not authorization. The
filter must validate the kernel-generated ECP and grant before the create
reaches WinFsp; the FSD service must default-deny direct private-name opens
and reject any generation without a prepared service grant. PID alone is
insufficient because it can be reused; a random hidden path alone is not
permission. Confirm that the pinned WinFsp create path and SafeUpload's
instance altitude preserve and expose this custom ECP before treating the
bridge as proven. Do not attach or spoof system-defined ECPs, depend on
fabricated `AccessState` or `RequestorMode`, or grant callers direct access to
the backing store. Other original ECPs relevant to create semantics must be
preserved according to Microsoft's contracts.

The NTFS backing directory must have a service-only DACL from creation,
remain protected after driver/service failure, and be outside synchronized
destination roots. WinFsp's tutorial documents a LocalSystem service model and
its Backup/Restore privileges for operating an NTFS backing store under that
service identity. That establishes a feasible storage approach, not an
acceptable SafeUpload ACL: the actual owner, group, DACL, service binary,
recovery behavior, and direct-path denial need a separate review and tests.

## Hard compatibility and destination gates

- **Stable identity and file-ID opens:** SafeUpload currently keys much of its
  registry by source volume and full 128-bit FileId, and tracks stream suffix,
  hard-link names, and rename generations. WinFsp's file-info index number is
  64-bit and its compatibility list says `FILE_OPEN_BY_FILE_ID` is
  unsupported. A filter-side translation from source ID to an authenticated
  private path could be built, but it must preserve aliases, ADS, replacement,
  and retained-handle semantics without a path-to-object race. Test query-by-ID
  and `OpenFileById` against the exact existing contract. Fail closed if the
  mapping is unknown.
- **Rename and replacement:** writer handles live on the WinFsp volume while
  the public destination is on the source filesystem. Same-volume rename,
  `RootDirectory` handles, `REPLACE_IF_EXISTS`, open source/target handles,
  delete-on-close, tombstones, hard links, and name-provider results need
  exact tests. WinFsp supports ordinary rename/delete but documents no hard
  links and no stream rename. Translate a rename into owner namespace/journal
  operations; do not issue a cross-volume physical rename from an FSP handle
  and assume NTFS semantics.
- **Raw extents and independent observers:** M1's current scripts obtain the
  fixture's NTFS LCN from a separate open to the physical destination, then
  compare full raw-sector bytes; that is compatible with writer-only
  redirection if the source file remains allocated and unmodified. A query of
  `FSCTL_GET_RETRIEVAL_POINTERS` on the WinFsp writer handle is a different
  operation and WinFsp documents sparse/volume-specific FSCTL limitations.
  Preserve and rerun the exact script predicates; do not fabricate extents or
  substitute a buffered read for the raw observer.
- **USB/removable:** route every supported volume alias and file-ID open,
  retain the exact source-volume binding across remove/reinsert, and prove
  pending generations remain private and recoverable while the physical
  destination is unavailable. The stage remains on the protected local store;
  publication is refused until the exact device identity is back.
- **UNC/SMB:** a local minifilter/WinFsp owner does not protect a second
  machine or a server-side writer that bypasses this client. SMB share leases,
  reconnect, access checks under service credentials, and cross-machine
  writers require explicit qualification or server-side ownership. Do not
  report UNC protected from one client's local redirect alone.
- **Sync clients:** test a real supported sync client, including its service
  process, placeholder/reparse behavior, alternate APIs, and restart. The
  service-only private store must stay outside every sync root; the client must
  receive only approved physical content. A client process that writes a
  protected path must go through the same owner grant and policy path.
- **Boot and readiness:** current SafeUpload coverage readiness requires fixed
  NTFS and a passed NTFS canary. An owner volume/instance must be identified
  explicitly and accepted only when its service, mounted filesystem, journal,
  policy epoch, and backing are healthy. A boot-start filter can fence source
  creates until the WinFsp owner is ready; it must not report protection Ready
  merely because the source NTFS filter attached. The user's approval permits
  owner allocation before policy/inspection/publication and an initial
  restart, but it does not waive all early creates or late-attach rules.
- **Dependency:** no WinFsp SDK, link target, FSP file-system project, or
  WinFsp-specific driver attachment path exists in the SafeUpload product
  tree. The repository contains only source-study and workload evidence. A
  real route needs a pinned supported WinFsp package/source version, license
  decision, installed kernel driver, new service/FSD project, service
  startup/dependency ordering, driver attach changes, and test deployment.

## Decision boundary

WinFsp writer-only routing is the smallest concrete owner prototype because it
can isolate the mapped writer generation while leaving M1 independent readers
and physical raw observers on NTFS. It is not yet an implementation plan for
all supported destinations. The first proof slice must test successful mapped
write and flush through WinFsp, a retained mapped section, separate
same-writer private reads and independent direct-NTFS reads, full unchanged
raw bytes/extents, private-store ACL/direct-path denial, crash/recovery,
query/file-ID behavior, rename/replacement, and service/mount failure—all on
the pinned builder/debugger snapshots. Only after that source→FSD grant and
identity/rename contract is reviewed should a new product path be selected.
USB, UNC/SMB, and a real sync client remain independent open gates. Until the
integrated route passes the owner's complete DOD, normal builds stay compiled
out, taint remains, and unsupported destinations/capabilities remain disabled.
