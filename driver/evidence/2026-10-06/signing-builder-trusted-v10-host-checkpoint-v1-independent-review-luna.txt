I confirmed two deterministic blockers that prevent every phase from reaching
its intended checkpoint action:

1. The host helper reads its own inputs.json successfully, then unconditionally
   parses the frozen V10 `plan.md` as JSON (`json.loads` of V10PlanPath). That
   file begins with Markdown (`# V10 trusted signer checkpoint package`), so
   this raises JSONDecodeError before the first libvirt command. The pinned
   path/hash are in inputs.json; the source format and parse failure were
   verified locally without execution.

2. `normalized_domain()` removes only the vda source value and any vda
   `backingStore`. `check_preflight()` and `verify-host` compare that result
   from the live XML with the inactive original XML. The actual pinned
   preflight `live.xml` begins `<domain type='kvm' id='12'>`, while
   `domain-initial.xml` begins `<domain type='kvm'>`; the live-only domain ID
   survives normalization. Thus a normal running-domain dump cannot compare
   equal. The failure occurs in preflight/shutdown before shutdown is requested.

Additional fail-closed corrections are needed before this recovery helper can
be approved:

* `restore-definition-before-start` checks that the current vda path is the
  child, then defines the complete initial XML. It does not first require the
  current normalized definition to equal the pinned definition with only the
  vda source changed. An intervening unrelated XML edit could be silently
  overwritten. Require the full allowed-delta comparison before restoring.
* The restore gate treats `start.txt` as proof that the child was started, but
  that marker is written only after `virsh start` returns. A runner failure in
  the interval after a successful start and before the marker write can leave
  no marker. Persist a start-attempt marker before calling `virsh start`, and
  refuse pre-start restore whenever it exists.
* `verify-host` walks the QMP chain recursively and rejects retry1 anywhere,
  and it checks child -> retry2, but it does not require the next node to be
  the pinned Recovery3 image. If the stated lineage is required after boot,
  assert child -> retry2 -> Recovery3 explicitly while retaining the
  whole-chain retry1 exclusion.
* `inputs.json` says `ReadyForExecution: true` while the package's plan says it
  remains review-only until review and fresh host gates pass. The executable
  guard checks the former boolean and does not consume a review attestation.
  Keep execution readiness false until review is complete, or bind and require
  the exact review record before a mutating phase.
