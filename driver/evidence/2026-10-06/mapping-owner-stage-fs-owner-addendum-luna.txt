# M1/M2 owner path: supported filesystem ownership addendum

Architecture review addendum, 2026-10-06. It supplements, and does not rewrite,
the frozen `mapping-owner-stage-m1-m2-integration-plan-luna.txt`. This is a
source/design review only. No driver, service, repro, signing, or build source
was changed; no runtime qualification is claimed.

## Finding that changes the implementation boundary

The present `StageCreate` completes a create above NTFS, installs SafeUpload's
own `FsContext` and `SectionObjectPointer` on the application's `FILE_OBJECT`,
and initializes a cache map. The private NTFS stage is a separate backing
object. That split is an intentional existing design, but the official Windows
contracts do not say that a minifilter may become the stream filesystem owner:

- Microsoft documents `FILE_OBJECT.SectionObjectPointer` as “set only by file
  systems.”
- Microsoft documents that `SECTION_OBJECT_POINTERS` is allocated by a file
  system or redirector, one per file stream, and that file-system filter
  drivers treat its members as opaque because the underlying file system owns
  their synchronization.
- Microsoft documents `CcInitializeCacheMap` as a routine filesystems call to
  cache a file.

Therefore the private backing file, custom FCB header, successful prototype
traces, and explicit section-acquire/write/flush hooks do not by themselves
establish that the current minifilter owns the mapped stream under the DDI
contract. There is an important nuance: Microsoft's system-defined ECP
guidance recognizes a filter that implements a *layered filesystem* by owning
file objects and issuing its own lower `IRP_MJ_CREATE` operations. That may
describe a legitimate design category for this code, but the exception is about
ECP propagation; it does not say that a minifilter may allocate/set a private
SOP or use Cache Manager APIs as an FSD. The SOP and cache-map ownership
contracts still need an authoritative basis for this exact stack. Until a
source-level DDI review establishes that basis, classify the current custom
upper-SOP approach as unproven, not as qualified ownership. Do not implement
owner-only M1/M2 by extending it without that review. Preserve the frozen plan
and its historical qualification record; treat its “existing owned-stream
architecture is the integration point” section as conditional pending either
a documented layered-filesystem contract for the exact implementation or a
reviewed filesystem-owner route.

## Candidate paths assessed

### 1. Reparse to an ordinary private NTFS file

A minifilter can use the documented name-reparse pattern illustrated by
Microsoft's SimRep sample. The redirected create is then completed by NTFS,
which correctly owns the resulting FCB and SOP. This removes the custom-upper-
SOP problem. It does not solve the access-control problem: the reissued create
targets the private file under the original caller's security context, so a
service-only DACL denies the application. Granting the application access to
that target makes direct stage-path access possible after filter/service
failure. A same-volume target can preserve volume serial, but does not change
the DACL result. ECPs carry create context; the documented system-defined ECP
contract says filters should treat them as read-only and not spoof them. It
does not supply an access-check bypass. No use of `RequestorMode`, fabricated
`AccessState`, or undocumented ECP is acceptable. This route is not currently
shown to preserve private backing and direct-path isolation simultaneously.

### 2. Filesystem owner / redirector (recommended supported ownership route)

Use an actual filesystem/redirector to own the logical stream and its SOP. The
smallest viable prototype is a WinFsp-based logical filesystem companion (or a
dedicated native FSD if an exact Windows surface cannot be met by WinFsp):

1. Before any application writable open, boot the filesystem owner and mount
   the protected logical namespace. Keep owner allocation/journaling available
   while delaying policy inspection, approval, and publication. Missing mount,
   owner service, scope, or durable journal means scoped mutation is refused
   and readiness remains false.
2. Route a logical open through the same immutable owner-scope, admission, and
   generation decision as `StageAdmit`; service the create from the filesystem
   owner rather than completing a create in the minifilter. The filesystem
   owner allocates the private stage in a real NTFS store with a service-only
   DACL, opens that backing under its service identity, and checks the
   caller's logical destination security before forwarding the operation.
   The filesystem owner, not a minifilter, associates all opens of a logical
   stream with its one SOP and owns the Cache Manager contract.
3. Keep the original destination bytes as the approved public generation.
   Give only the writer process/generation a private logical view. Independent
   buffered and uncached processes open the public logical generation. A raw
   observer that reads the underlying original NTFS volume must continue to
   see the exact pre-write bytes and extent allocation while a mapping is
   dirty. The stage is never reachable by ordinary path opens; after owner or
   filter failure its backing DACL remains service-only and its manifest stays
   private/owner-pending.
4. Carry exact target object identity and destination generation from the
   admitted logical open through source seeding, all follow-up generations,
   rename/link/delete transactions, seal, promotion, and publication. Existing
   targets bind to the full volume identity and file ID; new names bind to the
   parent identity and serialized name slot. Hold/revalidate the same object
   across every path-to-object boundary; a path lookup followed by a second
   path open is not sufficient. Identity drift refuses, leaves the private
   generation retained, and never opens the public target writable.
5. Keep policy inspection/publication separate from ownership. Early
   generations use a journaled `OwnerPendingPolicy` state and cannot enter the
   existing `Sealed` publication loop. Policy activation promotes only an
   exact owner epoch, scope digest, target identity, and generation match.
6. Keep current `StageStream` code only where it remains valid as a backing
   adapter or test oracle. Its private NTFS I/O and journal shape may inform
   the new owner, but no application `FILE_OBJECT` may receive a hand-built SOP
   from the minifilter. The policy hooks must gate the logical filesystem path
   and every bypass path; the original-volume admission fence still handles
   raw/uncached writes and volume lifecycle, with existing taint and unsupported
   modes unchanged.

WinFsp documents memory-mapped I/O, read/write, access control, named streams,
rename/delete, disk and network filesystem support. It also documents gaps that
   are directly relevant to SafeUpload's current identity and compatibility
   gates: no hard links, short names, `FILE_OPEN_BY_FILE_ID`, volume reads or
writes, sparse/compressed/encrypted FSCTL semantics, or NTFS change journal;
some NTFS cleanup, stream-rename, case-sensitive lookup, and reparse behavior
differs. Thus WinFsp is a supported candidate owner, not an already compatible
drop-in replacement. Its mount supplies a logical filesystem identity; the
current requirement to report the original destination volume/file identity
must be proven by an explicit identity mapping and native query tests, not
assumed. The same applies to `FSCTL_GET_RETRIEVAL_POINTERS`, file IDs, raw
observers, rename, `OpenFileById`, and sync-client opens.

## Identity, observer, and destination gates remain acceptance criteria

Do not silently reclassify any of these as nonrequirements to make a virtual
filesystem pass. The route must prove, or remain NotReady for, each existing
gate:

- Original normalized path, volume serial, full file ID, parent ID, rename and
  replacement generation remain stable as observed by supported applications.
- The same file is addressable through supported name aliases and native
  identity APIs; `OpenFileById` and hard-link operations are either supported
  with identical owner semantics or remain explicit fail-closed unsupported
  operations under the MVP's already documented capability policy.
- Buffered, uncached, and independent-process readers continue seeing the
  public approved bytes while the writer sees its private mapped generation.
  A raw physical-volume observer sees unchanged original bytes and extents.
- Existing delete/rename/replacement/tombstone ordering, held-version
  immutability, no direct private-stage access, service restart, driver restart,
  flush durability, owner draining, and crash recovery all remain mandatory.
- The route handles every currently supported destination adapter (local
  NTFS, USB/removable, UNC/network, and real sync folders), including all
  namespace aliases and sync-client access paths. Each adapter must prove its
  lower identity, access-check, stable-handle, raw-observer, restart, and
  publication semantics. A local NTFS M1/M2 pass cannot enable the other
  destinations or clear taint.

## Decision and next implementation boundary

The current evidence supports **filesystem ownership** as the only candidate
that both obeys the documented SOP ownership boundary and can keep backing
storage private while serving a logical per-writer stream. WinFsp is the
smallest practical proof route because it already provides a filesystem owner
with mapped-file support and can run as a service; a custom native FSD is the
fallback only if the existing original-identity/query contract cannot be
implemented through WinFsp. The original-NTFS reparse route is not approved
without a documented access-check design that preserves service-only ACLs and
direct-path denial.

Before product edits, Bridge review must choose the owner implementation and
verify a tiny architectural proof against existing exact M1/M2 identity and
observer predicates, including whether a filesystem mounted at the protected
logical path can preserve the required original volume identity and native
extent observation. If it cannot, record a concrete incompatibility rather
than weakening predicates. Then implement the whole vertical slice: owner
scope/load/readiness, pre-open owner start, allocator/journal role, logical
filesystem stream generations and mappings, policy gating, owner-pending
promotion, bypass fencing, independently spawned observers, and adapter
qualification. Do not leave a prototype that only allocates a private file or
denies opens and call it M1/M2 protection.
