WinFsp 2.2B4 builder-only administrative-image extraction (v2)
Status: authored for independent review; not executed or PowerShell-parsed.

Purpose and boundary

This package obtains the WinFsp development headers and x64 import library
from the already reviewed official MSI on the isolated trusted V10 builder.
It uses Windows Installer administrative-image mode (`msiexec /a`) into one
fresh GUID-named quarantine directory. The MSI is a complete administrative
image containing drivers, DLLs, EXEs, scripts, sample sources, headers, and
libraries. No extracted executable, DLL, script, or driver is invoked. The
package does not install WinFsp, start a service, load a driver, change trust,
touch the signing key, build product code, or claim runtime or privacy
qualification. The resulting SDK root is emitted explicitly for a later
feature-only native host build.

Path and file identity controls

The caller supplies only a fresh lowercase 32-hex GUID. The script fixes the
source and parent paths, rejects a wrong builder UUID/name/SID or a
non-elevated token, and constructs the target under
`C:\Users\vika\Documents\SafeUploadWinFspSdk-20261006-<guid>` with an
adjacent retained `.msi.log`. It opens every component from `C:\` through the
source directory and output parent with no-follow directory handles; those
handles reject reparse points and omit `FILE_SHARE_DELETE`, preventing
ancestor rename/removal during the operation. The MSI is opened before its
hash, signature, and table checks with read access and read-only sharing; its
held handle denies write/delete opens through `msiexec` and the post-check.
The script captures volume serial/file ID identities and reopens all pinned
paths to compare identities before reporting success.

The target is created exclusively with `CreateDirectoryW`, then held through
a no-follow directory handle. The log is created exclusively with a temporary
read/write handle, then reopened as read-only with read/write sharing and no
delete sharing; the two handles' volume/file IDs must match before the
creator handle closes. Windows Installer can then write its log while the
path remains pinned. Target and log are never deleted on error. After process
exit the log byte count and SHA-256 are captured, and an empty log fails the
result. A nonzero MSI exit, changed source
digest/signature/identity, installed WinFsp package/driver/service, or
unexpected build actors makes the result fail and retains all output.

Every target directory is enumerated without following entries. The script
opens each entry with `FILE_FLAG_OPEN_REPARSE_POINT`, rejects reparse points
for files and directories, records volume/file ID and all directory names,
hashes every file through a held read-only handle, and repeats the directory
name snapshots before returning. It derives exactly one `WinFspSdkRoot` only
when the same root contains `inc\winfsp\winfsp.h` and
`lib\winfsp-x64.lib`. The JSON result includes the full file/directory
inventory, before/after installation checks, process exit, source and log
hashes, and SDK root. The inventory contains paths and hashes, not file
contents.

Execution gates and caller flow

This package is not ready for execution until the trusted V10 host checkpoint
has been independently reviewed, created as a fresh child over healthy
retry2, host-verified, and the guest has passed the required pinned V13
read-only baseline on that child. The exact v2 source must then pass the
Windows PowerShell 5.1 parser with zero errors and be independently reviewed
before the root operator runs it in an elevated PowerShell 5.1 session on
that builder. The operator generates a fresh GUID and supplies only
`-RunGuid <guidN>`. The package does not perform those prerequisite VM/host
phases.

After extraction, root reviews the retained JSON result and complete public
inventory, verifies no installation/service/driver or unrelated state change,
and passes the exact emitted SDK root explicitly to a feature-only native
host build. Any build remains a separate operation. Runtime installation on
the debuggee, service/driver start, changes to boot/security settings, or a
privacy claim requires separate authorization and evidence.
