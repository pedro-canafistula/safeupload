## V6 ACL and key-use guard

The V6 creator pins the exact builder (`DESKTOP-O1LP5DG`, UUID `C6440689-D11C-4C63-A463-F3722B7DDB69`, vika SID `S-1-5-21-316478115-1595729549-2803163825-1001`) and requires `WindowsPrincipal.IsInRole(Administrator)` in the signing process. It creates only a 3072-bit RSA code-signing certificate in `LocalMachine\My` using Microsoft Software KSP, `KeyExportPolicy=NonExportable`, digital-signature key usage, exactly one code-signing EKU, CA=false, and 90-day validity. It retains the original user certificate and checks the original PFX/CER hashes before minting.

The key ACL guard requires a protected, canonical DACL with exactly two explicit, non-inheritable Allow ACEs: SYSTEM (`S-1-5-18`) and BUILTIN\Administrators (`S-1-5-32-544`). It accepts the provider's FullControl file mask or its raw GENERIC_ALL spelling, records the spelling without normalizing it, and requires the same full SDDL, owner, group, protection state, canonicality, and ordered ACE rows before and after the challenge. It does not grant vika an ACE or call `Set-Acl`. The permission claim is limited to the elevated vika process whose token has enabled Administrators membership; a different user, non-elevated process, extra ACE, unexpected owner/group or descriptor, or ACL drift fails closed.

Before public CER export, the creator performs a fresh random in-memory sign/verify challenge and checks the six complete certificate-store thumbprint inventories. Only `LocalMachine\My` may gain the new thumb. It rechecks ACL parity after the challenge and public export, then writes public metadata to the V6-only evidence path. The metadata records the full before/after ACL snapshots, effective Administrators membership, provider/key attributes, six-store inventories, CER thumbprint/hash, and whether any trust or export action occurred. On post-mint failure it captures the original exception and best-effort current ACL plus the original pre-mint ACL snapshot, inventories, matching certificate metadata, and whether a public CER exists. Preserve the failed branch and do not trust or use a failed key.

After a restricted key-bearing system-disk checkpoint is created, host-verified, cold-booted, and independently inventoried, the V6 cold-challenge script repeats the exact builder identity and Administrator-token checks. It pins the creation-metadata hash and public CER hash/thumbprint, verifies that the original certificate and PFX/CER hashes remain intact, requires all six store inventories to equal the mint metadata, validates the exact same machine CNG container and nonexportable 3072-bit key, and compares the current SDDL and ordered ACL rows against both mint snapshots. It signs/verifies a second fresh challenge in memory, then repeats the ACL and store checks. It emits neither the challenge nor signature bytes and performs no trust, source build, or artifact signing. If this cold-challenge gate fails, stop before trust or source mutation and retain the branch evidence.

The checkpoint claim remains limited to the builder system disk and signer state. It is not a full VM, firmware, TPM, or RAM backup. The existing NVRAM is reused, `testsigning` remains unchanged, and no firmware configuration is changed. The parent image must remain byte-pinned/read-only and the child must retain exact ownership/mode and QMP backing-chain evidence, as covered by the separately reviewed checkpoint procedure. A successful cold challenge does not close the wider VM qualification/restoration gate.
