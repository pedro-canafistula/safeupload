Observed failure
----------------
The c01d Control 24 receipt showed one Ready policy scope and one ready
instance, but 20 registry entries outside that scope were Unknown with
SAFEUPLOAD_REGISTRY_UNKNOWN_IDENTITY (0x4). They had no H/S/C/T/W activity or
opener PIDs. AdmissionCoverage.cs treated any WriterEntriesUnknown count as
Degraded, preventing Ready. The entries were mostly pagefile.sys and locked,
transient or system-maintained files. The captured activating-status page did
not include the status returned by the alias classifier, so the exact failure
site was not visible.

Receipt compatibility
---------------------
Control 19 is consumed by the Agent evidence-capture parser. Before this
change Inspector --activating-status also used it. The Agent parser pins the
v18 layout to 36,136 bytes, 1,128 bytes per entry, and a zero ReservedFlags
field. The Control 19 page and entry remain byte-for-byte the same. Control 25
is a separate diagnostic-only page used by Inspector --activating-status; it
appends the classifier NTSTATUS and step to the legacy entry. Readiness still
uses the separate Control 24 coverage receipt. No Agent wire version or
Control 24 readiness contract changes.

Fixes and safety arguments
--------------------------
1. Deleted or unlinked identities resolve Outside only with positive evidence:
   - An attempted FILE_OPEN_BY_FILE_ID on the registry entry's exact mounted
     volume returns STATUS_FILE_DELETED, STATUS_OBJECT_NAME_NOT_FOUND,
     STATUS_OBJECT_PATH_NOT_FOUND or STATUS_NO_SUCH_FILE. The entry must have
     a nonzero recorded volume serial and still reference that same PFLT_VOLUME.
   - A compact ADS resolver verifies the full FILE_ID_INFORMATION and serial,
     completely parses FileStreamInformation, and finds that the recorded
     suffix is absent.
   - FileHardLinkInformation returns STATUS_SUCCESS with exactly the complete
     header and BytesNeeded equal to that header. A zero count in a short,
     truncated or otherwise inconsistent response remains Unknown.

   A deleted stream cannot regain its old namespace identity. If an MFT ID is
   later reused or an ADS with the same suffix is recreated, it is a new stream
   incarnation; the stored SectionObjectPointer check rejects rebinding it to
   the old registry entry. The create/rename/link path applies the current and
   pending destination policy. In particular, a tracked handle no longer
   authorizes a new hard link or rename into a protected destination, and an
   unresolved destination on a volume that can hold scope fails closed. Writes
   through an already-open handle to an unnamed outside stream may continue,
   but the stream has no path into a protected destination.

   STATUS_DELETE_PENDING alone is deliberately not treated as proof of no
   names: a file marked for deletion may retain links and existing handles.
   It stays Unknown on the identity-classification path. The same status no
   longer proves registry or unknown-SOP quiescence. Microsoft documents that
   a marked file is deleted only after handles close and its link count is
   zero: https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_file_disposition_information

2. Paging files are classified after activation reopens the recorded identity.
   The only prior paging exclusion checked FsRtlIsPagingFile during create
   callbacks. That API documents a post-create false result in some timing
   conditions; its documentation also says it works properly on Vista and
   later, so c01d alone does not identify which create callback returned false
   or whether the file was marked only later. The reopened-stream check closes
   that timing gap without claiming which phase caused this entry. The reopened
   stream is fully link-enumerated; it resolves Outside (and is labeled
   PagingFile in Control 25) only when every current and pending destination
   alias is outside. A paging-file alias in scope or any incomplete
   classification remains gated/Unknown. The ordinary create skip remains in
   place when FsRtlIsPagingFile is already true. The old pagingCreatesSkipped
   counter was never incremented in this source, so c01d's zero value cannot
   establish whether the skip ran; the increment is now attached to an actual
   pre/post-create exclusion. Reference:
   https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-fsrtlispagingfile

3. Identity and parent opens use OBJ_KERNEL_HANDLE, FILE_READ_ATTRIBUTES |
   SYNCHRONIZE, full read/write/delete sharing, FILE_OPEN_BY_FILE_ID relative
   to the volume, FILE_OPEN_REPARSE_POINT, and IO_IGNORE_SHARE_ACCESS_CHECK.
   The hard-link query uses that minimum attribute-only access. These flags
   avoid I/O Manager share conflicts and reparse traversal; they do not bypass
   file-system access checks. Any remaining open, query, parent, name-build,
   malformed-buffer, allocation, or stability failure records its exact
   NTSTATUS and step and remains Unknown. Reference:
   https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltcreatefileex2

Still Unknown
-------------
- STATUS_DELETE_PENDING without independent evidence that the recorded
  stream has no name.
- Access denied or other failed ID/link/parent/name queries; mismatched file
  identity or SectionObjectPointer; truncated, oversized or malformed link
  lists; and scans that race a rename or policy-generation change.
- Any file with an alias in the current or pending scope until its normal
  activation gates resolve, plus unrelated registry, trust, capacity or
  instance-wide Unknown reasons.
- A successful empty FileHardLinkInformation response is accepted only when
  returned and BytesNeeded are exactly the header size and the 4 KiB-or-larger
  NTFS query buffer could hold any single NTFS link record. MS-FSCC says a
  successful query normally returns at least one name and that zero entries
  indicate insufficient room, so this header-only NTFS behavior must be
  confirmed in the orchestrator's Windows 10 NTFS run. Any response that does
  not match the exact header-only form remains Unknown.
