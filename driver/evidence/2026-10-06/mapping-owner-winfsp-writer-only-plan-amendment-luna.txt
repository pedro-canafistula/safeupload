# Writer-only WinFsp owner proof plan amendment

Date: 2026-10-06. This amendment supersedes only the policy-boundary wording
in the frozen `mapping-owner-winfsp-writer-only-proof-plan-luna.txt`. It does
not change that plan's scope, original mapping assertions, supported-destination
matrix, taint requirement, or deployment restrictions.

## One stable generation across policy expansion

An admitted owner epoch owns one stable private generation and one WinFsp file
node/section-object-pointer for the lifetime of that writer's mappings. A later
policy expansion does not switch that file object to a successor backing and
does not rebind its SOP, section, cache, internal path, or owner grant. All
bytes from the first writable open, including writes through a section retained
across M2 policy activation, stay in the same service-private generation.
Readers on the original NTFS path continue to see the last approved public
generation.

Policy activation and data-plane readiness are separate. The allocation owner
must be active before candidate writable opens; it may retain private bytes
while policy, inspection, and publication are unavailable. The generation is
not `Sealed`, inspectable, or publishable merely because the app handle cleaned
up or the final handle closed. Once all FSP file-object references, Cc/FSP
sections, outstanding file operations, and backing writes have rundown and the
backing has been flushed, the filesystem adapter may record one immutable
quiescence receipt. Promotion to `Sealed` then requires a separately accepted
policy receipt that matches the exact destination volume/parent/file identity,
component, owner epoch, immutable candidate-scope fingerprint, and current
non-audit policy version/fingerprint. If no currently accepted policy covers
that exact destination, keep the same generation private and retained; do not
publish it and do not create a policy-driven SOP switch. Recovery treats an
interrupted generation as private/unsealed until the same identity and policy
conditions are proved again.

The existing source-level allocator/journal proof must therefore model two
durable transitions: `OwnerPendingPolicy -> OwnerPendingPolicy` with verified
quiescence evidence, then `OwnerPendingPolicy -> Sealed` only with matching
policy acceptance. An ordinary `StageSeal` receipt remains insufficient.

## Executable handoff gates

The route is still only a source/dependency proof until an actual pinned Windows
run passes each gate. The required first runtime proof is the genuine kernel
create-ECP handoff through the SafeUpload minifilter's reparse path to a
minifilter instance on the WinFsp volume. It must demonstrate that the
driver-defined, one-use ECP is non-user-originated at the receiving instance,
maps to a referenced process object/lifetime, exact source volume and 128-bit
file or parent/name-slot identity, disposition and owner epoch, and is consumed
once. The FSP callback must receive only the registered generation route after
that kernel decision. A direct FSP pathname open, forged user ECP, stale or
replayed grant, wrong process/object/epoch, and missing service/mount all fail
closed. PID, path secrecy, WinFsp `GrantedAccess`, and a user-mode capability
string alone are not authority.

The proof must preserve and correctly propagate the original ECP list. It must
not fabricate system ECPs, access state, tokens, requestor mode, or file objects.
ECP visibility and lifetime across the actual reparse/FSP boundary remain an
open measured gate, not an assumed property. A miss means do not grant a
grantless/PID-only fallback and do not execute the owner route.

The same proof must use the real SafeUpload allocator and journal, then issue a
real FSP create/write/flush/close through the driver. It must show a durable
`OwnerPendingPolicy` manifest before policy activation, no inspection/public
publication before matching policy, and the unchanged NTFS destination/raw
extents for independent buffered, uncached, and raw observers. The final-close
receipt is valid only after FSP and Cc cache flushing, all relevant request and
section rundown, backing flush, and no future writes being admitted to that
owner node. A callback or `Cleanup` event alone cannot stand in for this proof.

## Immutable bounds

The source-only proof remains feature-gated and compiled out in normal builds.
It must keep current taint behavior and unsupported gates unchanged. No
WinFsp MSI execution, install, driver/service activation, signing/trust update,
or VM test is authorized by this amendment; those require a separate
checkpoint-bound reviewed action. USB, UNC/SMB, and sync-client rows remain
unqualified until their own destination adapters and adversarial acceptance
tests pass.
