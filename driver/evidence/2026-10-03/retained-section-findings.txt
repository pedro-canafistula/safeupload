Retained writable sections: what a filter can and cannot see (experiment record)
Date: 2026-10-03
Environment: isolated debuggee WIN10-DEBUGGED, Windows 10 Pro 22H2 build 19045.2965 (ntoskrnl 10.0.19041.2965,
fltmgr/ntfs 10.0.19041.1, queried 2026-10-03), local fixed NTFS, one volume, plain 4 KiB fixtures outside every protected scope, no agent, no policy.
Driver: feature build, test-signed. Diagnostic code is observe-only (no status is ever changed).

Why this was run
----------------
The adversarial review of writer-ledger design v1 (writer-ledger-design-v1-luna-review.txt) ruled it UNSOUND on
one point: a writable section can outlive its file handle and create new views later, with no documented way
for a filter to know the writer is gone. It asked for the cheapest kill test first. These runs are that test
plus the follow-up questions it raised.

Observations
------------
O1  Creating a writable section is filter-visible: 4 of 4 post-attach retained sections produced
    IRP_MJ_ACQUIRE_FOR_SECTION_SYNCHRONIZATION SyncTypeCreateSection with PAGE_READWRITE (0x4); the positive
    control (4 fresh sections inside the view window) was seen 4 of 4. In that window exactly 4 writable
    CreateSection events existed system-wide, all controls.
O2  Creating a view from a retained section (MapViewOfFile on a retained mapping handle, file handle already
    closed, no previous view) produced NO section event: 0 of 8 (4 pre-attach, 4 post-attach). The write then
    reached storage and was seen by a buffered reader, an uncached write-through reader and a fresh buffered
    reader in 12 of 12 fixtures, and a paging write carrying the stream's section pointer was recorded for each.
O3  MmDoesFileHaveUserWritableReferences (via the explicit probe, attribute-only open below the instance):
      YES  for all 8 retained writable sections BEFORE any view existed (pre-attach and post-attach);
      NO   for 4 streams with no section;
      YES  with a live view and open section; YES with the section handle closed but a view still mapped;
      YES  for a section whose only remaining handle lives in another process (duplicated; creator closed);
      NO   for a copy-on-write section with a live view; NO for a read-only section with a live view.
O4  End of life: after the last writable section handle / view was released the probe read NO at the first
    probe (244-523 ms later, bounded by probe latency, not by a lag), and again at +5.5 s and +17 s. Same for
    plain, cached (buffered I/O before mapping) and view-held-after-handle-close streams, and for the stream
    whose handle was in another process once that process was killed (NO at +250 ms and +5.5 s).
O5  The writer's own file object does not anchor the section: IRP_MJ_CLEANUP and IRP_MJ_CLOSE of the
    user's write file object arrive immediately at handle close (same millisecond) while the section is still
    held. For a cached stream the CLOSE is delayed 1-4 s until the lazy writer's flush. A SyncTypeOther acquire
    on a different (internal) file object of the same stream follows every CreateSection; no cleanup/close of
    any file object of the stream was recorded in the 55 s after the section handle closed.
O6  Section events are ~1000/s system-wide and a trace taken after an Inspector launch holds ~5800 entries;
    contention drops were 0-2 per dump and never affected a probe entry (probes wait for the ring).

Interpretation
--------------
I1  The review's decisive premise ("no way to know the writer is gone; MmDoes reads zero while a retained
    handle can still create a view") does not hold on this build: the section object itself is counted.
    Writer-free for sections is a STATE the OS maintains and that can be queried, not a history a filter
    must reconstruct from events.
I2  View creation remains invisible to a filter. A design must therefore never depend on seeing it.
I3  File-object CLOSE is useless as a section-lifetime signal (O5); the repair idea based on it is dead.
I4  A copy-on-write section does not read as writable (O3), so it cannot stall a file forever.

Not claimed
-----------
One OS build, local NTFS, 4 KiB fixtures, one process tree; not tested: other Windows builds, ReFS, network and
removable volumes, sections created through file-ID or reparse opens, image sections, large pages, DAX, TxF,
EFS, a section handle held by a service across logon sessions, hibernation/fast startup, mass section counts.
MmDoesFileHaveUserWritableReferences is documented, but its behavior for a section without a view is
observed, not documented: it must be re-qualified per OS build and guarded by a start-up self-test.
The experiment shows a predicate; it does not show a complete admission design (identity/aliases, write
handles, in-flight CreateSection, policy rundown, boot-start hazards, SMB are separate premises).
