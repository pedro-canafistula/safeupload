# Verdict: **UNSOUND**

The single most important reason is that the filter has no documented way to prove that an old writable section can no longer create a view. A file handle can close while a mapping view remains, and modified pages can be written lazily. If the ledger treats “no current writable references” as “no old writer,” a retained mapping handle may write after the file becomes Protected. If it keeps every file with a past writable section Activating forever, the design fails to make progress for those files. The design itself identifies this as an unverified premise, but has no safe completion rule. See the proposed activation rule in [writer-ledger-design-v1.txt](/home/victor/Work/safeupload-staging/driver/evidence/2026-10-03/writer-ledger-design-v1.txt:52) and the earlier lifetime analysis in [STAGED-WRITES.md](/home/victor/Work/safeupload-staging/driver/STAGED-WRITES.md:221).

**Documented:** `MapViewOfFile` maps a view from a file-mapping-object handle; closing file and mapping handles succeeds even when views remain, and dirty pages may be written lazily. The FSFilter callback reports section synchronization, including `SyncTypeCreateSection`. **Inference:** mapping another view from an already-created section object does not invoke a new section-creation callback. Microsoft does not document a per-view callback or a path-scoped way for a minifilter to revoke that mapping handle. That inference is a direct target for premise P3’s experiment, but the design cannot claim a documented rundown guarantee in the meantime. ([MapViewOfFile](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-mapviewoffile), [Closing a File Mapping Object](https://learn.microsoft.com/en-us/windows/win32/memory/closing-a-file-mapping-object), [section-sync parameters](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/flt-parameters-for-irp-mj-acquire-for-section-synchronization))

The review is read-only. The writer-ledger design is a proposal, not implemented or verified; code references below are to the current prototype and its feasibility limits. No builds or VM experiments were run. ([design status](/home/victor/Work/safeupload-staging/driver/evidence/2026-10-03/writer-ledger-design-v1.txt:3))

## B. Ranked defects

### P0 — Section lifetime defeats the Activating-to-Protected transition

**Confirmed documented limitation; the exact remap callback behavior is an inference to test.**

Interleaving: a process opens a file with write access, calls `CreateFileMappingW(PAGE_READWRITE)`, keeps or duplicates the mapping-object handle, unmaps any current view, and closes the file handle. The policy then adds the file’s path. If the ledger sees zero writable references and flushes, it marks the file Protected. The process calls `MapViewOfFile(FILE_MAP_WRITE)` on its retained mapping handle and writes through the returned pointer. Those writes need not enter at the pointer store and can reach disk later.

`MmDoesFileHaveUserWritableReferences` is documented as a check for a file associated with a transaction, including detection of writable views after file and section handles close. It is **not documented as a general section-handle lifetime API** or as a guarantee that a zero result rules out a future view. A sticky “section was created” bit avoids premature transition only by potentially leaving a file Activating forever. ([MmDoesFileHaveUserWritableReferences](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-mmdoesfilehaveuserwritablereferences), [MapViewOfFile](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-mapviewoffile))

**Fix:** No supported per-file minifilter fix is specified. A deployment-wide admission owner could prevent writable sections from existing before protection, but that is not the universal path-scoped design. Otherwise, the file must remain unavailable until a proven clean boundary, potentially reboot; a timeout or flush alone cannot safely make it Protected.

### P0 — Raw-disk writes cannot be made path-scoped by this minifilter

The proposal refuses writable opens of a volume containing protected scopes, but a writable `\\.\PhysicalDriveN` handle issues direct disk access outside the file-system volume stack. It has no pathname or per-stream identity for the ledger to check. Microsoft documents direct access handles to physical disks and volumes; that access is restricted and requires administrative privileges. **Inference:** physical-disk requests do not traverse this file-system minifilter’s volume instance.

Denying `\\.\X:` volume writes alone therefore does not cover this path. Blocking raw writes that could hit protected extents requires a lower storage/device boundary or denying raw writes to the containing device, which blocks unrelated raw I/O and conflicts with the owner’s scope rule. The current code also explicitly allows the empty-name volume-open form through its create callback: [Filter.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Filter.c:1379). ([CreateFile physical-disk and volume access](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea))

### P1 — TxF can commit after the ledger sees the writer handle close

**Confirmed interleaving, if TxF is supported by the qualified local NTFS stack.**

A process calls `CreateTransaction`, opens a target using `CreateFileTransactedW` with write access, calls `WriteFile`, closes the file handle, then calls `CommitTransaction`. Microsoft’s `CreateFileTransactedW` guidance says to close the file handle before committing or rolling back; TxF holds changes transactionally until commit. A ledger that decrements its writer count on file-object cleanup can see zero and protect the file before the transaction publishes its changes. `FLT_RELATED_OBJECTS` exposes the associated transaction, but v1 specifies no transaction context, enlistment, or commit rundown. ([CreateFileTransactedW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createfiletransactedw), [TxF overview](https://learn.microsoft.com/en-us/windows/win32/fileio/transactional-ntfs-portal), [FLT_RELATED_OBJECTS](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/ns-fltkernel-_flt_related_objects))

**Fix:** Track the transaction lifetime through commit/rollback and prevent publication while an old transaction can still commit, or fail closed on transacted mutations in protected scope. TxF is deprecated and Microsoft recommends alternatives, but it is still documented as available; that does not establish universal transaction support or eliminate the need to qualify it.

### P1 — “Current or pending” policy matching is not a mutation barrier

The design requires both policy-snapshot matching and rundown through operation completion. A lock around matching protects the snapshot, but not the lower-file-system operation after the callback returns. Interleaving: a create, rename, or section acquisition reads the old policy and is admitted; the candidate is published and its scan completes; the admitted operation reaches the file system afterward. The candidate is now current while an operation admitted under the old state can still create a writer or change namespace.

The current prototype illustrates the difference: policy publication uses a lock and transition mutex in [Policy.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Policy.c:403), while some current-or-pending checks occur in selected paths such as [StageStream.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:2401). Other admission paths use current-policy checks, and the source review records no common operation rundown ([round-three review](/home/victor/Work/safeupload-staging/driver/evidence/2026-10-03/late-attach-security-review-round3.txt:53)). This is a **confirmed gap in the current prototype** and an **underspecified requirement in v1**, which says rundown is required but gives no linearization or reference-lifetime algorithm.

**Fix:** Define one admission epoch acquired atomically with policy selection and held through lower completion for every mutating path: create, write, rename/link, FSCTL, delete/set-information, and section creation. The section-sync operation cannot be pended as a normal admission wait: `FLT_PREOP_PENDING` is for IRP-based I/O, while this is an FSFilter callback. Any policy refusal must complete immediately and accurately. ([pre-operation callback contract](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nc-fltkernel-pflt_pre_operation_callback), [callback-contract correction](/home/victor/Work/safeupload-staging/driver/evidence/2026-10-03/admission-gate-contract-correction.txt:5))

### P1 — Stream identity is not scope membership

A stream context or `SECTION_OBJECT_POINTERS` can identify a stream, but it does not answer whether **any name** for that stream is in a protected namespace. A process can open a file through an outside hard-link name while another hard link is under a protected prefix. Directory renames can move many open streams into or out of scope; reparse points and mount points can redirect a path to another object or volume. A file-ID open carries a file ID or object ID rather than a normal path. Short-name tunneling can change the final name after create, link, or rename.

Microsoft documents one `SECTION_OBJECT_POINTERS` structure per stream across file objects; it also documents hard links as multiple paths to one file and alternate data streams as separate streams. These facts help define identity, but do not supply the design’s missing path-to-stream alias index or atomic namespace-update algorithm. Normalized names also need post-operation tunneling handling in applicable creates, links, and renames. ([SECTION_OBJECT_POINTERS](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ns-wdm-_section_object_pointers), [hard links and junctions](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions), [reparse-point operations](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points-and-file-operations), [file-name tunneling](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltgettunneledname), [FILE_OPEN_BY_FILE_ID](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntcreatefile))

**Fix:** Define a stable identity such as volume plus file ID plus stream identity, and maintain a complete alias set with serialized rename/link/reparse updates—or refuse namespace operations whose identity or destination cannot be established. A reverse index of stream contexts is not specified in v1, and a context lookup from a file object is not itself a way to enumerate every existing context.

### P1 — The Untrusted late-attach fallback cannot stop extant views within the stated scope

Marking a volume Untrusted and denying new opens, new writable sections, and writes through visible handles does not revoke a view created before attachment. If its dirty pages arrive after attach, the paging path needs a known stream identity to deny only that stream. An incomplete inventory has no such identity. Denying unknown paging writes volume-wide violates the no-volume-wide-denial rule; allowing them does not fail closed for protected streams.

`InstanceSetup` is called on the first operation after mount, and Microsoft warns against synchronization or IPC in that callback. That supports a prompt mount-time attach path, not a late-attach recovery barrier. The prior assessment also found that post-attach scans leave a window for pre-existing views. ([InstanceSetup contract](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nc-fltkernel-pflt_instance_setup_callback), [scan-design assessment](/home/victor/Work/safeupload-staging/driver/evidence/2026-10-03/admission-gate-design-assessment.txt:73), [STAGED-WRITES.md](/home/victor/Work/safeupload-staging/driver/STAGED-WRITES.md:624))

**Fix:** Require an external admission gate before any handles or sections exist, or withdraw late-attach support. The `STATUS_FLT_DO_NOT_ATTACH` option leaves the volume unfiltered; it does not protect the scope.

### P1 — Boot start is an attempted load, not a fail-closed guarantee

A boot-start filter still needs its registry/service configuration, FltMgr dependency, correct group and altitude, initialized state, and successful `FltStartFiltering`. The current INF is demand-start with `ErrorControl=1` ([SafeUpload.inf](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/SafeUpload.inf:69)); that is deliberately not the proposed design. Microsoft documents that `SERVICE_ERROR_NORMAL` allows startup to proceed if the driver fails to load, and that filters in a load-order group do not thereby have a deterministic ordering among all drivers. `FltStartFiltering` may deliver I/O and volume notifications before it returns. ([INF AddService](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/inf-addservice-directive), [filter load order](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/what-determines-when-a-driver-is-loaded), [initiating filtering](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/initiating-filtering))

The agent is not available at early boot. V1 does not define a durable boot policy or protected-scope behavior before the agent reconnects. The current driver initializes policy before creating its port and the first client pushes policy; its ordinary pre-create path returns without inspection when no client is connected ([Filter.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Filter.c:242), [Filter.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Filter.c:1366)). A boot design must load a trustworthy policy before filtering or fail closed on protected scope without blocking unrelated paths. It must not wait on the agent in `InstanceSetup`.

**Resume:** Fast Startup saves the kernel session and device-driver state to the hibernation file; it is not equivalent to a fresh kernel initialization. A filter’s ledger and policy may therefore resume as live state rather than be rebuilt by `DriverEntry`. S3 and full hibernation need their own state-continuity checks. Treating every “boot” as a clean ledger start is an inference that needs testing. ([Fast Startup behavior](https://learn.microsoft.com/en-us/troubleshoot/windows-client/setup-upgrade-and-drivers/fast-startup-causes-system-hibernation-shutdown-fail), [system power states](https://learn.microsoft.com/en-us/windows/win32/power/system-power-states))

### P1 — SMB and sync destinations do not share one local writer universe

MUP routes UNC requests to a provider, but Windows documents provider-dependent behavior: Vista-model redirectors send remote file I/O through MUP, while legacy redirectors can bypass MUP after provider resolution. A filter must qualify the actual redirector path and attach to every required stack. A local ledger cannot see another computer’s server-side handles or views. Windows permits remote file mappings and documents that writable views on different computers are not coherent. V1’s non-goal for other computers writing through SMB therefore conflicts with an all-writers claim for a destination class that the owner requires to stay included. ([MUP and UNC support](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/support-for-unc-naming-and-mup), [MUP redirector changes](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/mup-changes-in-microsoft-windows-vista), [MapViewOfFile remote behavior](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-mapviewoffile))

The current staged prototype explicitly rejects network volumes in its stage path ([StageStream.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:883)). That is a feasibility warning, not proof that the new ledger design inherits the same code path. Sync clients are also not a single OS-defined actor class: local file writes may pass through the local file system, while provider-specific synchronization and remote publication require separate qualification. A loopback SMB test cannot prove all redirectors, remote clients, or sync providers.

### P1 — Activating admits file-specific denial of service, with no safe timeout

A user can hold an existing writable handle or mapping indefinitely before a scope is added. Under the accepted rule, the filter cannot force that old writer to close; the file remains Activating and blocks new writers/mappings or publication. A timeout would violate safety. Duplicating or inheriting a file handle does not create a new file object—the handles refer to the same object—so a ledger can account for it by keeping one writer entry until final cleanup. But that does not tell the agent every process holding a duplicated handle. A mapping-object handle can also be duplicated independently. The design should report “activation held; holder identity incomplete” unless it adds a supported way to identify holders. ([Using Files in a Driver](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/using-files-in-a-driver), [DuplicateHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-duplicatehandle))

This is not a fixable availability issue under the owner’s definition. Keep the file Activating, report best-effort holder information, and accept per-file denial of service explicitly; do not broaden the denial to the volume.

### P2 — Additional writer and callback cases

These are not equally likely, but they must be qualified before claiming a complete ledger:

- **Failed creates:** count only a successfully completed create with granted write capability. Roll back pending reservations on failed, canceled, reparsed, or drained creates. A pre-create reservation is needed to close the policy-publication race.
- **Fast I/O versus IRP:** fast I/O writes do not create a new writer if the filter already counted the successful writable file object and retains it through cleanup. The ledger still needs complete create/cleanup handling and correct callbacks for other mutation paths. The current normal registration skips paging writes, while the feature registration is broader ([Filter.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Filter.c:131), [Filter.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Filter.c:157)).
- **FILE_OBJECT/FsContext reuse:** do not retain raw file-object or FsContext addresses as durable identities past their lifetime. Use referenced Filter Manager contexts and generation/lifetime rules. Stream contexts can be unsupported for a given file object; Microsoft explicitly documents that `FltSetStreamContext` can return `STATUS_NOT_SUPPORTED`, and `FltSupportsStreamContexts` documents unsupported cases such as paging files. Current code returns `STATUS_NOT_SUPPORTED` when the file system lacks stream-context support ([Context.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Context.c:356), [FltSetStreamContext](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltsetstreamcontext), [FltSupportsStreamContexts](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltsupportsstreamcontexts)).
- **Copy-on-write and image sections:** `FILE_MAP_COPY` creates private pages backed by the paging file; those writes are never written back to the original file. Counting these as file writers would cause avoidable Activating stalls. For `SEC_IMAGE`, `MapViewOfFile` says the requested view access is ignored. Separate those from genuinely shared writable data sections. ([MapViewOfFile](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-mapviewoffile))
- **EFS, compression, sparse/dedup, USN activity:** ordinary EFS file access is transparent NTFS file I/O, but EFS service/filter ordering and generated I/O still need an actual stack test. EFS and TxF do not support all combinations. USN records report changes; they are not a writer-admission barrier. These are plausible stack/metadata concerns, not confirmed bypasses in the proposed design. ([File Encryption](https://learn.microsoft.com/en-us/windows/win32/fileio/file-encryption))
- **VSS/shadow copies:** VSS freezes file-system writes while a snapshot is created and the in-box provider uses copy-on-write. This can preserve a point-in-time version of data already present; a per-file ledger does not control the provider’s volume-level snapshot storage. That is a residual exposure if historical versions are in scope, not evidence that VSS itself bypasses an otherwise complete live-file admission rule. ([VSS overview](https://learn.microsoft.com/en-us/windows-server/storage/file-server/volume-shadow-copy-service))
- **Section refusal status:** the earlier review’s categorical objection to `STATUS_ACCESS_DENIED` was withdrawn. The generic completion contract and accurate-error guidance make it plausible for a policy refusal, but the section-specific page names `STATUS_INSUFFICIENT_RESOURCES` for a memory failure and does not name policy denial. Keep this as a target-stack test, not a claimed confirmed defect; never fake memory exhaustion. ([contract correction](/home/victor/Work/safeupload-staging/driver/evidence/2026-10-03/admission-gate-contract-correction.txt:5), [section-sync parameters](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/flt-parameters-for-irp-mj-acquire-for-section-synchronization))

## C. Premises P1–P7 and experiments

These experiments are plans only; none were run. “Observe-only” here means instrument and observe a disposable test stack without enforcing policy denials.

1. **P1 — Boot attachment before first user writer.**  
   **Docs:** Partly. Boot-start drivers load before system-start and auto-start drivers; Filter Manager’s group/altitude ordering still does not prove the exact first file operation on this machine. `FltStartFiltering` can receive I/O before returning.  
   **Experiment:** instrument `DriverEntry`, `FltRegisterFilter`, `FltStartFiltering`, `InstanceSetup`, `IRP_MJ_CREATE`, and section-sync callbacks with timestamps, flags, path, access, PID, and stream identity; correlate with kernel file-I/O ETW on cold boot. Have a test process use `CreateFileW`, then `CreateFileMappingW` and `MapViewOfFile` on a fixture as soon as it starts.  
   **Falsifies P1 if:** any user-mode writable create or writable section occurs before ledger initialization/attachment, or any boot-time writer to a later protected fixture is invisible. Repeat for full hibernate, Fast Startup, and resume.

2. **P2 — Newly mounted volume reaches setup before first file open.**  
   **Docs:** Mostly answers the normal case: `InstanceSetup` is called on the first operation after a newly mounted volume, and `NEWLY_MOUNTED_VOLUME` identifies that reason. It does not establish the absence of pre-existing raw-device handles or detached-volume behavior.  
   **Experiment:** attach a disposable VHDX with `CreateVirtualDisk`/`AttachVirtualDisk`, mount it with `SetVolumeMountPointW`, then immediately use `CreateFileW` and `CreateFileMappingW`. Trace setup flags and first create/section callback. Repeat with USB-style removable media and a detached/remounted volume; keep a raw `CreateFileW` handle to the test device before mount.  
   **Falsifies P2 if:** a file create/section reaches the file system before successful setup, the expected flag is absent on a relevant stack, or a raw writer survives into the mounted scope without a policy.

3. **P3 — Section callback precedes every writable view.**  
   **Docs:** The callback contract covers creation of a section, not a guarantee for every `MapViewOfFile` call. `MapViewOfFile` accepts an existing mapping-object handle. The gap is an inference from those contracts and needs a target test.  
   **Experiment:** on NTFS, call `CreateFileW(GENERIC_READ|GENERIC_WRITE)`, `CreateFileMappingW(PAGE_READWRITE)`, then `MapViewOfFile(FILE_MAP_WRITE)`. Unmap the view, close the file handle, keep and duplicate the mapping-object handle with `DuplicateHandle`, then map and write a second view after an observe-only “policy published” event. Record section acquire/release callbacks, `MmDoesFileHaveUserWritableReferences`, paging writes, and an independent raw-byte observer.  
   **Falsifies P3 if:** the second view can be created and written without a corresponding pre-view callback, or a write reaches storage after the design would have marked the stream Protected. Also test large-page mappings, `SEC_IMAGE`, `PAGE_WRITECOPY`, and `FILE_MAP_COPY`.

4. **P4 — SMB/MUP coverage.**  
   **Docs:** Partly. MUP/provider behavior is documented, including redirector-model differences and remote mapping incoherence. It does not promise that one MUP attachment covers every redirector or another computer’s server-side writes.  
   **Experiment:** use a disposable SMB share and instrument the client filter plus server-side byte observer. Exercise `CreateFileW(L"\\\\server\\share\\file")`, a mapped drive created with `WNetAddConnection2W`, `CreateFileMappingW`/`MapViewOfFile`, `DuplicateHandle`, and a second client that opens/writes the same file. If qualifying a provider-specific path, also trace its redirector device path using `NtCreateFile`.  
   **Falsifies P4 if:** a relevant create, section, or write reaches the share without the expected local ledger event, or a second client can write while the ledger declares the file Protected. A loopback result cannot qualify other providers or clients.

5. **P5 — Ledger and `MmDoesFileHaveUserWritableReferences` agree.**  
   **Docs:** The DDI documents user-mapped sections for transactional file systems and detection of writable views after handles close. It does not document the full general-purpose ledger use proposed here, especially a retained mapping handle with no live view.  
   **Experiment:** in a diagnostic driver, query the same stream’s section pointers for: writable view with file handle open; writable view after file handle close; no view but a retained mapping handle; read-only view; `PAGE_WRITECOPY`/`FILE_MAP_COPY`; `SEC_IMAGE`; and opens through a hard link, ADS, and file ID.  
   **Falsifies P5 if:** an actual shared writable view reports zero, the same stream’s opens do not share the expected identity, ADS are incorrectly combined or separated from intended scope, or a retained handle can later create a view after a zero result.

6. **P6 — Stream-context identity is stable and represents aliases correctly.**  
   **Docs:** `SECTION_OBJECT_POINTERS` is per stream and shared by file objects for that stream. NTFS hard links are multiple names for one file; ADS are separate streams. This does not establish name membership, reparse behavior, file-ID mapping, or stream-context support across every destination type.  
   **Experiment:** create a file with `CreateFileW`; add a hard link with `CreateHardLinkW`; create an ADS using `CreateFileW(L"file:stream")`; obtain `FileIdInfo` via `GetFileInformationByHandleEx`; open by ID with `OpenFileById` or `NtCreateFile(FILE_OPEN_BY_FILE_ID)`; and exercise rename with `SetFileInformationByHandle(FileRenameInfoEx)`, short names with `GetShortPathNameW`, and reparse paths with `CreateSymbolicLinkW`/`FSCTL_SET_REPARSE_POINT`. Log stream context and section-pointer identities plus every policy decision.  
   **Falsifies P6 if:** a hard-link alias is treated as an unrelated stream, ADS scope does not inherit the intended base-file policy, a file-ID/reparse/short-name open resolves to an unclassified protected object, or a context is missing on a required stack.

7. **P7 — Cost is within budget.**  
   **Docs:** No Windows contract answers product latency or pool-cost targets.  
   **Experiment:** use the existing latency harness or an equivalent timed workload of repeated `CreateFileW`, `WriteFile`, `CreateFileMappingW`, `MapViewOfFile`, `UnmapViewOfFile`, and `CloseHandle` across many unique files and ADS. Collect ETW/QPC p50, p95, max latency, nonpaged-pool usage, context count, and failure rate under memory pressure.  
   **Falsifies P7 if:** p95 exceeds 250 ms, any call exceeds the stated 1,000 ms maximum, memory grows without a safe cap, or allocation pressure causes unprotected admission.

**Missing premises:** TxF commit lifetime after file-handle cleanup; a complete path/alias-to-stream index and namespace-update linearization; a capacity/resource-exhaustion policy; lower-stack and raw-device writes; driver-load failure and policy-before-agent behavior; and state preservation across Fast Startup, S4, S3, surprise removal, and dismount. The design’s P1–P7 list does not settle those items.

## D. Non-goals that need a narrower threat statement

- **Other computers writing through SMB:** this is a reasonable exclusion only if SafeUpload promises protection against local endpoint writers, not all writers to a UNC destination. It conflicts with an unqualified per-file writer claim for SMB destinations. Remote mapped views are explicitly not coherent across computers.
- **Mandatory dismount/unload:** not outside a reasonable endpoint availability model for USB/removable destinations, surprise removal, and normal power transitions. If the filter can be removed while protection is active, protection must fail closed externally or mark the volume unusable.
- **Offline disk access:** reasonable to exclude from a live file-system filter threat model if device loss/data-at-rest is handled separately, for example by full-volume encryption. It is not reasonable to claim protection against a person with physical disk access without that separate boundary.
- **Kernel-mode adversaries:** generally reasonable to exclude for a minifilter. However, legitimate lower-stack drivers and file-system filters are not adversaries; their generated I/O still needs qualification.
- **Remote mapped-file incoherence:** not a harmless footnote while SMB remains in scope. Either define remote writers as trusted/out-of-scope or add server-side cooperation.

## E. Alternatives

- **Keep staging disabled and retain the current taint behavior** until the protection boundary is implementable. That does not satisfy this design’s objective, but it avoids treating the unqualified scan fence as proof. The design document itself says the writer ledger is not yet implemented and taint remains active ([writer-ledger-design-v1.txt](/home/victor/Work/safeupload-staging/driver/evidence/2026-10-03/writer-ledger-design-v1.txt:3)).
- **Private backing from the first controlled open, then inspect and publish an exact version** is more robust for new writes because bytes do not enter the public destination before approval. It still needs an admission boundary before earlier handles exist and complete identity/alias handling; it does not solve late policy expansion by itself.
- **External admission on a managed dedicated local NTFS volume** can drain/deny access before a scope is enabled, but it violates the required universal destination scope. `FSCTL_LOCK_VOLUME` is volume-wide, fails if any file is open, fails on system/pagefile volumes, flushes cached data before locking, and is unsupported for SMB 3.0 in its documented compatibility table. ([assessment](/home/victor/Work/safeupload-staging/driver/evidence/2026-10-03/admission-gate-design-assessment.txt:16), [FSCTL_LOCK_VOLUME](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_lock_volume))
- **A custom file system or stricter file-system-level admission** could prevent new writable handles/sections before they exist, but changing the file-system layer does not revoke existing mapped views and cannot by itself cover remote server-side writers or raw disk access.
- **A timeout, ACL change, oplock, or flush** is not a substitute for revoking an existing section/view. The section-sync oplock behavior is not a universal hold: writable-section creation breaks specified oplocks without acknowledgement and proceeds immediately. ([oplock behavior](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/fs-filter-acquire-for-section-synchronization2))

## F. Recommended order if the design is revised

1. **Cheapest kill test:** run P3 on a disposable NTFS VHDX. Keep a writable mapping-object handle open, unmap all views, close the file handle, observe `MmDoesFileHaveUserWritableReferences`, then map a new view and write after the proposed Protected transition point. An independent raw-byte observer determines whether the write becomes durable. If a new view can write after a zero result or without a new section-acquire event, stop the ledger design.
2. If that test survives, settle TxF close-then-commit, raw-device access, and lower-stack filter routing before designing data structures.
3. Define the volume/file/stream/alias identity model, global active-writer index, capacity handling, and boot/agent/resume failure states.
4. Prove an operation-admission epoch across all creates and mutations; separately prove what section-acquire callbacks can and cannot drain.
5. Only then build an observe-only ledger, qualify NTFS/removable/SMB stacks, and measure pool and latency. Keep staging and taint behavior unchanged until those gates pass.

The design does not survive as written: no policy-rundown refinement fixes the section-object lifetime gap, and the raw-device boundary conflicts with path-scoped fail-closed behavior.
