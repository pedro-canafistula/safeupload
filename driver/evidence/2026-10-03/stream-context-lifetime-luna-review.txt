Stream-context lifetime countermeasure review
Date: 2026-10-03
Reviewer: delegated Luna security/source-contract review
Reviewed checkout: HEAD 740e47457f35cab185b77ded2a23e77796f2dca8
Scope: whether an FLT_STREAM_CONTEXT can safely retain the writable-section
fence for a section handle that survives policy expansion without a mapped view.

Disposition
============

The idea is plausible as a policy-expansion countermeasure on a specifically
qualified stack, but its key lifetime assumption is not established by the
documented contracts. Do not implement or count it as closing the leak based on
documentation alone. No files were changed by the review; no build, VM run, or
target-stack experiment was performed.

Lifetime and race findings
==========================

Microsoft documents that a stream context is associated with a stream object
and is cleaned up when that object is torn down. Microsoft also documents that
the memory manager associates a file object with a section. Neither contract
establishes that a retained section handle with no mapped view keeps the source
FILE_OBJECT and its stream context alive until that handle closes. Therefore it
does not prove that a context installed during policy expansion is still
retrievable when the section handle later creates its first writable view.

With no driver-held context, file-object, instance, or section reference, an
attached marker has no obvious driver-created self-pinning cycle, but its
availability across the retained-section lifetime remains unproven. An
external registry that holds a context reference can delay context cleanup;
using that same cleanup callback to unlink the owning registry entry would
create a lifetime cycle unless the registry has a separate safe rundown and
unlink protocol.

Stream-context support is per file and must be checked. A missing context,
unsupported stream, or failed lookup cannot be treated as evidence that a
stream is outside protected scope. Context lookup is compatible with the
pre-operation IRQL range, but higher-IRQL paths need separate handling.
Filter Manager deletes contexts when the associated object is deleted, an
instance detaches, or the filter unloads, so this mechanism cannot preserve a
fence through mandatory teardown. The asynchronous InstanceSetup scan also
leaves a late-attach window before a context is installed. Thus even a proven
retained-section lifetime would close only one policy-expansion slice.

Evidence required before any prototype
======================================

1. On each target stack, retain a writable section handle with no view after
   closing the source file handle; prove the context remains retrievable
   through later map, write, unmap, and final section-handle close, and prove
   cleanup occurs only after no later writable view can be created. Include
   NTFS, every intended USB filesystem, SMB redirector/server paths, and the
   actual sync-client stack.
2. Race section creation immediately before and during candidate admission
   and scans; install the marker on all candidate streams; map for the first
   time after publication; verify denial and independently observe destination
   bytes. Include aliases, links, and incomplete-scan cases.
3. Review context cleanup, IRQL, reference ownership, locking, rundown, stale
   registry pointers, and fail-closed behavior on unsupported contexts,
   lookup failures, and capacity exhaustion.
4. Prove behavior during manual teardown, dismount, surprise removal, mandatory
   detach/unload, and recovery. Context deletion on teardown means this still
   blocks cutover unless protected state remains private after the event.
