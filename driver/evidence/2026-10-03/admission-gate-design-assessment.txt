Admission-gate design assessment
Date: 2026-10-03
Basis: Luna's official-Microsoft-source review and the cited Microsoft contracts below.

Disposition
===========

Universal destination admission is NOT PASSED. No supported path-scoped OS
primitive was identified that quiesces every existing handle and writable
view across fixed NTFS, USB/removable storage, SMB/UNC, and sync clients. The
current minifilter cannot turn a late scan or policy transition into that
missing admission barrier. Staging remains disabled by default; do not change
taint enforcement. This note is an architecture assessment, not a
cutover approval, implementation result, or proof of byte privacy.

A managed, dedicated fixed-local-NTFS volume may support a restricted
cooperative experiment. That option requires a trusted external admission
owner to block direct access before any ordinary handle or writable section
can be created, drain prior users, and keep access closed through filter attach
and complete inventory. It is volume/deployment-specific and does not satisfy
the universal destination requirement.

Contract constraints
====================

* File access is checked when a handle is opened and granted rights attach to
  that returned handle. CreateFile share constraints remain in force for that
  handle until it is closed. A mapped view is a process address-space pointer
  that can be written directly; the system may write changed pages later.
  Therefore, changing ACLs or share settings after open does not revoke
  already-granted handles or existing views. This conclusion follows from the
  documented per-open rights/share behavior and mapped-view behavior; it is an
  architectural inference, not a separate revocation API guarantee.
* The section-acquire callback cannot be pended as a policy admission wait.
  Microsoft documents the section-sync operation as an FSFilter callback and
  permits FLT_PREOP_PENDING only for IRP-based I/O; the IRP pending contract
  therefore does not provide a wait/resume path for this FSFilter operation.
  The section-specific page says SyncTypeOther cannot fail and documents
  STATUS_INSUFFICIENT_RESOURCES as an allowed SyncTypeCreateSection failure
  when memory is insufficient; it does not say that is the only possible
  failure. The generic minifilter contract permits FLT_PREOP_COMPLETE with a
  final NTSTATUS other than STATUS_PENDING, and the FS_FILTER callback contract
  says a non-success status fails the request and should describe the error
  accurately. Together these contracts indicate that STATUS_ACCESS_DENIED for
  an actual policy refusal on SyncTypeCreateSection is contract-consistent,
  although the section-specific page does not name that status. Confirm the
  exact behavior on each qualified OS/filesystem stack. Never report fake
  memory exhaustion as a policy refusal. The filter's FltCreateSectionForDataScan
  facility creates sections for scanning; it is not a way to deny a caller's
  section creation.
* FSCTL_LOCK_VOLUME is volume-wide. It succeeds only when there are no open
  files, flushes cached data before locking (so dirty data may be made public
  before the lock), and fails for system or pagefile volumes. The page's
  Windows 8/Windows Server 2012 compatibility table marks SMB 3.0 protocol,
  SMB 3.0 Transparent Failover, and SMB 3.0 Scale-out File Shares as
  unsupported; CsvFS is marked "See comment" and has separate open-file and
  node-notification conditions. Do not generalize those table rows beyond
  their stated technology/version scope. FSCTL_LOCK_VOLUME is not a
  path-scoped gate and must not be used to flush unapproved mapped bytes as a
  purported privacy measure.
* FSCTL_DISMOUNT_VOLUME is not a safe substitute: it attempts to dismount even
  while processes use the volume, can have unpredictable results, and the OS
  can remount the volume on access.
* The FS_FILTER_ACQUIRE_FOR_SECTION_SYNCHRONIZATION-specific oplock contract
  says that a writable section-create acquire
  (SyncTypeCreateSection with PAGE_READWRITE or PAGE_EXECUTE_READWRITE) always
  breaks Read, Read-Handle, Read-Write, and
  Read-Write-Handle oplocks to None without acknowledgement, and the operation
  proceeds immediately; this operation does not affect other (legacy) oplock
  types. This callback behavior is not a universal hold. By inference from
  that contract and the mapped-view model, oplocks cannot prove all existing
  writable views have drained or prevent direct mapped-pointer stores.
* In-filter operation rundown can help drain admitted IRP mutations only. By
  inference from the documented mapped-view model, it cannot stop arbitrary
  writes through an already returned user-mode view pointer, nor can it make an
  incomplete/failed inventory complete. InstanceSetup is called on the first
  operation after mount and must not synchronously wait or perform IPC due to
  deadlock risk. Mandatory teardown/dismount remains outside a voluntary
  QueryTeardown veto.
* As a design inference, USB/removable support would need managed
  automount/access controls plus a separately enforced restriction on
  direct/manual volume access. Microsoft's automount command is documented as
  preventing automatic mounting of new volumes; it does not claim to block
  direct/manual opens. CreateFile and volume-GUID naming provide direct volume
  access forms, so disabling automount alone is not an admission barrier.
  Similarly, as a design inference, SMB/UNC support would need an early
  network/MUP admission layer that remains present at all times; it is not
  implemented here.
  Microsoft documents MUP's UNC routing and also documents that subsequent
  handle-based operations may bypass MUP after provider resolution; the
  proposed early admission requirement is an inference from those paths, not
  a Microsoft guarantee that a MUP filter alone covers every network access.
  Pausing or disconnecting a sync client does not prove that its handles or
  mappings are drained. The broader conclusion that no supported path-scoped
  primitive covers all these actors and storage types is an architecture
  inference from the cited contracts, not a Microsoft guarantee about every
  possible deployment.

Restricted cooperative option (not approved)
============================================

For an isolated, dedicated fixed-local-NTFS test volume only, a future design
could keep an external broker/management gate closed before the first ordinary
open or section creation, stop or drain every writer and sync process, and
maintain that gate while the filter attaches and completes a full, verified
inventory. FSCTL_LOCK_VOLUME could be evaluated only as a secondary
whole-volume no-open check on a known-clean test fixture. Because it flushes
cached data before locking, the design must first establish that no dirty,
unapproved mapped bytes exist; lock success alone cannot establish that fact.
Keep the external gate closed across any unlock, scan, retry, cancellation, or
recovery step, and release it only after coverage and filter readiness are
independently verified. This is a cooperative managed-volume workflow, not a
path-scoped Windows primitive and not support for general fixed-volume,
removable, network, or sync-client destinations.

Required failure and restart behavior
=====================================

Any open/mapping drain failure, lock failure, unknown filesystem or volume
classification, attach gap, incomplete/over-cap scan, candidate-scope skip,
retry failure, or uncertain teardown must leave external admission closed and
staging off. External admission must precede handle/section creation; if it
cannot be established, destination support remains off. Never release access
because a timeout elapsed, one mutable volume snapshot omitted an identity, or
quarantine alone appears successful. Do not substitute a forced dismount. A
restart is an availability/recovery action,
not evidence that dirty mapped data stayed private; shutdown may itself flush
dirty pages. Before restarting or clearing sticky quarantine, keep external
access blocked and establish a safe dirty-data state. If the external gate
cannot be preserved or re-established across failure/restart, that deployment
must remain unsupported for staging.

Minimal proof experiment
========================

Use a disposable dedicated fixed-local-NTFS volume that is neither the system
volume nor a pagefile volume. An independent raw-volume observer records the
entire allocated fixture extent after the fixture is initialized and flushed.
First demonstrate that the external gate closes before any test process can
open the fixture or create a writable mapping; include a competing process
that repeatedly races CreateFile/CreateFileMapping/MapViewOfFile against gate
closure. Prove that an already-open test handle makes FSCTL_LOCK_VOLUME fail
and that the external gate stays closed; with all test handles gone and only a
known-clean fixture, record whether the lock check succeeds. Do not issue
FSCTL_DISMOUNT_VOLUME.

While external access remains closed, attach the filter, run the full inventory,
and verify exact scope, coverage counters, and readiness. Inject attach,
classification, scan, and capacity failures; each must keep the external gate
closed and staging disabled. Keep the gate closed across the lock/unlock and
scan sequence. Only then test controlled staging, release of ordinary access,
concurrent admission attempts, and a separate raw comparison of the complete
fixture extent. Any changed byte, unobservable probe, incomplete coverage, or
successful open/mapping while admission should be closed is a failure. A pass
would validate only that explicitly managed local-volume workflow; it would
not validate USB/removable, SMB/UNC, sync clients, or the universal DoD.

Contract correction (2026-10-03)
================================

A follow-up Luna review corrected an earlier overstatement that
STATUS_ACCESS_DENIED is categorically unsupported for writable-section
creation. The general callback contracts permit an accurate final error
status; the section-specific page does not name a policy-denial status but also
does not say its documented insufficient-memory failure is exclusive. Thus
STATUS_ACCESS_DENIED appears contract-consistent for a policy-denied
SyncTypeCreateSection, subject to a disposable target-stack test. The actual
privacy blocker is lifetime of already-created writable views: Windows
documents that handles can close while views remain mapped and that modified
pages may be written lazily later. A process can store through the view pointer
without issuing file I/O at the time of the store. The section acquire/release
notifications do not provide a documented path-scoped rundown of all extant
views across processes or SMB clients. This lifetime conclusion is an
inference from the documented view and callback contracts, not a theorem that
Windows cannot add such an API. MapViewOfFile is documented to work with
remote files, but writable mappings on different computers are not coherent.
The full destination DoD therefore remains open; do not narrow it or claim a
universal admission gate based on this correction.
