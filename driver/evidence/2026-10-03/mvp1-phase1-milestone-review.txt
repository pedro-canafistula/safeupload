# Verdict

**No—Phase 1 cannot be called complete on HEAD `de9f096a`.** The plan says it remains open pending this review and the unexercised branches; the evidence covers many normal create and section paths, but not late or manual attachment with an existing writer, TxF, mounted-volume tracking loss on filter unload, or a writer-free decision followed by a physical-file cache flush. Most seriously, setup flags are recorded but ignored by the canary, so a late-attached instance can report `PASSED` without accounting for writers that existed before attachment. The end-to-end MVP guarantee is also still open: the plan labels the publication regression as regression evidence, not acceptance, and Phases 2–5 remain open. This is a source and evidence review only; the experiments below are proposed, not run. ## Findings

### P0 — F-01: Late/manual attachment can report a passed canary with an uncounted live writer

**Location:** `InstanceSetup` saves `SetupFlags`, but `SafeUploadStageCanaryTick` gates only on fixed NTFS and detached state; it does not reject late or manual attachment. The canary publishes `PASSED` based on its own temporary-file check. H is added only in successful post-create, while a missing stream context can snapshot as zero. [Context.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Context.c:341) [StageAdmission.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageAdmission.c:871) [StageAdmission.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageAdmission.c:845) [StageWriters.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:149) [StageWriters.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:297)

**Scenario:** A user opens a file for write on an already mounted fixed NTFS volume and keeps the handle open, optionally duplicating it to a child process. SafeUpload is then loaded or manually attached. That create was not seen, so its writer node was never added. A probe may report H=0, S=NO and C=0 for the file while the old handle remains a write capability; the new temporary-file canary can independently pass. The canary is therefore not evidence that this late-attached volume is safe to trust. Windows exposes separate setup flags for automatic attachment, manual attachment, and newly mounted volumes, but this code does not use them to enforce the owner’s late-attach rule. [Microsoft instance-setup flags](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nc-fltkernel-pflt_instance_setup_callback)

This establishes a false free-of-writers observation and an invalid canary trust label. I would measure whether the old handle can still alter a protected fixture too; the current physical-write gate may deny that particular write, which would not cure the false state.

**Why evidence misses it:** The new-volume canary run used a fresh VHDX attached as newly mounted; the writer-count corpus opens writers after attachment. Neither exercises a writer held across late/manual attachment. [canary-newvolume-run1-6-readout.txt](/home/victor/Work/safeupload-staging/driver/evidence/2026-10-03/canary-newvolume-run1-6-readout.txt:8)

**Experiment:** E1.

### P0 — F-02: The required TxF writer state is absent

**Location:** The design defines T(F) for uncommitted transacted writers and requires transacted write opens in a protected scope to fail closed. `StageAdmit` classifies writes by desired access and disposition but has no transaction check; the writer snapshot and admission trace expose H/S/C, with no T state. [writer-state-design-v2.txt](/home/victor/Work/safeupload-staging/driver/evidence/2026-10-03/writer-state-design-v2.txt:21) [MVP-PLAN.md](/home/victor/Work/safeupload-staging/driver/MVP-PLAN.md:30) [StageStream.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:2287) [Protocol.h](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Protocol.h:719)

**Scenario:** A user starts a transaction, opens a target with `CreateFileTransactedW`, writes, closes the file handle while leaving the transaction open, then commits. H can fall to zero at cleanup, and S/C do not represent the still-commit-capable transaction. Windows documents transacted file handles and transaction commit separately; the design itself says this case needs explicit rejection or tracking. [CreateFileTransactedW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createfiletransactedw) [How to Use TxF](https://learn.microsoft.com/en-us/windows/win32/fileio/how-to-use-transactional-ntfs)

**Why evidence misses it:** The listed writer, section, canary and regression readouts contain no transacted open/close/commit case.

**Experiment:** E2.

### P1 — F-03: Any instance teardown is classified as safe volume teardown

**Location:** `SafeUploadStageWritersInstanceTeardownStart` explicitly ignores `Reason` and marks the token `TEARING_DOWN` for every teardown. When the writer context is freed in that state, it increments `WritersDroppedAtTeardown` without setting global Unknown; the active-state path does set Unknown. Voluntary unload preparation checks the fence and staged streams, not H writer records. [StageWriters.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:70) [StageWriters.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:256) [StageStream.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:2163)

**Scenario:** Keep an ordinary write handle open on a still-mounted volume, disconnect the Inspector, then request voluntary or mandatory filter unload. If writer contexts are freed during that teardown, the code treats the loss like dismount/removal. A reload without reboot starts with fresh global state, while the old handle may still be live. Whether Windows permits this exact sequence with the handle outstanding needs VM confirmation.

**Why evidence misses it:** Manual detach was vetoed. The teardown qualification exercised dismount, where Filter Manager still delivered held-acquire completion and cleanup; it explicitly leaves filter unload with open files and the dropped-at-teardown branch unexercised. [section-teardown-run1-10-readout.txt](/home/victor/Work/safeupload-staging/driver/evidence/2026-10-03/section-teardown-run1-10-readout.txt:17)

**Experiment:** E3.

### P1 — F-04: H reaching zero is not a physical-file cache-flush barrier

**Location:** H is decremented at cleanup. Physical-file dispatch tracks writable section synchronization, but does not use the owned-stream `StageFlush` path for an unowned NTFS file. `StageFlush` calls `CcFlushCache` only for SafeUpload’s owned stream. [StageWriters.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:215) [StageStream.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:2917) [StageStream.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:891)

The design already requires cached data to be flushed in addition to `Free(F)`. This finding is about keeping those conditions separate: H/S/C/T being clear does not itself prove that dirty Cache Manager data for a physical file cannot still be written back. Microsoft documents `CcFlushCache` as a separate operation for flushing cached data; whether a later transition reliably performs and waits for that barrier is not established here. [CcFlushCache](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ccflushcache) [MmDoesFileHaveUserWritableReferences](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-mmdoesfilehaveuserwritablereferences)

**Scenario:** A buffered writer dirties a physical file’s shared cache, then closes its last user handle. H decrements; S may be NO and C zero. If a consumer treats that state alone as ready to protect, later paging/writeback can still change the on-disk bytes.

**Why evidence misses it:** The cached-write run measures H while the handle is open and after close, but does not correlate H=0 with later paging writes or an independent raw-volume observation. The design calls for a separate flush condition, but the readouts do not qualify its implementation.

**Experiment:** E4.

### P1 — F-05: A higher-altitude filter can hide a physical open from H

**Location:** H depends on SafeUpload receiving the create callbacks registered in `Filter.c`. A higher filter can complete a pre-operation before lower instances are called; Microsoft documents that completion this way stops delivery to lower minifilters and the filesystem. A higher filter or kernel component that proxies a real file through a lower-targeted open can therefore avoid SafeUpload’s H create accounting, and may also send writes below its physical-write gate. [Filter.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Filter.c:129) [StageWriters.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageWriters.c:149) [FltCompletePendedPreOperation](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltcompletependedpreoperation)

**Scenario:** A signed upper-altitude minifilter completes or proxies a user create, opens the underlying file below SafeUpload, then services writes through that lower object. SafeUpload has no counted create for the file, while the proxy can still change its bytes. This requires another kernel filter/component; `IO_IGNORE_SHARE_ACCESS_CHECK` alone is not this bypass.

**Why evidence misses it:** The lower-filter experiments show SafeUpload handling lower acquire failures and holds, not an upper filter completing creates or servicing writes through a lower-targeted object. [section-lower-run5-sectiondrain-verifier-readout.txt](/home/victor/Work/safeupload-staging/driver/evidence/2026-10-03/section-lower-run5-sectiondrain-verifier-readout.txt:10)

**Experiment:** E5.

## Ordered VM experiments

Run on a checkpointed Windows 10 19045.2965 VM with local fixed NTFS and independent restoration.

1. **E1 — Late/manual attach with an existing writer.** Before loading/attaching SafeUpload to an already mounted volume, open a fixture for write with broad sharing and keep the handle alive; duplicate it into a child. After attachment, capture setup flags, canary state, and H/S/C for the file, then write a marker through the old handle and verify it with an independent reader/raw observer. A canary pass with non-new-mount setup flags and H=0 confirms the false trust result. If the write is denied by the physical-write gate, record that separately; it does not refute the missing late-attach quarantine.

2. **E2 — TxF commit after handle cleanup.** Use a helper with `CreateTransaction` and `CreateFileTransactedW` on a fixture in the protected folder. Write a marker, close the file handle while keeping the transaction open, capture H/S/C and the open result, then commit and inspect bytes independently. Confirm the gap if a commit-capable transaction coexists with a reported free state or if its protected write is admitted. Refute it if the open is rejected or the file stays Unknown/Activating until transaction completion.

3. **E3 — Unload with a live writer on a mounted volume.** Keep an ordinary physical write handle open on a file with no SafeUpload staged stream or writable mapping. Disconnect the Inspector, attempt voluntary unload, preserve the writer, reload without reboot, reconnect, and write a marker. Capture teardown reason, dropped-writer counters, and global Unknown using kernel trace or a small test-only event because unload resets in-memory counters. Confirm if tracking is dropped as teardown without sticky Unknown and the old handle still writes; refute if unload is vetoed or mounted loss stays Unknown.

4. **E4 — Dirty cached writeback after H reaches zero.** Use buffered `WriteFile` without `FlushFileBuffers`, close the last handle, and repeatedly sample H/S/C while tracing paging/modified-page writes for the file. Use the independent raw-volume observer to correlate later writes with the H=0 interval; apply memory pressure to encourage delayed writeback. A paging write after H=0 confirms that Free alone is not the flush barrier. A promotion path that waits for an explicit flush/purge before protection would refute the integration concern.

5. **E5 — Higher-altitude proxy path.** Add a small signed test minifilter above SafeUpload. Have it proxy a fixture create and open/write the physical target through a lower-targeted instance or device-object hint. Capture SafeUpload create/write callbacks and H/S/C, then verify the target bytes independently. A changed target with no H count or SafeUpload write callback confirms the stack-order precondition; if the path cannot be implemented under the qualified stack, record that constraint as an explicit deployment assumption.

6. **E6 — Post-success cancel and real FASTIO callbacks.** Use a companion minifilter in both relevant altitude positions to call `FltCancelFileOpen` only after the lower filesystem reports a successful writer create. Record create status, H insertion/release, cleanup and unmatched counts. In a separate cached I/O loop, instrument actual `FLT_IS_FASTIO_OPERATION` callback hits alongside IRP writes. Confirm the evidence gap if the harness exercises only pending-create cancellation or IRP writes.

7. **E7 — Canary timeout and section draining.** Use a test-build hook to hold the released-NO answer until the canary’s two-second timeout; capture state/status, trigger another tick/request, and verify Failed remains sticky until reboot. Separately force an acquire completion through `FLTFL_POST_OPERATION_DRAINING` during unload/teardown and verify global Unknown persists. A normal PASS or cleanup with no Unknown would confirm a fail-closed defect.

8. **E8 — Writable section from a read-only file handle.** As a normal user, open a fixture with read access only, attempt `NtCreateSection(SECTION_MAP_WRITE, PAGE_READWRITE)`, duplicate any resulting section handle to a child, map and write. Record syscall results, C callbacks, H/S/C and the file’s physical bytes. Use `FILE_MAP_COPY` and an image/`WriteProcessMemory` case as controls; private-copy changes do not count as backing-file writes. If the read-only handle cannot create a backing-writable section or only private bytes change, this candidate is refuted.

9. **E9 — Test-control reachability and packaging.** From an elevated administrator with privileges disabled, attempt to connect to the filter port and issue the test commands; then repeat from the SYSTEM Inspector. Inspect the exact intended Release artifact for command handlers. Confirm the current access gate if admin is denied, and confirm owner compliance only if the user-receivable artifact lacks context-delete/canary-hold commands. If SYSTEM commands are reachable through the test harness, record whether they cause only the expected fail-closed availability effects.
