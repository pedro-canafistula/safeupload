## Findings

### P0 — F-01 late attach leaves pre-attach mapped writers outside the fence

**Location:** [Filter.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Filter.c:305), [Context.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Context.c:327), [StageStream.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:2746), [StageFence.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageFence.c:1735), and [Test-StagedBootStart.ps1](/home/victor/Work/safeupload-staging/driver/scripts/Test-StagedBootStart.ps1:671).

Boot mode disables scan-based fence refresh; a late-attached instance is marked untrusted, but that state only gates new opens. A writable section created before attachment is not necessarily in the fence table. Paging writes are denied only when the table recognizes the section, and an empty table returns “not fenced.” The E1 harness opens a file before reattachment but does not retain and write through a writable mapping afterward. Its prepared policy scopes C:, not the S: VHDX used by E1, so E1 can report Untrusted without exercising protected-write refusal. This is the unresolved F-01 described in the [triage](/home/victor/Work/safeupload-staging/driver/evidence/2026-10-03/mvp1-phase1-milestone-triage.txt:3).

**Fix / settling check:** Keep a late-attached volume’s potentially protected writes quarantined until reboot, including writes through pre-attach handles and mapped sections. Extend E1 to scope S:, retain a pre-attach writable mapping, write through it after attachment, and verify destination bytes independently.

### P0 — Any SYSTEM process can replace policy and clear the boot union

**Location:** [Communication.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Communication.c:78), [Communication.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Communication.c:253), [Communication.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Communication.c:551), and [Policy.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Policy.c:379).

The port checks that the connecting process has a SYSTEM user SID and binds requests to its PID; it does not establish that the process is the SafeUpload service. A non-service SYSTEM process can connect, send a valid policy with zero destination prefixes, then send the finalize form. Zero prefixes pass validation, and finalization clears `SafeUploadBootScopes` after checking only that the message matches the live policy. It does not verify that the durable registry commit occurred. The documented port ACL also allows SYSTEM access.

**Scenario:** An unrelated SYSTEM process installs an empty policy and finalizes it. Subsequent writes to the former boot-protected path are outside the active scope, even if the agent is down.

**Fix / settling check:** Authenticate the service identity (for example, a dedicated service SID), not merely SYSTEM, and bind finalization to a kernel-verified durable transaction. Test that a separate SYSTEM process cannot connect or alter/finalize policy.

### P0 — ACL-rejected and salvaged registry data still controls enforcement

**Location:** [BootPolicy.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/BootPolicy.c:347), [BootPolicy.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/BootPolicy.c:361), and [Policy.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Policy.c:203).

When the ACL check fails, the reader marks the state ACL_REJECTED but continues reading and using `Scopes` and `PendingScopes`. `SafeUploadInitializePolicy` activates boot protection only if decoded prefixes or flags exist. Thus a weak or empty record can be enforced despite an ACL-rejected state; a partially salvaged record can omit scopes that were not recoverable. The plan explicitly accepts “no scope” when no scope can be identified, which means a missing, corrupt-empty, or ACL-rejected-empty policy provides no protection.

An elevated local Administrator with `SeTakeOwnershipPrivilege` can take ownership of registry keys and change their DACLs; Microsoft documents that this privilege applies to registry keys and is assigned to Administrators on client computers by default ([registry key access rights](https://learn.microsoft.com/en-us/windows/win32/sysinfo/registry-key-security-and-access-rights), [Take ownership of files or other objects](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/security-policy-settings/take-ownership-of-files-or-other-objects)).

**Fix / settling check:** Do not consume policy values after ACL rejection. Decide how missing or corrupt-empty policy prevents writes before relying on the driver; the current owner decision in [MVP-PLAN.md](/home/victor/Work/safeupload-staging/driver/MVP-PLAN.md:164) explicitly leaves those cases unprotected when no scope is identifiable. On the VM, verify that ACL-rejected, missing, and corrupt-empty states cannot result in an accepted boot with writes reaching the test scope.

### P0 — Service create passes through if normalized-name lookup fails

**Location:** [StageStream.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:2348), [StageStream.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:2366), and [StageStream.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:2394).

For a writer identified as the service, a failed name lookup can return `FLT_PREOP_SUCCESS_NO_CALLBACK`. That is before the protected-name trust/authentication gate and before `SafeUploadPublicationCreate`. With a path-prefix-only policy on a known local volume, the code cannot match the destination when the name is `NULL`, so a lookup failure can pass the create through.

This is an edge path, not the normal “new file” case: Microsoft documents that normalized pre-create lookup succeeds when only the final path component does not exist. Resource failures and other query failures remain possible ([FltGetFileNameInformation](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltgetfilenameinformation)).

**Fix / settling check:** Fail closed for service writes whenever the destination name is unresolved; require a successfully normalized name and explicit publication authorization before passing a service create through. Exercise the lookup-failure path with fault injection.

### P0 — Driver or boot-policy failure can leave the startup probe writing into the test scope

**Location:** [SafeUpload.inf](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/SafeUpload.inf:69), [Policy.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Policy.c:203), and [Test-StagedBootStart.ps1](/home/victor/Work/safeupload-staging/driver/scripts/Test-StagedBootStart.ps1:479).

`ErrorControl=1` intentionally lets Windows continue if driver initialization fails. Separately, a missing or unreadable boot policy leaves the scope set empty without stopping the filter from proceeding. The AtStartup SYSTEM task records whether the filter was ready, but attempts the write regardless; the policy-state check also occurs later in `AfterBoot`. If the filter is absent or boot policy is empty, that task can place bytes in the protected test directory and only report the failure afterward.

**Fix / settling check:** Treat a failed or invalid policy load as an explicit protection failure, and do not count an after-the-fact write probe as proof that the destination stayed clean. If continuing to boot is required, an independent protection layer must cover the failure case. On a diagnostic VM, treat any missing filter, invalid policy, or visible destination bytes as a failed run and restore the checkpoint.

### P1 — Failed or pending canary does not revoke boot trust

**Location:** [Context.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/Context.c:329), [StageAdmission.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageAdmission.c:845), and [StageStream.c](/home/victor/Work/safeupload-staging/driver/SafeUpload.Minifilter/StageStream.c:2394).

Trust is assigned from the newly-mounted flag and remains so if the asynchronous canary later fails or times out. The create trust gate checks trust and client authentication, not canary state. That conflicts with the owner decision that a failed or timed-out startup canary stays Untrusted until reboot ([MVP-PLAN.md](/home/victor/Work/safeupload-staging/driver/MVP-PLAN.md:243)).

**Fix / settling check:** Require a passed canary before trusted admission; keep the instance Untrusted on failure, timeout, unsupported, or pending state. Test those outcomes before allowing the service to install policy.

### P1 — The service policy file has no explicit ACL enforcement in source

**Location:** [AgentPaths.cs](/home/victor/Work/safeupload-staging/agente/SafeUpload.Agent.Core/Infrastructure/AgentPaths.cs:6), [LocalPolicyStore.cs](/home/victor/Work/safeupload-staging/agente/SafeUpload.Agent.Core/Infrastructure/LocalPolicyStore.cs:53), and [MinifilterInterceptor.cs](/home/victor/Work/safeupload-staging/agente/SafeUpload.Agent.Service/Interception/MinifilterInterceptor.cs:481).

The code creates or reads `%ProgramData%\SafeUpload\policy.json` without setting or verifying an ACL. The source comment says the real agent would protect this path but the mock does not. If a normal user can modify the file on the VM, they can keep at least one active category (so validation passes), set `auditOnly=true` or remove destination paths, and have the service push that weaker policy and persist it as boot policy.

**Fix / settling check:** Explicitly protect the directory and file, verify owner/DACL before loading, and fail closed on mismatch. On the target VM, check effective write access for a standard user on both the directory and existing file; if writable, treat this as P0.

### P1 — Checkpoint and reboot recovery are not automatic or conclusively verified

**Location:** [Invoke-DebuggeeExperiment.sh](/home/victor/Work/safeupload-staging/driver/scripts/Invoke-DebuggeeExperiment.sh:40), [Invoke-DebuggeeExperiment.sh](/home/victor/Work/safeupload-staging/driver/scripts/Invoke-DebuggeeExperiment.sh:91), and [Invoke-DebuggeeExperiment.sh](/home/victor/Work/safeupload-staging/driver/scripts/Invoke-DebuggeeExperiment.sh:121).

A failed volume-cache flush only prints a warning before checkpoint creation. Reboot-request errors are ignored, and SSH availability is treated as proof the guest returned; it does not prove a reboot occurred. If SSH never returns, the wrapper records recovery instructions and overlay details but does not stop the VM or restore the disk.

The startup task also measures only its own post-readiness attempt and file visibility, not the earliest user-mode write or raw destination bytes. That does not satisfy the X4 exit criterion in the [plan](/home/victor/Work/safeupload-staging/driver/MVP-PLAN.md:188).

**Fix / settling check:** Abort checkpoint creation unless the flush succeeds. Require a boot identifier or `LastBootUpTime` change before continuing. Add an independent observation of destination bytes and the earliest user-mode attempt. Make offline rollback a required operator step if the guest does not return.

## Orchestrator checklist

This revision is a **no-go for a security pass** until the P0 findings are addressed. If the orchestrator chooses an isolated diagnostic boot, it must treat the startup probe as capable of writing its test content when protection is absent.

1. **Confirm the target and clean state.** Verify the intended VM identity and Windows 10 19045.2965 build. Record the original driver hash, service `Start` value, policy file, BootPolicy values and DACLs, active disk path, and backing chain. Do not use a VM containing user data.

2. **Establish a recoverable checkpoint.** Require `VolumeCacheWritten=True`; abort if the flush fails. Create the disk-only external checkpoint, record the overlay and backing file, and confirm `vda` is actively using the overlay before proceeding.

3. **Check the boot inputs.** Confirm the installed driver hash. Verify `Start=0`, `ErrorControl=1`, `LoadOrderGroup=FSFilter Anti-Virus`, and dependency `FltMgr`; do not substitute the demand-start Phase 1 diagnostic path. Confirm the durable policy state is VALID and includes the exact protected test path. Record effective ACLs on the policy file and parent directory.

4. **Check the test scope.** The current E1 policy covers C: but not the S: VHDX. Do not count E1 as a protection test unless S: is in scope. Retain a writable mapping created before reattachment and write through it after reattachment; verify the target volume’s bytes independently.

5. **Prove that a reboot happened.** Capture the reboot command result. Require the guest to go offline and then return with a changed boot identifier or `LastBootUpTime`; SSH responding by itself is insufficient.

6. **Keep the agent stopped for the initial checks.** Verify C: is attached, the boot policy is VALID, and the canary is PASSED before accepting a protection result. Record Verifier output and filter instances. Any missing filter, invalid policy, canary failure, or boot-policy mismatch is a failed run.

7. **Verify the write result independently.** Do not use only the scheduled task’s `Test-Path` result as proof of no destination bytes. Capture the first user-mode attempt versus filter readiness and inspect the underlying destination bytes. If the task reports not ready, treat the run as failed even if the guest boots.

8. **Recover on any boot failure.** If the guest bugchecks, hangs, enters a boot loop, or does not return within the 15-minute window, preserve the overlay and evidence. Power off the VM at the hypervisor, restore `vda` to the recorded clean backing file offline, verify the active disk path and backing chain, then boot the clean baseline. Do not run `AfterBoot` or `Finalize` against an unverified boot.

9. **Verify restoration before closing the run.** After the test cleanup restores the original driver and policy, require another confirmed reboot and verify the final driver hash, service start type, policy state, and active disk. The wrapper’s current failure branch is a manual recovery recipe; it does not perform that rollback itself.
