# T5 public-proxy routing design review — Luna 6

Date: 2026-10-11; reviewed proposal: `05ad4df9`; kernel/backend base: `4e070ab2`.
Review type: source and design review only; no implementation, build, VM, or runtime qualification.

## Verdict: NOT READY

The same-volume `TargetFileObject` retarget is supported by the Filter Manager contract. The proposed cache/section identity mechanism is not established as supported: it gives a synthetic app-facing FILE_OBJECT an NTFS-owned `SectionObjectPointer` while that FILE_OBJECT has a different, driver-owned FCB. The official contract assigns that pointer to the file system and requires filters to treat its members as opaque. The proposal itself requires proof of this pairing (`T5-PUBLIC-PROXY-ROUTING.md:49–57`); the cited WDK contract does not provide it. The read/image-mapping lifetime and NTFS mapped-file delete checks therefore cannot be certified for this proxy.

There is also a position-state contradiction. The proposal says to change only `TargetFileObject` (`:19–23`) but also says to keep the app-facing FILE_OBJECT's position and use it for implicit-offset reads (`:37`). The app-facing and backend FILE_OBJECTs have separate `CurrentByteOffset` fields. Retargeting the request does not, by itself, synchronize those fields. A correct adapter would need to carry the app position into each read and publish the resulting position back under the same per-handle serialization; that is an additional parameter/state transformation beyond the specified target-only change.

The lifetime requirement is correctly called out in the proposal, but the current backend release API cannot be used to implement it as-is. Filter Manager post-operation callbacks can run in arbitrary thread context at IRQL up to DISPATCH_LEVEL. `SafeUploadStagePublicReleaseOperation` is marked PASSIVE-only, placed in pageable code, and calls backend dereference that can wait for rundown and close/free the object (`StagePublic.c:37–43,113–123,146–152`). The integrated implementation needs a nonpaged post-release path that only drops operation/local references there, then defers any final handle close and object destruction to PASSIVE_LEVEL, as the proposal requires (`:70–73`).

The older accepted review (`t5-empty-public-delete-design-review-luna6.md:3,7–11`) accepted the empty-file and public-delete transaction design as a source-only review. It did not review or approve this new synthetic-FCB/native-section-pointer pairing.

## What the proposal gets right

Microsoft's `FLT_IO_PARAMETER_BLOCK` documentation permits a minifilter to change `TargetFileObject` when the new file object is for a file on the `TargetInstance` volume. It also says lower filters see changed inputs while this filter's own pre/post callbacks and filters above it retain the original inputs. Requiring the exact original instance and volume is conservative and satisfies that rule. The `FLT_CALLBACK_DATA` documentation also prohibits changing `Thread` and `RequestorMode`, consistent with the proposal. These contracts support the narrow routing premise; they do not prove the separate section-object pairing.

Current code already has the pieces for a supported native-object path. `StageCreate` leaves an unowned non-writer create to the file system (`StageStream.c:2122–2125`). The public-backend module opens the real existing object with the original access/share request and verifies the granted DELETE right (`StagePublic.c:371–390`). The stream-handle context helpers attach per-open filter state to a real file object (`Context.c:712–748,778–810`). The synthetic private stream instead owns its own `FSRTL_ADVANCED_FCB_HEADER` and `SECTION_OBJECT_POINTERS` (`StageStream.c:55–82,2401–2429`); that self-owned arrangement does not establish that its FCB may share NTFS's section pointer.

## Concrete correction

For a non-writing DELETE-capable open of an existing public file when the caller has no private staged view, let the original CREATE reach NTFS and keep the resulting native FILE_OBJECT as the app-facing object. Attach the driver's per-handle state with a Filter Manager stream-handle context. Keep the separately opened, caller-checked public backend for the exact identity binding and one-use disposition transaction. After CREATE, compare the native app object's volume and full file identity with that backend before exposing success; on mismatch, fail/close the app open and cancel or reconcile the backend's exact durable intent before releasing its identity. Route ordinary reads, metadata queries, byte locks, section operations, and paging through the native app object. NTFS then owns the FCB/section pointer relationship and applies its normal share, lock, mapping, and delete rules. Keep owner-private staged views on their existing owned FCB/cache path, with the public capability separate.

Classify `MAXIMUM_ALLOWED` and generic rights using the actual grant before exposing a native public handle. If the effective grant includes content-write authority, retain the private-stage path. For public `FILE_DELETE_ON_CLOSE`, persist the required intent before CREATE success, strip the create flag while the exact object is being bound, then apply the equivalent supported per-handle `FILE_DISPOSITION_ON_CLOSE` state to the verified native app FILE_OBJECT before completing CREATE. The original CREATE already carries DELETE access because `NtCreateFile` requires it with `FILE_DELETE_ON_CLOSE`; the verified file object can therefore receive the on-close disposition under that original grant. Use Filter Manager's `FltSetInformationFile` path and preserve its actual NTFS result. If it fails, fail the create and reconcile the durable intent; do not leave an unbound on-close delete. This preserves the existing rule that durable intent precedes successful CREATE and preserves NTFS's per-handle on-close behavior (`T5-DELETES.md:188–191`).

This correction does not require a new product choice about delete authority, service latency, failure reporting, taint, or cutover. It retains the existing caller-token check, same-volume identity binding, NTFS result, durable intent, and public-delete generation rules (`T5-DELETES.md:112–147,161–198`). The implementation still needs the required concrete integrated kernel lifetime/lock-order/retirement review before its first revised VM boot (`T5-DELETES.md:6,379–382`).

- Microsoft's [FLT_IO_PARAMETER_BLOCK](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/ns-fltkernel-_flt_io_parameter_block) and [FLT_CALLBACK_DATA](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/ns-fltkernel-_flt_callback_data) contracts support same-volume retargeting and preserve the current filter's original callback inputs.
- Microsoft's [FILE_OBJECT](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ns-wdm-_file_object) documentation says `SectionObjectPointer` is set only by file systems; it also identifies `CurrentByteOffset` as per-FILE_OBJECT state.
- Microsoft's [SECTION_OBJECT_POINTERS](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ns-wdm-_section_object_pointers) documentation defines one pointer structure per stream, requires opens of the same stream to share it, and says filter drivers must treat its members as opaque.
- Microsoft's [FltSetStreamHandleContext](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltsetstreamhandlecontext) is the supported per-open filter-state mechanism. The [FILE_DISPOSITION_INFORMATION_EX](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_file_disposition_information_ex) documentation defines per-handle on-close state and reports `STATUS_CANNOT_DELETE` when a mapped view prevents deletion; [FltSetInformationFile](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltsetinformationfile) is the minifilter API for setting information on an open file object. The [NtCreateFile](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntcreatefile) documentation requires DELETE in DesiredAccess for `FILE_DELETE_ON_CLOSE`. The Win32 [DeleteFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-deletefilea) documentation also describes normal mapped-file/share restrictions.
- Microsoft's [PFLT_POST_OPERATION_CALLBACK](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nc-fltkernel-pflt_post_operation_callback) contract allows IRQL up to DISPATCH_LEVEL, so post-operation release bookkeeping cannot call the current pageable PASSIVE-only backend release routine.
