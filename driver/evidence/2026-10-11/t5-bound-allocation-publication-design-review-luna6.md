# T5 bound allocation/publication design review (Luna 6)

**Verdict: READY WITH TWO REQUIRED CONTRACT CORRECTIONS.** The revised integration is feasible for a non-live implementation. The 124-byte V23 payload fits the existing carrier, and the proposal now closes the earlier authority gaps by binding the original source, durable destination generation, allocation seed, and physical publication to the same checked namespace identity and head. Keep live admission disabled until the full head-aware pipeline is integrated and qualified; the separate integrated kernel lifetime/lock/retirement review remains required before its first revised VM boot. No new owner policy decision is needed.

The corrected proposal at [T5-NATIVE-PUBLIC-OPENS.md:317–374](../../docs/design/publication-and-namespace/T5-NATIVE-PUBLIC-OPENS.md:317) has the right shape: source `FILE_ID_128` replaces the redundant request driver GUID, while the authenticated active connection supplies the current driver identity; V23 has a dedicated exact parser and capability; the driver captures case-correct anchored root/parent/leaf authority; the service persists exact identity plus generation with the manifest and holds the allocation turn through the durable claim; the publisher uses checked parent-relative create and two linked one-use permits; and retry, startup, and interrupted-publication paths all consult the same head. Allocation and journal continuations must remain asynchronous off the filter-port receive loop. Do not enable any legacy path-only fallback for a bound identity.

The current source-ID rule is still ambiguous. The draft says zero means “no public seed” and only expressly requires a nonzero ID for `FILE_OPEN` ([proposal lines 323–337](../../docs/design/publication-and-namespace/T5-NATIVE-PUBLIC-OPENS.md:323)). That does not distinguish an absent target from an existing target that is not copied, such as `FILE_OVERWRITE`; nor does it state how `FILE_OPEN_IF` with an existing target is represented. The allocator’s current semantics check existence for `FILE_CREATE`, `FILE_OPEN`, and `FILE_OVERWRITE`, and seed bytes only for `FILE_OPEN` / `FILE_OPEN_IF` ([StagedTransferAllocator.cs:178–198](../../../agente/SafeUpload.Agent.Service/Interception/StagedTransferAllocator.cs:178)).

Define the field as **the exact original public target identity, or all-zero only when the anchored lookup proved that target absent**, independent of whether its bytes are copied. `ReferenceKind` selects the seed: `NONE` uses the public target when the disposition is `FILE_OPEN` or existing `FILE_OPEN_IF`; `FOLLOWUP` uses only its separately journaled exact held private predecessor; `TOMBSTONE` requires `FILE_CREATE` and proven absence. For `ReferenceKind=NONE`, validate the disposition matrix explicitly (`FILE_OPEN` and `FILE_OVERWRITE` require a public ID; `FILE_CREATE` requires zero; `FILE_OPEN_IF`, `FILE_OVERWRITE_IF`, and `FILE_SUPERSEDE` allow either). For `FOLLOWUP`, apply those existence rules to the exact private predecessor record instead. Before exposing the private open, revalidate that the anchored leaf still maps to the transported full ID, or remains absent for zero. Parent identity plus leaf spelling alone does not prove this. On mismatch or incomplete lookup, fail closed. This makes zero plus `ReferenceKind`/disposition sufficient without adding a payload field or conflating absence with “not copied.”

The insensitive-name canonicalization rule is not yet safe. The draft retains `.ToUpperInvariant()` as the head key and relies on equivalence tests to discover a mismatch ([proposal lines 332–335](../../docs/design/publication-and-namespace/T5-NATIVE-PUBLIC-OPENS.md:332)); the current identity does the same ([StagedDestinationCommitJournal.cs:13–64](../../../agente/SafeUpload.Agent.Service/Interception/StagedDestinationCommitJournal.cs:13)), while directory observation compares with `OrdinalIgnoreCase` ([StagedDestinationNameObserver.cs:119–122](../../../agente/SafeUpload.Agent.Service/Interception/StagedDestinationNameObserver.cs:119)). Tests cannot prove that two Unicode spellings which NTFS treats as one name cannot get separate durable heads. Microsoft recommends `CompareStringOrdinal` for non-linguistic identifiers including NTFS file names; its case-insensitive mode uses the operating system uppercase table ([Handling Sorting in Your Applications](https://learn.microsoft.com/en-us/windows/win32/intl/handling-sorting-in-your-applications)). NTFS also documents its `$UpCase` collation table ([MS-FSCC NTFS Reserved File Names](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fscc/b04c3bd0-79dc-4e58-b8ed-74f19fc2ea0a)).

Minimum correction: persist the exact UTF-16 leaf and make the sole service head resolver compare insensitive leaves with `CompareStringOrdinal(..., TRUE)`, Microsoft's documented ordinal comparator for NTFS file names, rather than using an independently generated invariant-uppercase string as authority. Use that same equality rule for allocation, native observation/reconciliation, publication, and recovery. Resolve within the exact volume/root/parent/case bucket; case-sensitive buckets use exact UTF-16 equality. If multiple persisted entries compare equal, fail closed and reconcile them—never create a second head or fall back to a pathname key. Keep the NTFS equivalence qualification gate as verification of the implementation, not as a substitute for this comparator rule; if supported NTFS volume semantics diverge from the documented comparator, admission must remain closed until the resolver matches those semantics. Continue resolving an existing short-name spelling to its actual long leaf and verifying the original CREATE’s bound identity.

The source references support these corrections without changing product policy: `StageProtocol.c` already carries `ReferenceKind` and disposition in the allocation request ([StageProtocol.c:771–795](../../SafeUpload.Minifilter/StageProtocol.c:771)); the current allocation behavior demonstrates why existence and copying are separate facts ([StagedTransferAllocator.cs:178–198](../../../agente/SafeUpload.Agent.Service/Interception/StagedTransferAllocator.cs:178)). The dedicated parser/capability, exact durable identity/generation, exact held seed, two permits, head-aware retry/recovery, and asynchronous continuation requirements remain as stated in the corrected proposal. No implementation, live admission, or VM boot was reviewed here.
