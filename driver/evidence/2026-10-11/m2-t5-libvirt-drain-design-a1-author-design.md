# T5 libvirt barrier and active-guest recovery design

**Purpose:** provide an implementable path from `PREPARING` to a source-consistent run and independently verified restoration, including loss of the transaction worker while the selected QEMU guest is running. This is a design artifact only. It makes no host, service, policy, VM, libvirt, filesystem, or Git changes.

## Decision

For the MVP, use a **version-pinned terminal fence on the old monolithic `libvirtd` process, followed by explicit helper/QEMU reconciliation**. Do not call it an RPC drain: the barrier is the old daemon process exiting, which prevents any of its threads from continuing an accepted request. Requests that had partial effects when the process exited are ambiguous and must be reconciled against durable checkpoints before recovery proceeds.

This is the shortest route that proves the old daemon cannot later complete an already-authorized call without rebuilding libvirt. It is host-wide and interrupts management connections. It need not kill running QEMU guests: libvirt documents daemon restart as preserving running guests, while warning that management work such as migration or block-copy can be interrupted. Therefore the selected guest can remain active across transaction-worker loss, but the recovery executor must reconnect it and resolve its jobs before shutdown or cleanup. This path is viable only after the bounded read-only captures below confirm all listener routes, helper process behavior, QEMU cgroups, hooks, and active jobs.

Do not use any of the following as the barrier by itself: `PREPARING`/polkit, `virAdmClientClose`, closing the API client, `prioWorkers=0`, a `jobQueueDepth=0` observation, a zero ordinary-worker busy count, or two quiescent polls. Official docs describe client close as forceful disconnection and describe thread-pool values as current counts; they do not promise request completion, an atomic multi-counter snapshot, or a wait in `virAdmServerSetThreadPoolParameters`. The installed 12.7 header declares `prioWorkers`, `nWorkers`, `freeWorkers`, `jobQueueDepth` and Get/Set APIs, but declarations are not a drain contract. The official API reference's getter parameter list omits `jobQueueDepth`, despite the `virt-admin` CLI documenting it. Upstream implementation history distinguishes a stop signal from a separate drain/wait operation; lowering the priority-worker target is not a public drain operation. Even a genuinely idle RPC pool would not prove that QEMU block jobs, asynchronous libvirt jobs, or spawned helpers have finished.

If a global daemon restart is not acceptable, the alternative is a small, version-pinned libvirt dispatch-epoch patch. Its barrier must atomically close request admission for every server endpoint, account for each accepted request before it can be queued, and signal completion only after all prior-epoch handlers have returned. It must not block a worker waiting for itself. That patch still needs separate QEMU-job/helper reconciliation and the source-path fix below. It adds a custom daemon build, deployment, and qualification burden; it is not the MVP path recommended here.

## Bounded transaction

Use one root-owned per-run guardian service as the durable owner of the canonical lifecycle lock, `PREPARING` state, source descriptors/read leases, transaction journal, and recovery entrypoint. Run the ordinary coordinator as a monitored child. This keeps source leases and the gate alive if the coordinator dies while QEMU is active. If the guardian itself restarts, the A3 protocol must acquire and verify new owner-bound leases on newly opened descriptors, store them, and only then release old descriptor-store references; A2's requirement for a `/proc/locks` row bearing the dead owner PID is contradicted by the recorded owner-exit control.

The service is per transaction, not a global libvirt configuration change. Its state machine is durable and monotonic:

`PREPARING → OLD_DAEMON_FENCED → RECONCILED → BASELINED → PRIVATE_RUN_READY → RUNNING → QUIESCENT → XML_RESTORED → INDEPENDENTLY_VERIFIED → CLEANED`.

Any unknown state, absent receipt, path mismatch, lease break, unrecognized XML, process still holding a protected file, nonterminal QEMU job, or failed comparison stops progress and retains the journal, leases, private copies, and run overlay in quarantine. Never unlink a run artifact or restore a path over an unexpected object as an error-recovery shortcut.

1. **Close the transaction gate first.** Acquire the canonical lifecycle flock and durably publish `PREPARING` before querying domains, opening a source, or issuing a mutation. Keep it in place through final verification. It blocks new requester-authorized API calls but is not treated as a barrier for calls already authorized.

2. **Fence the old daemon generation.** Record the exact service invocation ID, PID/start time, executable/package identity, and all listener endpoints. Stop the exact legacy listener sockets and any alternate activators, including the inactive `virtproxyd.socket` that shares the primary Unix path; enumerate actual Unix/TCP/TLS listeners first. Stop `libvirtd.service` under the pinned unit behavior. Wait for a pidfd-confirmed exit of the exact old main process; do not infer it from a successful `systemctl` return alone. Keep the requester gate closed. A later daemon may accept only recovery traffic under the gate.

3. **Reconcile before taking a baseline.** `KillMode=process` means stopping the main process does not prove that service children exited. Wait until every non-QEMU child/helper from the old service generation is terminal and no process has an open descriptor to the selected source, NVRAM, TPM, or run paths. Identify helpers by PID, executable, arguments, cgroup, start time, and open-file identity; never kill an unclassified process. If any old helper remains or identity cannot be attributed, do not snapshot or mutate. Reconcile every request that might have completed partly by reading live/inactive XML, domain state, pool/volume state, process identity, and durable transaction checkpoints. Any state outside the exact old XML, private-state XML, or run-bound XML checkpoints quarantines the run.

4. **Reattach and reconcile QEMU separately.** Start only the pinned `libvirtd` generation while the requester gate remains closed; capture its new invocation/PID. Keep `virtproxyd` and other alternate activation paths disabled for the fence interval. Verify the selected QEMU PID and XML after libvirt reattachment. Inspect every active domain's migration, block-copy, block-job, and other asynchronous job state before proceeding. Wait for existing unrelated jobs to reach terminal state before the restart window; if a job cannot reach a safe point, defer the fence. After restart, query the selected domain and verify no target QEMU job remains before restore. Do not kill QEMU to force the state machine forward. If QEMU is unmanageable, will not shut down in the bounded timeout, or has an unknown job, keep the guest and all evidence intact; cleanup is prohibited.

5. **Resolve requester-writable source ancestors before baseline.** A read lease pins source bytes through an open inode but does not prevent rename/unlink of its parent directory entry. A pathname walk or repeated stat cannot close that race. The reviewed A3 path should copy the complete selected disk chain and persistent state into a dedicated root-controlled directory with no requester-writable ancestor, using no-follow `openat2` traversal, pinned file descriptors, read leases, and before/after name→device/inode checks. Full-stream compare the copy to the pinned input before use. Preserve the old files untouched. Inventory all persistent writable inputs, including any managed-save state, snapshots, file-backed devices, UEFI variables, or other domain state beyond the known disks/NVRAM/TPM. The selected domain and exact cold alias must both be rebound to the verified controlled chain; enumerate every libvirt and storage-pool reference before doing so. Keep a rollback receipt with both exact XMLs and original paths; rollback restores only those XMLs and retains the duplicate until independent comparison succeeds. This is a selected-domain/alias data migration requiring owner review, not a global libvirt setting. Do not proceed if space, chain membership, QEMU read access, metadata needs, or any additional reference is unknown. A copy based on a changed or replaced source path is not accepted.

6. **Take immutable baselines and run only private writable state.** Once the old daemon generation and helpers are reconciled and the protected path is established, record exact disk-chain bytes/metadata, selected XML, NVRAM, and the complete TPM set (including lock/member inventory). Save durable, readback-verified disk/XML/NVRAM/TPM recovery copies before any mutation. Create the writable qcow2 overlay and NVRAM/TPM run copies only in the protected per-run directory. Persist each intended mutation before calling libvirt or creating its object. The guest never writes the baseline files.

7. **Recover coordinator loss while the VM is live.** The guardian notices child loss with a pidfd, durably records `OWNER_LOST`, preserves the lock/leases/gate and run evidence, then performs the same terminal fence on the current libvirtd generation. It reconciles child effects from the durable journal and exact XML checkpoints, reattaches the still-running QEMU, checks jobs and open files, and requests orderly guest shutdown. It restores baseline XML only after QEMU is confirmed stopped and no helper has any run-file open. If shutdown or reattachment fails, leave the guest running and quarantine all state; do not force-stop it or discard the overlay.

8. **Use an independent verifier and cleanup last.** A separate verifier process, with no coordinator memory or write handle, checks exact inactive XML, absence of the selected QEMU PID and target-file FDs, every full disk-chain byte stream and metadata item, every inventoried persistent state stream against its recovery copy, and directory membership/ownership. Compare using separately opened read-only paths/descriptors and record hashes plus byte-for-byte results. Only after an all-pass receipt may the guardian delete exact run objects, remove retention markers, and release leases/lock. Any disagreement leaves the evidence and gate in place for reviewed recovery.

## Impact, rollback, and qualification

The recommended fence temporarily interrupts all libvirt client connections and can abort management operations across the host. It should run only after unrelated libvirt jobs are terminal. The builder guest itself may remain running; the old and new daemon generations must reconcile it without changing its disk or domain XML. A libvirtd QEMU hook runs on restart/reattach and a failing hook can kill an existing QEMU process, so hook bytes and behavior are a go/no-go prerequisite. The selected VM should execute only from a private overlay and private NVRAM/TPM copies. No force-kill of any guest is in scope.

Pre-baseline rollback restores only the exact selected-domain and cold-alias XMLs from pinned receipts, leaves original data objects untouched, removes only candidate-created objects whose inode/object identity is still exact, and verifies old XML and file hashes independently. After a libvirt fence or any ambiguous API result, do not roll back by guess; retain state and reconcile first. After guest start, the only safe rollback is orderly shutdown, exact XML restoration, full independent comparison, and cleanup last. The disk-chain copy has a real storage cost of at least the full selected chain plus private overlay and state copies; free space and destination filesystem semantics must be read-only captured before review.

Before use on the product VM, qualify this exact sequence on a disposable domain using the same daemon package, service-unit behavior, filesystem type, storage path permissions, QEMU identity, systemd FDStore, and lease policy. Exercise accepted API calls at each transaction phase, old-daemon termination, worker loss during an active guest, supervisor restart, QEMU hook success/failure, helper persistence, active QEMU jobs, manager restart, and final full-stream verification. Product use remains unqualified until a separate independent review confirms both normal completion and owner-loss recovery.

3. For the active `libvirtd` generation, capture process tree, cgroup membership, child/helper executables/arguments, and open FDs to selected sources, state, and run paths. Establish whether QEMU runs outside `libvirtd.service`'s cgroup and whether any helper survives `KillMode=process`; do not terminate anything to test this.
4. Capture exact QEMU hook inventory/bytes and the deployed package version/build identity. The service layout receipt omits the running hook behavior and does not prove reattachment will preserve QEMU.
5. Capture owner/group/mode/ACL and stable device/inode metadata for every source-path ancestor and selected object, plus the storage-pool references, destination filesystem, available capacity, and QEMU's required read/traverse/write identity. The known requester-writable ancestors remain unresolved until a protected per-VM chain path is reviewed.
6. If anyone still proposes the thread-pool counter route, capture the exact distro v12.7 source for `virThreadPoolSetParameters`, all `virNetServerGetThreadPoolParameters` paths, dispatch queueing/completion, and admin/server threadpool separation. The installed header and public API docs are insufficient to assert that setting priority workers to zero waits. This design does not depend on such a claim.

## Primary sources

- [libvirt RPC server internals](https://libvirt.org/kbase/internals/rpc.html): requests enter a worker queue; one client can have parallel calls.
- [libvirt Admin API reference](https://libvirt.org/html/libvirt-libvirt-admin.html): `virAdmClientClose` is a forceful connection close; thread-pool Get/Set descriptions make no drain promise and the getter documentation omits `jobQueueDepth`.
- [virt-admin thread-pool commands](https://libvirt.org/manpages/virt-admin.html): current ordinary/priority workers and queue depth are reported as current values; setting parameters changes thread-pool attributes.
- [upstream thread-pool stop/drain change](https://lists.libvirt.org/archives/list/devel%40lists.libvirt.org/thread/XYA343XSCGOEJLIVPYPJA3TOPHHPQXAW/?sort=date): distinguishes a stop signal from a drain that waits for worker termination. This is implementation-history evidence, not a substitute for capturing the installed 12.7 source.
- [libvirtd daemon](https://www.libvirt.org/manpages/libvirtd.html): running guests survive daemon restart; clients should expect management interruptions.
- [QEMU daemon restart guidance](https://libvirt.org/kbase/qemu-core-dump.html) and [QEMU job/thread notes](https://www.libvirt.org/kbase/internals/qemu-threads.html): long-running jobs may be interrupted, while asynchronous jobs can outlive the initiating API call.
- [QEMU hook behavior](https://libvirt.org/hooks.html): a QEMU hook failure during daemon reconnect can kill an existing QEMU process.

The official web documentation was checked on 2026-10-11. Exact deployed source behavior of the 12.7 setter was not locally captured; accordingly, no part of the recommended barrier relies on that setter or on counter polling.
