## Correction

`Write-HarnessGateKeeperReadyReceipt` still rejects any noncanonical run token, PID/start identity, job names, or final path before filesystem work. It serializes the same receipt fields and computes the digest from those exact UTF-8 bytes. It then creates a random same-directory staging leaf using `FileMode.CreateNew`, `FileAccess.Write`, and `FileShare.None`; writes the complete payload; calls `Flush($true)`; closes the stream; and publishes with a same-directory `File.Move` to the deterministic final path. The target is not deleted or replaced. A target collision fails closed, and no fallback copies bytes into the final path.

`HarnessWindowsGateLeaseKeeper.ps1` changes only the comment above its existing sticky-retention assignment. The comment now accurately says retention is armed before staging begins and remains active on any failure until explicit CANCEL recovery. This small source change is needed because R20’s comment referred to a post-publication hash operation that no longer exists. The assignment remains before the writer call; the catch path still retains both exact job handles. Temporary cleanup is attempted only after this invocation successfully created that staging name. Cleanup failure cannot create or validate the final ready path; it leaves the run fail-closed with keeper retention armed.

The RUN consumer and VERIFY/CANCEL receipt checks are unchanged. They poll and open only the deterministic final path and continue to verify its full schema, run token, process PID and creation FILETIME, both exact job names, successful main-job query marker, keeper membership marker, and durable hash. Staging names are never treated as readiness evidence.

The .NET Framework API references document `Flush(Boolean)` support in .NET Framework 4.0+ and its disk-flush behavior, and document that `File.Move` without an overwrite option throws if the destination already exists: [FileStream.Flush(Boolean)](https://learn.microsoft.com/en-us/dotnet/api/system.io.filestream.flush?view=netframework-4.8.1), [File.Move](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.move?view=netframework-4.8.1). R21 uses a temporary leaf formed by appending to the already validated final path, so source and target are in the same directory. These references support API availability and no-overwrite behavior; they do not replace the required Windows runtime test of publication visibility and filesystem behavior.
