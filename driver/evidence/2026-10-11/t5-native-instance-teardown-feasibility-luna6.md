# T5 native per-instance teardown feasibility

Date: 2026-10-11  
Reviewed source: `7b106913`  
Scope: whether a preallocated native-open record can guarantee exact last-handle cleanup observation across Filter Manager instance teardown. No product code or VM state was changed.

## Verdict

**Forced per-instance teardown prevents guaranteed `IRP_MJ_CLEANUP` capture, so exact automatic close reconciliation is impossible for that edge. The owner-approved `AcceptedUnresolved` hold does cover it if the product keeps the registered unload callback's mandatory-service-stop prohibition: preserve the unresolved native record, veto any voluntary global unload while cleanup coverage is lost, and release the durable publication hold only on exact cleanup evidence or the qualified actual-OS-boot proof.** Ordinary close and service restart while the same instance remains live still support automatic exact reconciliation. This verdict depends on retaining `FLTFL_REGISTRATION_DO_NOT_SUPPORT_SERVICE_STOP` in every build that registers `FilterUnloadCallback`.

## Filter Manager boundary

Microsoft states that after `InstanceTeardownStartCallback` runs, the filter’s pre/post callbacks are not called for **new** I/O on that instance. Existing operations may finish, but a later app close can issue a new cleanup operation after that point. The teardown callback is `VOID`; its documented duties do not include refusing teardown or arranging continued I/O callbacks. `InstanceTeardownCompleteCallback` runs after outstanding I/O has completed or been drained, which is not proof that every application handle has reached last-handle cleanup. The callback’s reason can be volume dismount, internal error, manual detach, or filter unload ([PFLT_INSTANCE_TEARDOWN_CALLBACK](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nc-fltkernel-pflt_instance_teardown_callback), [loading and unloading a minifilter](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/loading-and-unloading)).

The registered `InstanceQueryTeardownCallback` can veto **manual** detach only; Microsoft says it is not called for automatic or mandatory detach, including volume dismount. The feature build already returns `STATUS_FLT_DO_NOT_DETACH` for manual detach (`Filter.c:759-797`), but that does not protect a forced dismount or internal-error teardown ([PFLT_INSTANCE_QUERY_TEARDOWN_CALLBACK](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nc-fltkernel-pflt_instance_query_teardown_callback)).

`FltObjectReference` prevents a filter, instance, or volume object from being freed; it does not re-enable callbacks after teardown starts ([FltObjectReference](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltobjectreference)). A stream-handle context cleanup callback is also not a last-app-handle receipt: Filter Manager deletes contexts when their object is deleted, when an instance is detached, and when the minifilter unloads; the callback is only a context-free hook ([context cleanup callback](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nc-fltkernel-pflt_context_cleanup_callback), [supporting minifilter contexts](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/managing-contexts)). No supported API in the reviewed design recovers the missing cleanup event from a retained `FILE_OBJECT` pointer, path, process exit, or later instance attachment.

## Distinct teardown cases

- **Manual per-volume detach:** veto it before teardown. `SafeUploadInstanceQueryTeardown` already does so in the feature build (`Filter.c:759-797`). This is the only per-instance case where the driver can refuse the detach.
- **Voluntary global filter unload:** the unload callback may refuse a non-mandatory request. Close admission and drain the native records while instance cleanup callbacks still operate, then call `FltUnregisterFilter`. The T5 design already requires this ordering (`T5-NATIVE-PUBLIC-OPENS.md:179-184`).
- **Mandatory global unload:** Microsoft documents that `FLTFL_REGISTRATION_DO_NOT_SUPPORT_SERVICE_STOP` makes mandatory unload requests fail without calling `FilterUnloadCallback`; the current prototype registers this flag (`Filter.c:184-191`). Keep this invariant in every build with an unload callback. A mandatory callback, if reached in a future configuration that removes the flag, cannot veto and cannot satisfy the approved local drain after cleanup coverage was lost; that configuration is unsupported by this design and requires a new owner decision. Under the approved flag, standard service-stop requests do not create that path. See [when FilterUnloadCallback is called](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/when-the-filterunloadcallback-routine-is-called) and [FLT_REGISTRATION](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/ns-fltkernel-_flt_registration).
- **OS shutdown:** Microsoft says `FilterUnloadCallback` is not called at system shutdown ([when FilterUnloadCallback is called](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/when-the-filterunloadcallback-routine-is-called)). The durable pre-CREATE intent must survive. Startup can use the previously reviewed qualified boot proof; shutdown notification itself is not a cleanup receipt.
- **Forced fixed-NTFS volume dismount or internal error:** this is the uncovered case. The query-veto callback does not run; the teardown-start callback marks the instance retiring, but subsequent app cleanup may bypass this minifilter instance. The current prototype callback only tombstones the instance and waits for pended attach transactions (`Filter.c:736-755`; `StageStream.c:2888-2938`). Current writer-registry teardown retires per-instance state and records drop counters (`StageWriters.c:1324-1366`, `3891-3898`); those counters and context deletion must not be reused as native cleanup evidence. A global native-open map can preserve the unresolved record but cannot observe the missing event.
- **Future removable-volume removal:** this review does not extend fixed-NTFS assumptions to removable devices. Keep that under T21’s separate lifetime design.

## Safe correction under the approved hold rule

At `InstanceTeardownStart`, fence new native CREATE/disposition work for that exact instance and mark every still-unresolved native record owned by it as **cleanup coverage lost** in local diagnostic metadata. Keep the same `AcceptedUnresolved` state and durable pre-CREATE reservation; do not add a protocol state. Do not wait inside teardown for future cleanup callbacks, because the callback contract does not provide them for new I/O after this point. Do not infer cleanup from instance reference release, context cleanup, dismount completion, or a new attachment.

On service reconnect, replay the unresolved record and the coverage-loss reason. Keep publication held. If exact authenticated cleanup evidence becomes available, use it; otherwise wait for the qualified actual-OS-boot branch from the boot-lifetime review. A same-boot service restart or instance reattach is not enough. A voluntary global unload must inspect this record and return `STATUS_FLT_DO_NOT_DETACH` before `FltUnregisterFilter`; otherwise the different-driver-instance boot proof would be unsound. The T5 design already makes late attachment untrusted until reboot (`Context.c:341-374`) and says no automatic global-Unknown clearance is added (`T5-NATIVE-PUBLIC-OPENS.md:187-203`).

For the durable destination hold, the failure mode is technically fail-closed: preserve the intent, identify the affected file in the tray, and keep later saves private until exact cleanup evidence or the qualified boot proof. That boot proof rejects a mere `BootId` increase: release requires a strictly greater unsigned counter, a different authenticated driver instance, and a complete current-driver replay with no live matching original record. Microsoft documents Fast Startup as restoring kernel and driver state, so the same `DriverInstanceId` must make the proof fail even if `BootId` increased ([system power states](https://learn.microsoft.com/en-us/windows/win32/power/system-power-states), [distinguishing Fast Startup from wake-from-hibernation](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/distinguishing-fast-startup-from-wake-from-hibernation)). A service restart, same-boot reload, or ordinary Fast Startup is not the required proof; do not present “shut down and power on” as equivalent to Windows **Restart**. The different-ID predicate also relies on the unresolved record remaining in the old driver’s global rundown map: with the mandatory-service-stop flag retained, a voluntary unload must veto while that record is unresolved, and the actual OS shutdown path does not call `FilterUnloadCallback`. Record the teardown reason and absence of a cleanup receipt in diagnostics; no manual journal edit or hold-clear action is appropriate.

This leaves one owner question before implementation: is the visible duration acceptable when forced per-volume teardown loses exact cleanup coverage, so the affected destination can remain held until the user performs a qualified Windows **Restart**? The recovery and tray behavior can be automatic after that restart; the user must not be told that service restart, app close, volume reattach, or Fast Startup is sufficient. The product must retain the mandatory-service-stop flag and the voluntary-unload veto for unresolved native records. If a future build removes that flag and can enter a mandatory unload callback with a coverage-lost record, the approved drain cannot complete and that build is unsupported. The normal mounted-instance close and same-driver service-start path remain automatic.

Microsoft distinguishes Fast Startup from a full restart: Fast Startup saves the kernel session, while a restart uses a full shutdown and boot ([system power states](https://learn.microsoft.com/en-us/windows/win32/power/system-power-states)).
