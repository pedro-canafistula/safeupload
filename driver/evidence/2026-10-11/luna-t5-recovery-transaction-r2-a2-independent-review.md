# Independent source review: T5 recovery transaction R2 A2

**Disposition: NO-GO for A2 source integration, host changes, runtime qualification, or product VM use.** The frozen source has sound transaction-ordering and normal-path restoration structure, but its restart reattachment path is contradicted by a corrected disposable control, and A2 still lacks an executable restart-to-full-restoration supervisor and proof that already-authorized libvirt work has drained. Source-only A3 work may proceed against these findings.

## Findings

**P1 — A2 cannot reattach source lease ownership after the setter process exits in the observed control.** `reattach_from_receipt()` requires the old setter PID to be gone, adopts only the FDStore-retained descriptors, and then requires one matching `/proc/locks` `ACTIVE READ` row bearing that old PID (`T5SourceLeaseGuard.py`, around lines 742–760). It does not establish a lease on a new open-file description or retarget lease-break notification to the restarted process. Its later `signal.signal(SIGIO, ...)` only installs a handler in that process; it does not change the lease's kernel signal owner.

The corrected, separately pinned owner-exit control at `output/review-candidates/m2-t5-lifecycle-recovery-transaction-r2-luna-a1/context/driver/evidence/2026-10-11/m2-t5-file-lease-owner-exit-control-a3-luna-verified2.py` reports `F_GETLEASE=F_RDLCK` after the child that set the lease exits, while the exact matching `/proc/locks` row disappears. Its adjacent `.stdout.txt` is separately pinned. The raw control parses major/minor as hexadecimal and inode as decimal, so this is not the earlier radix-matching mistake. Script SHA-256: `230120b1e3a60ed06124ef21b90b68f57073ec6fdaf82a41a27600f9bad03fde`; stdout SHA-256: `5a5196be4761434cd7f93acd23d67ffb1daf2789412c1609311070db2e82c182`. The control also observes a blocking writer remain blocked while the duplicated descriptor remains open, so it shows lease survival, not lease loss or writer admission.

A second post-capture disposable control at `output/review-candidates/m2-t5-lifecycle-recovery-transaction-r2-luna-a1/context/driver/evidence/2026-10-11/m2-t5-file-lease-new-owner-rebind-control-a3-luna.py` reports that a newly opened read-only descriptor can acquire a new read lease while the old FD remains leased; the `/proc/locks` row then names the new process, and a later nonblocking writer attempt signals that process. Its adjacent `.stdout.txt` is separately pinned. Script SHA-256: `498daf121e2fb3346b2e51e04015930e82210031bca8fc0a889a3faf6dd3ab93`; stdout SHA-256: `e426b7d9414eac883097b284483f794151a75aaef324bf41b4da3ea9609762de`. This suggests an A3 design can acquire, verify, and store new owner-bound leases before removing old FDStore references. It is not deployed systemd, selected-filesystem, or crash-recovery qualification. A2's specific old-PID row requirement fails in the observed owner-exit control; do not describe that as the kernel lease itself being lost.

The frozen `/proc/locks` parser is radix-correct: `_proc_locks_rows()` parses device major/minor in base 16 and inode in decimal. Its synthetic self-check row formats the same fields as the kernel example. The self-check covers synthetic ACTIVE and BREAKING rows while the setter lives, but not a real owner-exit/restart row. The [`proc_locks(5)` documentation](https://man7.org/linux/man-pages/man5/proc_locks.5.html) also warns that visibility is scoped to the PID namespace for which procfs was mounted. A2 still needs exact deployed-kernel and procfs-namespace qualification after any rebind implementation.

**P1 — the restart adapter is not a recovery executor.** A2 can describe/adopt source descriptors, but has no executable entry point that reconstructs the coordinator's in-memory prepared context, resolves each persisted mutation phase, restores XML, compares original disk/NVRAM/TPM state to the required baseline, and safely completes or retains cleanup after process loss. The author note expressly records this gap and the absence of systemd manager restart/stop and boot-loss recovery qualification. FDStore is a plausible way to retain duplicate descriptors across a service restart, as the [systemd FDStore documentation](https://systemd.io/FILE_DESCRIPTOR_STORE/) describes, but it does not supply the missing recovery state machine or qualify manager and host failure modes.

**P1 — PREPARING closes future policy admission but does not drain already-authorized libvirt requests.** Root invocation takes the canonical lifecycle flock and publishes PREPARING before persisting the source-acquisition intent and acquiring the source set. This fixes the ordering gap recorded in the accepted A1 review. The code comment and author report correctly state that a request already accepted by libvirt may have passed the authorization gate before PREPARING. The candidate contains no drain, completion barrier, or equivalent proof that such a request cannot finish after the XML/source scan. This remains a separate integration blocker.

**P1 — the selected backing path currently fails A2's requester-write preflight.** `_verify_protected_source_filesystem()` checks requester UID 1000's effective mode-bit write access along each selected source path and refuses ACL-bearing components; it does not claim to block every privileged actor or every directory-entry operation. The A2-captured R1 independent review records that the observed `/mnt/storage` ancestors are UID-1000-writable and that strict preflight rejects that layout. The read lease pins an inode but does not protect its pathname's directory entries from rename/unlink. This is a concrete selected-path dependency to resolve through a reviewed transaction or a different verified mechanism; it is not a universal owner-permission rule. Keep the current path gate closed until resolved.

**P1 — A2 source results are not independent product-restoration evidence.** The normal source path has useful checks: a two-pass fixed-hash baseline for each disk before mutation; durable/readback-verified disk and XML checkpoints; private-state XML persisted before `defineXML`; run-bound XML persisted before overlay creation; then shutdown, exact original XML/state checks, post-run disk rehash, full-stream comparison of original NVRAM/TPM against recovery copies, private-copy deletion, and retention-marker removal last. The reports themselves set `WholeVMPass=false`, `AtomicSnapshotProven=false`, and `ExternalStartStopExcluded=false`. Those same-invocation observations do not independently qualify the whole VM or satisfy the requirement that every product run end with independently verified full baseline restoration. No product VM was started in this capture.

The zero lease-break-time dependency is described accurately by the upstream Linux implementation reviewed here: the linked [`fs/locks.c` source](https://code.googlesource.com/linux/torvalds/linux/+/68ff4a3ccda9f98c74f23c70c8c7c581f9eee931/fs/locks.c) treats a zero deadline as never expiring and computes a nonzero deadline only for positive values. This corrects a superficial reading of generic grace-period prose; I do **not** count zero as an A2 semantic reversal. The exact host kernel, lease-capable filesystem, fsync behavior, zero-timeout behavior, and service-manager restart remain unqualified dependencies, as A2 itself states. A pending `F_GETLEASE` target of `F_UNLCK` is also not by itself proof that a blocking writer was admitted; the owner-exit control's blocking-writer observation confirms the distinction.

## Boundary and conclusion

The exact cold `win10-debug2` alias exception is narrowly bound to its UUID, inactive XML digest, shutoff/crashed state, and sole shared-backing reference. The accepted canonical-flock ordering is reflected in A2: PREPARING is published before acquisition intent and source leases, and source acquisition intent precedes lease acquisition. Durable destination-pool and object intents precede their mutations. These are sound source-level properties; they do not resolve the restart, API-drain, selected-path, or end-to-end qualification findings above.

Keep A2 **NO-GO** for source integration, install/policy/sysctl/ACL/permission/daemon changes, libvirt operations, and VM execution. A3 should correct the lease reattach protocol while retaining old descriptors until every new owner-bound lease is verified and stored, and must provide restart-to-full-restore execution plus already-authorized RPC draining. Any selected host policy change requires review of its concrete transaction before final owner approval. The current host/source path and all product-run restoration claims remain unapproved and unqualified.
