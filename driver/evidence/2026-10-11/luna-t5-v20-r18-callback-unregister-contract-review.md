# R18 communication-port callback source-lifetime contract review

**Date:** 2026-10-11  
**Scope:** Microsoft primary API/documentation and official sample review for `PFLT_CONNECT_NOTIFY`, `PFLT_DISCONNECT_NOTIFY`, and `PFLT_MESSAGE_NOTIFY`; read-only inspection of frozen R18 teardown ordering.  
**Relation to prior report:** focused addendum. The earlier independent report remains immutable; this report refines its callback-source blocker after examining the combined documented contract and Microsoft samples.

## Disposition

The prior callback-source/code-image concern is **resolved at the documented architecture level**. The docs do not exclude communication-port notify routines from `FltUnregisterFilter`’s unqualified minifilter callback-unregistration guarantee. The communication overview explicitly classifies the connect, disconnect, and message routines supplied to `FltCreateCommunicationPort` as minifilter callback routines. The official unload sequence for communication ports closes the listener before `FltUnregisterFilter`, permits existing connections to persist until filter unload, and says Filter Manager closes client ports as part of unloading. Microsoft’s MiniSpy sample implements exactly that pattern: its unload routine closes the server port, calls `FltUnregisterFilter`, and only then frees callback-reachable state; its disconnect callback uses the still-live `MiniSpyData.Filter` to close the client port. That is the ordinary supported lifecycle, not an inference from local counters.

R18 follows that supported boundary and adds stricter state handling: it retires/closes the current client slot, closes the listener, waits for current callback/channel users, keeps callback-reachable objects resident across `FltUnregisterFilter`, then waits for its local EX rundown before freeing stage/policy/taint state. I found **no source-reachable ordering in the frozen R18 teardown path that leaves these callback pointers executable after their image/state lifetime ends**, assuming the documented generic unregister operation performs its stated callback unregistration.

The state/image distinction matters. `CommunicationCallbackRundown` protects callback-reachable driver state after the callback enters; `FltObjectReference` keeps the opaque Filter Manager object alive when it succeeds. Neither pins the executable image. The source barrier is the documented `FltUnregisterFilter` callback-unregistration operation. Microsoft documents that Filter Manager calls the unload callback *before* unloading the minifilter ([When the FilterUnloadCallback Routine Is Called](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/when-the-filterunloadcallback-routine-is-called)); therefore the image remains resident throughout R18’s post-unregister rundown wait and state release. If a callback is already in flight, its acquired local rundown keeps state resident until it returns. A new source dispatch after unregister is contrary to the general callback-unregistration lifecycle. Counts and rundown support this sequence, but are not substitutes for that API contract.

This is a source-architecture disposition only. It does not qualify Windows runtime behavior, compiler output, a matched pair, or cutover. Windows lifecycle testing remains required by the owner’s acceptance objective.

## Applicable Microsoft contract

The [FltCreateCommunicationPort DDI](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltcreatecommunicationport) takes a `PFLT_FILTER` plus Connect, Disconnect, and Message callback pointers. Its parameter documentation says Filter Manager calls Connect on a user connection, Disconnect when the user handle count reaches zero or the filter is about to unload, and Message when a user-mode message arrives.

The [communication overview](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/communication-between-user-mode-and-kernel-mode) states that the minifilter implements those three routines and passes their pointers to `FltCreateCommunicationPort`; its table identifies their types as `PFLT_CONNECT_NOTIFY`, `PFLT_DISCONNECT_NOTIFY`, and `PFLT_MESSAGE_NOTIFY`. It also says Filter Manager terminates existing connections when the minifilter unloads. This is explicit category evidence: these are minifilter callback routines registered against the filter, even though the pointer arguments are supplied through the port-creation DDI rather than members of `FLT_REGISTRATION`.

The [FltUnregisterFilter DDI](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltunregisterfilter) says the call unregisters “the minifilter driver’s callback routines,” removes registered contexts, and calls the instance teardown start/complete routines for each instance. Its introductory description says Filter Manager no longer calls the minifilter to process I/O. The separate [Unregistering the Minifilter](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/unregistering-the-minifilter) article describes callback routines as unregistered and explains that `FltUnregisterFilter` waits for outstanding rundown references on the opaque filter pointer. Neither source narrows the generic callback-unregistration statement to only callbacks stored in `FLT_REGISTRATION`, and neither says communication-port notify callbacks are excluded.

The listener/client distinction is important. [FltCloseCommunicationPort](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltclosecommunicationport) says closing the server listener prevents new connections but leaves existing connections unaffected. The dedicated [Closing the Communication Server Port](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/closing-the-communication-server-port) guidance says the unload callback must close that listener before calling `FltUnregisterFilter` to avoid a system hang, and that Filter Manager closes remaining client ports when the minifilter is unloaded. [FltCloseClientPort](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltcloseclientport) says minifilters normally call it from DisconnectNotify; Filter Manager invokes DisconnectNotify when the user handle count reaches zero or when the minifilter is about to unload.

Together, these statements form a documented lifecycle: stop new connections by closing the server listener; let existing client connections be retired explicitly or as part of filter unload; unregister the minifilter callback source; keep callback state alive through unregister; then release state. No word-for-word sentence naming the three callback typedefs inside `FltUnregisterFilter` is required to apply the general callback contract to callback routines the same documentation explicitly calls minifilter callback routines.

## Microsoft sample corroboration

Microsoft’s [MiniSpy sample](https://github.com/microsoft/Windows-driver-samples/blob/main/filesys/miniFilter/minispy/filter/minispy.c) provides a concrete supported order:

- `SpyDisconnect` calls `FltCloseClientPort(MiniSpyData.Filter, &MiniSpyData.ClientPort)` (`SpyDisconnect`, around lines 2573–2609).
- `SpyFilterUnload` calls `FltCloseCommunicationPort(MiniSpyData.ServerPort)`, then `FltUnregisterFilter(MiniSpyData.Filter)`, then empties the output buffer list and deletes the lookaside list (around lines 2614–2665).
- The sample does not pre-close the client port in `SpyFilterUnload`; its disconnect callback remains responsible for client cleanup as Filter Manager tears down the connection during filter unload. The callback uses `MiniSpyData.Filter`, and the unload routine frees related global resources only after unregister returns.

Microsoft’s [AvScan sample](https://github.com/microsoft/Windows-driver-samples/blob/main/filesys/miniFilter/avscan/filter/avscan.c) independently closes its three server listeners, calls `FltUnregisterFilter`, nulls the filter pointer, and deletes the scan-context resource (`AvUnload`, around lines 3400–3475). Its unload routine first marks the subsystem unloading and coordinates outstanding scans with user mode, showing that an application may add its own work quiescence before entering the same port-close/unregister boundary.

The samples are corroboration, not a replacement for the DDI contract. In combination with the generic unregister statement and explicit callback classification, they demonstrate the expected supported design rather than merely showing a test that happened not to race.

## R18 order checked against that contract

The frozen source is `output/review-candidates/m2-t5-driver-wire-v20-r18-root-a1/src`; the root 26-input capture SHA-256 is `f47075cfce996c87b7a51c8080621b47bdc7bc731ff3cb4dc02dc6d055e17c2d`. The exact capture and per-file source pins are recorded in the earlier independent report. I inspected the relevant ordering in frozen `Communication.c` and `Filter.c`.

`SafeUploadCloseCommunicationPort` sets permanent connection-closing state, revokes the exact current cookie/generation, closes the shared client slot through `FltCloseClientPort`, closes the server listener through `FltCloseCommunicationPort`, then waits for connection uses and entered control callbacks (`Communication.c:425-496`). The close helper drops `SafeUploadConnectionTransitionLock` around `FltCloseClientPort` because DisconnectNotify may run synchronously; the retired-cookie path prevents that callback from taking ownership of or closing a replacement slot (`Communication.c:1073-1120, 1450-1512`). It also performs callback waits after the close operations, so the client/listener handles are not treated as callback-source proof.

After successful feature preparation and fence commit, `FilterUnload` closes communication and drains the send-channel rundown, joins stage workers, releases paging/backing and instance references, then calls `FltUnregisterFilter` (`Filter.c:517-565`). Crucially, it retains `SafeUploadData.Filter`, the EX callback rundown, stage state, and policy/taint storage until unregister has returned and `ExWaitForRundownProtectionRelease(&SafeUploadData.CommunicationCallbackRundown)` has completed (`Filter.c:557-578`). A DisconnectNotify callback that Filter Manager delivers during unregister can still acquire the open local rundown and use resident state. The EX rundown wait drains any callback that acquired it; after the rundown closes, a later callback entry fails at that first shared-state guard and returns. The driver image remains loaded until the unload callback itself returns. The code then clears the filter pointer and frees stage/policy/taint state. This divides responsibility correctly: Filter Manager unregisters the callback source; driver rundown protects callback state while in flight.

The same boundary appears in DriverEntry failure cleanup: the listener is closed and communication users drained before workers/instance refs are released and `FltUnregisterFilter` runs; callback rundown and state release follow unregister (`Filter.c:350-387`). The process-exit callback is independent: `StageFree` first closes stage admission under `StageListLock`, and `SafeUploadFreeTaint` later unregisters the process notification before deleting its table/lock (`StageStream.c:7370-7394`; `Taint.c:185-230`). That separate registration does not participate in the port-callback contract.

I found no exact unsafe ordering requiring a separate callback-type-specific API sentence. A contrary source conclusion would require a basis that the generic phrase “minifilter driver’s callback routines” excludes callbacks explicitly identified by Microsoft as minifilter callback routines and registered on the `PFLT_FILTER`, or an authoritative statement that unregister may return while those callback pointers remain newly dispatchable. The reviewed primary sources and official examples provide neither. Counts and local rundown alone would not close this question; the documented unregister lifecycle does.

## Result

For the narrow callback-source question: **GO on the ordinary documented API interpretation; no callback-specific architecture-confirmation gate remains.** The previous report’s callback-source NO-GO was conservative; this focused review revises that single sub-disposition. The earlier report remains unchanged and immutable.
