# R19 keeper-retention correction design

R19 is a fresh candidate copied byte-for-byte from the root-frozen R18 63-path source tree. The complete R18 independent report is `driver/evidence/2026-10-11/luna-t5-harness-windows-gate-r18-independent-review.md`, SHA-256 `8d2eb7dcf8af5d4e8533a00b789b4f03679541aaeb399422906da0f17077e3fb`. R18's source disposition is NO_GO for three Windows PowerShell 5.1 static-call syntax errors and one keeper handle-retention defect. R18 remains unchanged.

The three parser corrections only add method-call parentheses around `CreateKillOnCloseJob` in the remote runner and lifecycle fixture. The manifest's four affected pins (runner, keeper, fixture, and local client) are recomputed from the candidate bytes. The client self-check's source assertion is updated to the corrected fixture syntax.

The keeper arms `$retainHandlesForCancel` after it has checked the exact inherited job handles, job membership, durable run token, keeper path, and persisted PID/creation FILETIME, but **before** it creates or flushes the readiness receipt. This ordering covers the race where the receipt becomes readable while the keeper is still returning from its own hash operation. The keeper does not treat receipt visibility as parent acknowledgement. The existing RUN handshake independently parses and hashes the receipt against the exact token, keeper PID/start FILETIME, and deterministic job names; only after that function returns does RUN persist `KEEPER_READY`, before worker creation.

Before the retention flag is armed, validation failures can exit and close the child's inherited handles because RUN remains inside its startup mutex and still holds its own named-job and keeper-process handles. RUN's bounded readiness/error path terminates the exact jobs and waits on its retained process handles. If RUN itself disappears before that recovery completes, incomplete state or a missing job remains UNKNOWN; neither absence nor elapsed time is turned into a terminal receipt.

After arming, any exception from readiness-file creation/hash, deadline termination, drain, active-count query, or exact PID-list query emits at most one bounded stderr line and enters a one-second thread sleep loop. The loop performs no query retries, output writes, or cleanup. Both inherited job handles remain open; the sticky flag prevents `finally` from closing them. The existing CANCEL control opens the deterministic main and keeper jobs, terminates the held keeper job and exact keeper process, and requires zero active count plus an empty exact PID list for both held jobs before it can write a terminal record. Forced process/job termination closes the keeper's handles through OS process teardown.

Only a successful final pair of main-job observations—active count zero and exact process-ID list empty—clears the flag and allows ordinary `finally` cleanup. The 3600-second stopwatch initiates actual termination and drain; it is never terminal proof. If a query never recovers, the keeper may remain alive indefinitely until a real CANCEL. That retained resource is an explicit fail-closed outcome, not a bounded-lifetime claim.

R19 does not modify the native protocol, coordinator, actor, service, transport, shell, or the 33 closed execution-source inputs. Offline tests check the 88-assertion client control and use disposable copies to confirm rejection of both reverted static calls, a removed keeper-retention branch, and an unconditional cleanup guard. These checks are source controls only; they do not run PowerShell or prove Windows behavior.
