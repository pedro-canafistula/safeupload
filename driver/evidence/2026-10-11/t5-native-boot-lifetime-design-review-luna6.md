# T5 native boot-lifetime review

Date: 2026-10-11
Scope: product-security feasibility of native `FILE_DELETE_ON_CLOSE` recovery using the journal-only `AcceptedUnresolved` state. No product code, VM, or host state was changed.

## Verdict

**BLOCKED as currently implemented in `f87cc7a2`. The corrected two-branch proof is feasible and can satisfy automatic close/start recovery once its provenance checks are enforced at the journal boundary.** The current greater-`BootId` shortcut must not ship: `ReconcileNativeDeleteOnCloseAsync` accepts it without checking a different driver instance or a complete native-record replay (`StagedDestinationCommitJournal.cs:393-417`). Its test explicitly resolves with a greater counter and no cleanup evidence (`StagedDestinationCommitJournalTests.cs:108-129`).

Microsoft documents `KUSER_SHARED_DATA.BootId` as an `ULONG` boot sequence “incremented for each boot attempt by the OS loader,” not as a unique cold-boot identifier or a guarantee of persistence, non-wrap, or monotonicity across restored images ([KUSER_SHARED_DATA](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-kuser_shared_data)). Windows hibernation restores memory and drivers to their prior state; Fast Startup saves and reloads the kernel and loaded drivers ([system power states](https://learn.microsoft.com/en-us/windows/win32/power/system-power-states), [distinguishing Fast Startup from wake-from-hibernation](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/distinguishing-fast-startup-from-wake-from-hibernation)). Therefore a larger counter alone cannot establish that a recorded application object is gone.

## Required proof rule

Keep the single `AcceptedUnresolved` state. Permit automatic downgrade to the existing `Admitted + NativeOnClose` scheduled intent only after anchored-parent identity reconciliation and either:

1. **Exact cleanup:** an authenticated receipt replayed from the current driver’s preallocated record for the same original `TargetFileObject`, binding, and operation ID; or
2. **Old driver lifetime ended:** a strictly greater unsigned `BootId`, a current authenticated driver instance different from the binding’s original instance, and a complete, authenticated, reconciled snapshot of native-open records for that current instance that contains no live record matching the original native operation/object. Gate publication on completion of that snapshot; a partial, stale, or unbound replay is not “no live record.”

`StagedNativeLastCleanupReceipt` currently carries only a binding and operation ID; value equality is not authentication. The dispatcher must construct this input only from the authenticated live driver channel/replay and bind replay provenance to the current driver instance and current connection epoch. Likewise, `ReconcileNativeDeleteOnCloseAsync` needs the verified current-instance/replay result as required input or an unforgeable internal token; it must not remain callable with just a counter, optional receipt, and directory observation. The `DriverInstanceId` is generated at driver initialization (`StageStream.c:5866-5880`) and is a useful epoch discriminator, but it does not itself prove an OS reboot or object cleanup.

After either proof, reconcile the anchored name, then remove only the exceptional barrier by changing `AcceptedUnresolved` to `Admitted` (or `Superseded` for the exact durable newer publication). Preserve the native-on-close kind and generation floor. This is not a cleanup ACK and must not become `Complete` or `Canceled`; NTFS still controls pending-link deletion and publication may need automatic retry. The current code already retains the floor on downgrade (`StagedDestinationCommitJournal.cs:421-429`, `647-650`).

## Lifetime cases and limits

- **Service restart with the same live driver:** replay the exact live/cleaned records. A live matching record keeps the hold. A recorded last-handle cleanup can take branch 1. If replay is incomplete, retain the hold. Do not infer cleanup from process exit, pathname, connection epoch, or handle duplication. Microsoft’s cleanup contract marks the last application handle; outstanding section or cache references can remain ([IRP_MJ_CLEANUP](https://learn.microsoft.com/en-us/previous-versions/windows/drivers/ifs/irp-mj-cleanup)).
- **Lost close notification / post-CREATE context-attach failure:** the pre-CREATE nonpaged record must already be registered against the exact original file object and must record cleanup independently of the optional stream-handle context, as the design requires (`T5-NATIVE-PUBLIC-OPENS.md:117-129`). A service crash before persisting that event is recoverable when the same driver replays its map. If the record or replay is missing, do not invent a cleanup receipt; wait for branch 2 or retain the hold. Registration/allocation failure must prevent forwarding CREATE. A failed post-bind after successful NTFS CREATE stays `AcceptedUnresolved` (`StagedDestinationCommitJournal.cs:365-388`).
- **Hibernation and Fast Startup:** preserve driver-instance identity and every live fallback record across resume. A changed `BootId` with the same driver instance never takes branch 2; a live record remains a hold. Resume must not clear or rebuild the map as empty. Windows describes hibernation as restoring drivers and services rather than restarting them, so this rule covers both ordinary resume and Fast Startup.
- **Rollback and wrap:** store and compare the field as `uint`; use a plain strict `current > original` check only as one conjunct. Equal, lower, wrapped, absent, or inconsistent values cannot prove lifetime end and must fail closed to the exact-cleanup route or a later qualified boot. Do not use signed comparison, wall-clock time, or wrap-adjusted ordering to release a hold. Microsoft’s definition does not promise more than increment-per-loader-attempt.
- **Cold OS restart:** a new driver instance plus strictly greater `BootId` plus complete replay with no matching live record is a safe automatic lifetime proof, followed by exact parent enumeration. It releases the exceptional SafeUpload hold while preserving the native scheduled intent and retry behavior.
- **Teardown prerequisite:** branch 2 is sound only if the approved `T5-DELETES.md` §7 local drain is implemented for these records: fence new native opens, keep cleanup callbacks operating, and do not unregister until every tracked application object reaches last-handle cleanup and local operation holds drain. The driver must not wait for service acknowledgement. A new instance’s empty map is not a substitute for that drain.
- **Same-boot driver unload/reload:** the proposed boot branch intentionally cannot release because `BootId` is not greater. The already-approved late-attach gate remains non-Ready until a real OS boot. If the owner instead requires same-boot reload to release without a service-authenticated cleanup receipt, this design cannot prove it from a new instance’s empty volatile map; that requires a separately approved durable unload/drain receipt or a user-visible indefinite hold. Do not treat a changed driver GUID as equivalent evidence.

This construction satisfies automatic resolution after last-handle cleanup while the original driver survives, service reconnection/restart, and a later qualified OS boot. An unresolved row may remain held after an unacknowledged same-boot driver teardown until that later boot; that is the existing fail-closed late-attach behavior, not a cleanup fact. The real startup path currently does not call this reconciliation: `RecoverStagingSubsystem` recovers transfer-journal work (`MinifilterInterceptor.cs:1313-1342`), and the design itself says startup/live dispatch wiring remains pending (`T5-NATIVE-PUBLIC-OPENS.md:150-155`).

The simpler cleanup-receipt-only rule is insufficient: a driver/service crash can destroy the only in-memory cleanup record before the service durably receives it, leaving no automatic way to clear the hold. The qualified boot branch is the minimal recovery proof for that case; neither branch needs another protocol state.
