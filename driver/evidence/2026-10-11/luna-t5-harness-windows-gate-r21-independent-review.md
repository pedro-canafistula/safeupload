## Source review

`Write-HarnessGateKeeperReadyReceipt` validates the nonzero keeper PID/start identity, exact deterministic job names, and exact deterministic final receipt path before filesystem work. It serializes the fixed ordered receipt once to UTF-8 bytes and computes the SHA-256 over those same bytes. It creates a random same-directory staging path using `FileMode.CreateNew`, write access, and `FileShare.None`; writes the payload; calls `Flush($true)`; closes the stream; then publishes with same-directory `File.Move` to the final path. There is no overwrite or copy fallback. If creation, write, flush, close, or move fails, the catch closes any open stream, attempts cleanup only when this call created the staging name, ignores cleanup errors, and rethrows. A cleanup failure cannot create or validate the final receipt.

The keeper sets `$retainHandlesForCancel = $true` immediately before calling the writer. That flag remains armed on publication or subsequent keeper failure, and the catch keeps the exact main-job and keeper-job handles open while it waits for explicit CANCEL. It is cleared only after termination and exact zero active-count/PID-list queries succeed. The final receipt can become visible to RUN before the writer returns, but retention is already armed at that point.

The RUN startup reader polls only the deterministic final receipt path, rejects non-plain/reparse files, parses the complete JSON, and checks the exact run token, keeper PID and start FILETIME, both exact job names, the successful main-job query marker, and keeper-membership marker before recording the digest. VERIFY/CANCEL reads only that same final path and checks its durable hash and tuple. Random staging names do not constitute consumer readiness.

The R21 manifest and shell pins match the changed protocol, keeper, and manifest bytes. The manifest closure and all execution-source records remain those of frozen R20. The pinned T5 self-check is still `dbc00a84c456b97f6903cfcb4ccc0ba37c5ff763fc6b67e83aab3e86e807245f`, so this candidate does not include the separately reviewed R16 coordinator correction or resolve its later fixture-shape failure. The full gate remains NO-GO pending correction, a new closed inventory, and its required validation.
