## Security conditions for implementation

1. **Private creation is creation, not evidence repair.** Supply the protected owner/SYSTEM/Administrators descriptor in the native create operation for a fresh private directory/file. Do not obtain a green result by changing an existing unsafe fixture/root/record. Preserve existing-root/file ACL, trusted-owner, reparse/single-link and inventory checks before allocator recovery. Production `requireProtectedParent` and SYSTEM identity checks must remain in their original order. An existing object or create collision must receive validation/refusal, never retroactive trust. Do not use this helper to create an unvalidated production ancestor chain.
2. **Default selection follows the consumer mode.** Legacy `LoadAsync` and `CreateDefault` retain 20 MiB/5 s; current staged loads and `CreateStagedDefault` receive 4096 MiB/900 s for omitted settings. The two explicit resource fields continue to override both modes, including previously persisted small values. Explicit JSON null/zero/negative is rejected rather than reclassified as omitted. A newly generated shared JSON must omit the two overrides. Effective resource values remain included in the existing policy-content fingerprint.
3. **A staged load cannot enlarge legacy fallback.** Cache a validated legacy mapping of the same trusted document even when only the staged interface loaded it. A subsequent rejected ACL may return this legacy view only through the legacy API. Staged current reads continue to propagate current-policy absence, ACL rejection, malformed JSON, invalid policy and provider failure; no fallback or stale default is introduced.
4. **Snapshot accounting follows the native readers.** Use an immutable construction-time budgeted flag. A no-budget snapshot may return the exact read-only `FileStream` duplicate as before; every budgeted reader must retain its reference before duplication, release only after its handle closes, and release on duplication failure. Owner disposal must close its native handle before dropping its reference. Do not choose untracked mode from the mutable lifetime field: a concurrent last close could clear that field. Preserve exact-object duplication, restricted native granted rights, delete-on-last-handle behavior, and existing worker/timeout accounting.

## Required verification and limits

- Keep the existing RN-012/RN-013 expectations and the exact native snapshot type/rights/lifetime assertions. Change the large-file fixtures to create fresh private child directories with product creation code; retain separate intentionally unsafe-root fixtures and assert byte-identical descriptors after rejection.
- Exercise native Windows broad parent inheritance, exact protected child directory/file ACLs and owner, grant/ledger creation, restart acceptance, existing unsafe root/file rejection, and original FileShare behavior. Check a create collision without normalizing the existing object. For snapshots, exercise budgeted owner-disposal/read overlap and final refund after the final reader; a failed duplicate must neither leak a reference nor release another reader's charge.
- Cover local and remote omitted/explicit policy fields in both APIs, generated JSON, invalid/null fields, changed effective fingerprints and staged-load-then-legacy-ACL-fallback. The legacy fallback cache must still satisfy the existing same-instance assertion for an originally loaded legacy policy.
- Linux local/shim controls may provide feedback. Actual Windows ACL/sharing and the complete Debug/Release feature user/SYSTEM four-leg matrix remain delivery conditions. Do not report a successful source/build review or diagnostic subset as a full matrix pass.
- The nine T11 first-use/retained-epoch cases and five strict metadata missing-parent cases remain outside this repair unless a concrete large-change cause is demonstrated. Preserve those production guards and list their exact failures/correct setup requirements for their owners. The currently failed matrix is not green.

The design preserves the owner-approved storage formulas, existing-install legacy guard/accounting, failure-only seal, exact cleanup/recovery authority and runtime enablement/readiness gates. It introduces no new kernel/import or destination-support claim. Final coherent source review remains pending.
