## Deletion ownership resolved in the revised diff

The first diff allowed both the worker and common lookup to call FltDeleteContext for one fenced context. That ownership race is corrected: the worker owns retirement deletion; the common lookup only waits and retries. [Microsoft's deletion contract](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/deleting-contexts) describes deletion for a context currently set for an object; [FltDeleteContext](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltdeletecontext) preserves the caller's reference and removes the association. The revised source avoids relying on repeated explicit deletion of the same association.

The revised source initializes a NotificationEvent before context publication. The ordinary-prune worker owns retirement deletion, with its context pin retained; after dropping RegistryLock and WriterLock, it deletes and signals. A common get that observes the permanent retired fence waits at PASSIVE with no Registry/Writer lock, then releases its pin and retries. An already-fenced worker performs delete and signal even if mandatory teardown begins afterward. No service response or caller action is needed to complete that signal. The current common-helper callers are post-CREATE paths; the retirement worker's quiescence/activation paths use direct FltGet and do not recursively call the waiting helper. Native Verifier must still test this lock-free wait against actual filesystem and Filter Manager scheduling.

The final common-get header and definition repeat PASSIVE SAL. StageRegistryGetBoundContext has a matching PASSIVE prototype/definition and PAGE placement. The unknown-writer helper now states PASSIVE at its prototype and definition; its only caller is the existing post-CREATE path. Its spin sections remain in a resident helper, while the wait occurs only in the pageable common getter outside those sections.

The existing explicit diagnostic delete site is also coordinated. InvalidateLifetime now returns a deletion claim only when it wins under WriterLock against both the permanent retired fence and another diagnostic claim. It publishes sticky global tracking loss regardless. If invalidation wins, ordinary retirement sees invalid state and refuses; if retirement wins, the diagnostic returns a conservative failure without a second delete. This resolves duplicate driver-issued deletion owners without treating explicit removal as natural Ended or attempting to control automatic Filter Manager teardown.

A detached witness's old entry references remain unchanged; the explicitly retired destructor excludes natural Ended and publishes sticky loss if it finds contradictory owned state.
