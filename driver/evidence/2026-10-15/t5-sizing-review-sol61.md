1. **High — replace per-transaction full-image writes. Verified.** [T5-RECEIPT-SIZING.md:154](driver/T5-RECEIPT-SIZING.md:154) specifies a 13,672,448-byte image; [the update protocol](driver/T5-RECEIPT-SIZING.md:164) rewrites it for every transaction. Even **one transaction per save writes 136.8 GB across 10,000 saves**, including selectors. Multiple transactions and semantic-store writes increase this. Host-write arithmetic is verified; latency and physical wear are unmeasured. [The existing checkpoint](agente/SafeUpload.Agent.Service/Interception/StagedMetadataCheckpointV30.cs:233) has the same amplification.

   **Required change:** make ordinary/amortized writes proportional to changed records/pages: bounded, preallocated checksummed WAL with transaction commit records and periodic checkpoints, or page COW with a transactional root map. Apply this requirement to semantic-checkpoint writes on the save path too. Preserve complete-transaction visibility, semantic-commit-before-projection ordering, acknowledged floors, and reader drain before reuse. Commit/checkpoint durability must precede acknowledgment/log reuse; ambiguous recovery must hold, never select independent records’ highest sequences or roll back acknowledged floors. Preserve fresh full-store integrity validation. Add crash/torn-write, replay-idempotence, log/page reuse, checkpoint-boundary and written-byte controls. [Microsoft’s flush guidance](https://learn.microsoft.com/en-us/windows/win32/fileio/flushing-system-buffered-i-o-data-to-disk) supports the required persistence ordering.

2. **Medium — cancellation handoff is underspecified. Inferred hazard, not a confirmed existing bug.** [Lines 63–66](driver/T5-RECEIPT-SIZING.md:63) require joining an “entered callback,” but cancellation can already be selected before callback entry. [`FltClearCancelCompletion`](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltclearcancelcompletion) also returns `STATUS_CANCELLED` when no routine was registered; that result alone cannot identify an expected callback. [`FltSetCancelCompletion`](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltsetcancelcompletion) supplies no synchronization.

   **Required change:** specify one stable lookup owner across waiter→admitted transaction, exactly-once registration/clear, one completion winner, and rundown covering selected-but-not-entered callbacks. Preserve original caller/subject ownership and the preoperation-return barrier. Add delayed-entry, duplicate-clear, timeout/admission, exit, disconnect and teardown races.

Identify which runnable progress path releases each saturated resource. Require FIFO participation by fresh fast paths, consistent multi-family ordering, and progress scheduling that cannot queue behind the fresh work it must unblock. Saturation/fault controls must demonstrate these properties at minimum and maximum profiles.

Test pauses around pin, comparison and user acquisition against Fence, reuse and mandatory teardown.
