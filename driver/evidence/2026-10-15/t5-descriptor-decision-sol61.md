**How many ordinary users could encounter this?**

**Documented:** creating a file without supplying security information is a normal Windows path. Windows assigns default security inherited from the containing directory. Thus “inherited NULL-input creation” describes ordinary default creation in an inheriting user folder; it does **not** mean creating a file with a NULL DACL that grants everyone access. Applications can supply explicit security or use different save/replace sequences. [Microsoft: file security](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights).

**Inferred:** refusing this shape could disrupt routine new-file saves and subsequent saves of normally inherited files in Documents, Desktop or Downloads on supported local NTFS storage. The moved-file shape is also legitimate: a native move can retain security inherited at the former location. Actual frequency depends on applications and folder configuration; **two failures among seven deliberately chosen descriptors is not a prevalence estimate**.

**Verified:** the current publication construction loses precisely `0x0400` in both cases, `0x8C04 → 0x8804`; owner, group and ordered ACL bytes remain equal. Adding `AUTO_INHERIT_REQ` reproduced both failures. These are builder **19045.6466** measurements, not qualification on target **19045.2965**. **What the bit changes—and what remains uncertain**

| Area | Documented behavior and implication |
|---|---|
| Meaning | `SE_DACL_AUTO_INHERITED` marks a DACL supporting Windows’ automatic-inheritance model. It is distinct from each entry’s `INHERITED_ACE` flag and from `SE_DACL_PROTECTED`, which prevents inherited modification. Losing it changes recorded inheritance state. It does not itself add or remove a permission entry. [Microsoft control definitions](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/security-descriptor-control). |
| Parent permission changes | Windows’ propagation APIs apply inheritable entries to existing descendants and impose the current inheritance model, setting auto-inherited markers on converted descriptors. Therefore, **the missing bit does not establish that future inheritance is disabled**. Conversion can also protect an ACL when reordering would change its meaning. Whether the two measured descriptors behave identically during later updates remains untested. [Automatic propagation](https://learn.microsoft.com/en-us/windows/win32/secauthz/automatic-propagation-of-inheritable-aces). |
| Explorer / `icacls` | `icacls`’ `(I)` describes an entry inherited from its parent; those entry flags survived. Similar entry displays are therefore **expected, not verified**. Explorer’s exact display and subsequent editing behavior also need observation. SDDL definitely exposes the difference: `D:AI…` becomes `D:…`, as the retained evidence shows. [icacls](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/icacls), [SDDL flags](https://learn.microsoft.com/en-us/windows/win32/secauthz/security-descriptor-string-format). |
| Backup / restore | Backups can include security information, so a descriptor-aware backup or audit can observe the missing marker. Microsoft does not promise that every restore path reproduces every control bit unchanged. Backup restoration requires its own security rights; it cannot supply caller authority for publication. Effects on particular backup tools are **unverified**. [BackupRead](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-backupread), [BackupWrite](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-backupwrite). |
| `SetNamedSecurityInfo` | This API propagates inheritable entries to existing children and places inherited entries after explicit entries. It accepts ACL components, rather than an arbitrary descriptor-control word. Calling it is a permission-management operation, not a guaranteed “restore this one bit” operation. DACL changes require caller ownership or `WRITE_DAC`. [API contract](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-setnamedsecurityinfow). |
| `TreeResetNamedSecurityInfo` | This explicitly resets security throughout a tree. `KeepExplicit=TRUE` retains explicit entries while replacing inherited entries; `FALSE` removes explicit entries too. DACL reset requires `READ_CONTROL` and `WRITE_DAC` on every affected object. Its result must be compared between the native and reconstructed files. [API contract](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-treeresetnamedsecurityinfow). |
| `ConvertToAutoInheritPrivateObjectSecurity` | It compares against the parent, classifies inherited entries, can reorder entries or set protection, and sets auto-inherited markers. Microsoft describes the returned descriptor as security-equivalent, but that is weaker than byte equality. It returns an allocated descriptor; its privilege-free conversion does not authorize writing that descriptor onto an NTFS object. [API contract](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-converttoautoinheritprivateobjectsecurity). |

The immediate evidence is reassuring about **unchanged permission entries**. It does not establish equivalence of every later ACL-management or restoration operation.

**Owner choices**

1. **Keep exact equality.** No metadata promise changes. Publication remains unavailable until an exact construction works; blocking inherited files would affect ordinary workflows, so this cannot be presented as a minor compatibility exclusion.
2. **Accept a narrowly bounded DACL-marker exception after controls.** Routine saves can proceed once the remaining gates pass. Permission entries remain exact, while descriptor audits/backups can report the missing marker. Later permission-management compatibility becomes an explicitly qualified limitation.
3. **Redesign publication around object preservation/native replacement.** May retain exact metadata for more existing files, but adds substantial work on authority, sharing, atomic visibility and recovery. Users wait longer for a complete save path.

**Recommend option 2**, preferring exact NULL-input inheritance wherever proved. Permit only the observed direction—expected `0x0400` set, stored bit clear—with every other byte equal. Preserve both raw descriptors in evidence; keep SACL `0x0800`, protection and request bits exact.

The residual risk is a later Windows or third-party ACL/restore operation distinguishing the descriptors despite unchanged current permission entries. That risk needs explicit owner acceptance and the finite controls above; the existing measurements do not justify calling the bit universally non-material.
