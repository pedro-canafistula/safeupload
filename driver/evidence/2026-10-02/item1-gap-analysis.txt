TOP TEN (ranked by exploitability; each probe is a proposal, not run)
1. Candidate-policy plain I/O window (LEAK; highest priority). Failing scenario: while a real policy push expands a scope to a new directory, an untainted process repeatedly creates/writes a single-link file there before the policy swap; current-policy checks let those bytes go to NTFS. PowerShell test: create outside-current-policy candidate directory/file path; run a tight Add-Type FileStream write loop while service pushes candidate policy; immediately hash with a fresh independent handle after acknowledgment. Expected: writes during transition fail or are staged, and physical hash stays baseline until an approved publication.
2. DELETE-only FILE_DELETE_ON_CLOSE (INTEGRITY). Scenario: open an existing protected file with DELETE|SYNCHRONIZE and FILE_DELETE_ON_CLOSE; StageAdmit treats it as nonwriter and falls through. PowerShell test: Add-Type CreateFile P/Invoke with desired access DELETE, share all, OPEN_EXISTING, FILE_DELETE_ON_CLOSE; close handle. Expected: create is denied and destination remains present/content-identical.
3. FSCTL_SET_ZERO_DATA (LEAK/INTEGRITY). Scenario: retain a physical read/write handle opened before filter attach, then zero a range after load. Test: Add-Type DeviceIoControl FSCTL_SET_ZERO_DATA over bytes 0..4095; fresh hash/read. Expected: IOCTL denied and bytes unchanged.
4. FSCTL_DUPLICATE_EXTENTS_TO_FILE (LEAK). Scenario: pre-open protected target writable and an unprotected source containing marker bytes; issue extents copy on target handle after load. Test: Add-Type DeviceIoControl with one extent and source handle. Expected: denied and independent destination bytes unchanged.
5. FSCTL_SET_REPARSE_POINT (INTEGRITY). Scenario: hold a write-capable handle to a protected empty directory before filter load, then install a junction/symlink reparse target after load. Test: Add-Type DeviceIoControl on a disposable protected directory; query reparse data and destination identity. Expected: denied and target/namespace unchanged.
6. PREPARE_MDL_WRITE / MDL_WRITE_COMPLETE pass-through (LEAK). Scenario: an unowned physical writable object reaches NTFS through a cached MDL-write path; no StagePhysicalMutation case runs. Test: Add-Type native I/O helper on a pre-attachment physical handle, record fresh target hash and verify the guest actually issued PREPARE_MDL_WRITE/complete (if not, result is inconclusive). Expected: operation denied or target bytes unchanged.
7. ADS writable map missed by scan (LEAK). Scenario: map `fixture.bin:payload` writable and dirty it before filter load; after load modify/flush. Test: Add-Type CreateFileMapping/MapViewOfFile on an ADS under the protected prefix, then fresh ADS read/hash. Expected: mapped flush refused and ADS bytes unchanged.
8. Reparse descendant skipped by scan (LEAK). Scenario: put a junction under the protected prefix to an outside directory containing a pre-existing writable map; load filter then dirty/flush the view. Test: New-Item Junction plus Add-Type mapping helper; fresh target observer. Expected: mapping/flush refused and target bytes unchanged.
9. Unresolved-name section admission (LEAK). Scenario: hold a physical writable FileId-opened handle before attachment, then create a writable mapping when FltGetFileNameInformation cannot resolve it; code explicitly allows the section on query failure. Test: Add-Type OpenFileById + mapping; sample `sectionNameUnresolved` and fresh bytes. Expected: section denied or section-pointer-fenced, with bytes unchanged; a counter increment plus changed hash fails.
10. Hard-link created during candidate-scope scan (LEAK). Scenario: map an outside file writable, loop creation of a hard link into a directory being added by policy, and write through the existing view during the scan. Test: PowerShell Add-Type CreateHardLink + mapped writer concurrent with real policy expansion; fresh physical read of new protected link. Expected: link/write blocked for the entire transition and bytes unchanged.

NOT WORTH FIXING NOW (for the physical-byte/namespace invariant)
- Physical QUERY_SECURITY/QUERY_EA/GET_REPARSE and query-open metadata expose the existing physical object only; owned views return NOT_SUPPORTED. They do not write staged bytes or alter the protected namespace. Keep them as compatibility/privacy questions, not a release blocker for byte isolation.
- Directory notifications do not synthesize virtual staged-name events, but stage writes/renames do not mutate the protected directory. This can leave an application/sync client without a virtual notification; it does not leak an unapproved staged name or bytes to it.
- Owned oplocks, hard-link creation, delete/disposition, ADS, security/EAs and unsupported SET_INFORMATION classes already fail closed with NOT_SUPPORTED/denial. Adding virtualization for these is not needed to preserve the current private stream; the physical FSCTL and delete-on-close gaps above are separate.
- FAST I/O for an owned FCB is disabled; QUERY_OPEN is disallowed for owned views. Physical query paths return metadata only. No separate compatibility work here outranks the missing physical mutation gates.

COULD NOT VERIFY
- No VM/build/Verifier run was made. The citations establish only the recorded probes; none test delete-on-close, most SET_INFORMATION classes, security/EAs, FSCTL mutation/oplock behavior, directory notifications, ADS/reparse writable maps, short names, late attachment, unresolved-name mapping or ordinary nonpaging writes during policy expansion.
- I did not verify the user-mode NTFS access rights/callback selection for every FSCTL or whether a PowerShell operation can force PREPARE_MDL_WRITE on this exact Win10 NTFS build. The proposed MDL probe is inconclusive unless the operation is independently observed.
- Cancellation after generated paging-I/O submission, short-name canonicalization, distinct processes opening the same protected pathname, and service-side publication binding to the captured physical file ID remain unverified. No source-based kernel crash path was found for the listed pass-through/NOT_SUPPORTED branches; that is not a crash qualification.
- The workspace already contained modified source and unrelated untracked artifacts before this file was created. They were not edited by this analysis.
