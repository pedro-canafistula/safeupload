RV4 W-ledger kernel observer adversarial review
Date: 2026-10-05
Reviewed draft: `/tmp/safeupload-rv4-w-ledger-20261005`, base `6174dfda841132a0544dc1d96717207fc2392842`.
Scope: full draft diff for Protocol.h, Stage.h, StageStream.c, StageWriters.c; implementation notes; canonical `driver/MVP-PLAN.md` and RV4 W fixture contract. Source-only. No build, VM, runtime, or edits to the draft/repository.

Disposition

The wrapper is sensibly bounded: fixed nonpaged ticket slots own the original W completion context and an extra entry reference; the normal post path captures `IoStatus`/`Information`/draining before retiring W; rename attachment carries the same wrapper; ring loss and outstanding tickets are intended to make trace disable/clear fail closed. These are useful design choices, but the trace-control/loss race below can erase a missed W_BEGIN, so the current draft cannot yet support a complete paired ledger. The status snapshot is also only partially coherent as documented, and exact correlation to a lower-filter IRP remains an evidence requirement.

Blocking finding: ticket-pool exhaustion can lose the loss record across disable/clear

At `driver/SafeUpload.Minifilter/StageWriters.c:2615-2658`, the begin path holds recorder rundown while reserving/recording a ticket. If the fixed 128-slot pool is full, the `ticket == NULL` branch first releases that rundown at line 2656 and only then calls `SafeUploadStageAdmissionTraceNoteLost(traceState)` at 2657. That helper reacquires rundown at `StageStream.c:254-259`. A concurrent disable/clear can set the trace off, drain rundown, see no outstanding ticket for this unwrapped W operation, observe no LostEntries delta, and clear/reset successfully before the delayed note tries to reacquire. `SafeUploadStageAdmissionTraceBegin` then rejects the old state (`StageStream.c:156-168`), leaving neither a W pair nor a persistent loss marker. This violates contract lines 22-24 and the disable/clear protection added at `StageStream.c:293-320`; the trial could look clean after a dropped begin.

Minimal fix: increment `LostEntries` while the original recorder permit is still held, then release that permit; or make the loss helper explicitly record under an already-held permit. Do not call a second helper that may fail to reacquire after control has closed the trace. Preserve the core W path's pass-through/accounting behavior. Add a deterministic control-interleaving test for “pool full -> release/clear starts -> loss note,” and require `STATUS_DEVICE_BUSY` plus nonzero loss or an otherwise explicit INCONCLUSIVE receipt. A source-only review cannot establish that race's runtime scheduling behavior or the pool-exhaustion branch on the target VM.

Related admission-window race to close or define

Core W accounting happens before the observer admission attempt: `StageWriters.c:2563-2611` increments the original W context, then reads trace state and tries `SafeUploadStageAdmissionTraceBegin` at 2613-2616. Disable/clear closes rundown and waits only for threads that already acquired it (`StageStream.c:297-302`). A callback that has already incremented W but has not yet acquired observer rundown can therefore lose the race to the off transition; its `Begin` fails and the code records no loss (`StageWriters.c:2613-2659`). If the intended window is defined by successful observer-rundown acquisition, this operation is outside the trace epoch and must not be used in a trial; the coordinator needs an explicit boundary proving no stimulus callback was already in this pre-rundown gap. If the intended epoch starts when W begin executes, acquire/hold observer rundown before changing W, or otherwise make the off transition account for callbacks already inside the W begin path. The existing comment that off-state plus drained recorder rundown closes admission for observer tickets is not sufficient for work that has not acquired rundown yet.

Status-page coherence is weaker than the contract's full listed snapshot

The new W status read itself is under `Entry->StateLock` with H, state, generation and identity (`StageWriters.c:5646-5653`), and the existing outer `RegistryChangeSequence` start/end retry (`:5630`, `:5683-5685`) helps catch intervening mutations. However `T`, `S`, `UnknownReasons`, name, opener PIDs and C are collected after the state lock is released (`:5654-5675`). The `STATUS_RETRY` can make the page as a whole retry if each such mutation advances the same change sequence, but no new proof was added that every field has that coverage; the draft notes call out only the locked H/W/state subset. Do not describe one entry as a fully coherent H/S/C/T/W/Unknown/name snapshot unless change-sequence coverage for all those fields is established. Minimal fix is either include the required fields under a compatible lock/snapshot protocol, or label each field's sampling semantics and make host qualification rely only on the coherent H/W/state/identity subset plus a successful page-wide sequence check. Verify with targeted source audit and mutation/race tests; no runtime evidence was available here.

Evidence and integration limits that remain

- `StageMutatingIoRefreshEntrySnapshot` sets exact registry identity only for entry-tag tokens; marker/spill tokens intentionally have no exact identity (`StageWriters.c:2620-2621`, `2646-2649`; notes “Snapshot meaning”). Such W events cannot prove an exact file-specific W01 row and must remain INCONCLUSIVE.
- `CallbackData` is an opaque pointer copied at begin and overwritten at post (`StageWriters.c:2629`, `2706`). TicketSequence pairs upper-filter records. The source does not prove that this address is stable/unique across SafeUpload and the separate lower filter or cannot be reused before host correlation. Do not use the pointer alone as cross-filter exact-IRP proof without target-build evidence; bind lower receipts to the exact FO/SOP plus operation parameters/offset/length and correlate under an observed same-request rule. The current trace does not add write offset/length/payload tag, so the lower fixture must provide and independently validate those fields for W01.
- The completion hook records status/Information and post/draining flags on the SafeUpload post callback (`StageStream.c:3564-3581`), which is the required upper-side evidence. It is not the lower filter's own post receipt and does not by itself prove lower completion ordering. This matches fixture-contract lines 30-34 and 40-42 only when paired with independent lower receipts and raw pre/post evidence.
- Rename/link wrapper transfer appears preserved in `StageStream.c:3383-3397` and `StageWriters.c:2805-2814`; post captures from the rename context and `CompleteRename` retires that same inner wrapper (`StageStream.c:3564-3570`, `StageWriters.c:1912-1925`). Pre-operation exits intentionally produce the pre-lower-retirement flag (`StageWriters.c:2777-2781`), which host qualification must reject for a held-lower row. Runtime testing is still needed for success, failure, cancellation, and draining variants.
- `Protocol.h` grows the trace entry and batch while keeping protocol version 18 (`Protocol.h:55`, 906-924, 1195-1232). Communication enforces exact output size (`Communication.c:752-755`), so an old Inspector should fail safely with size mismatch, but it cannot decode these records. The Inspector adapter is explicitly separate in the implementation notes and must be rebuilt from the same header before trial use.

Authority alignment and limits

The fixture contract asks for a bounded nonpaged paired W observer, actual post flags/status/Information, exact rename ticket transfer, explicit overflow/loss, and INCONCLUSIVE on gaps; it says loss of live proof must withhold promotion (main output contract lines 20-26, 30-42). The MVP plan says tracking loss only withholds promotion and never refuses I/O (`driver/MVP-PLAN.md:207-216`). This draft keeps instrumentation observe-only and does not appear to alter enforcement decisions. No compile/PREfast/WDK results were checked; the report does not establish IRQL correctness at runtime, rundown behavior under verifier, exact cross-filter callback identity, or Windows 10 19045.2965 qualification.
