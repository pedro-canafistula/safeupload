Scope and evidence
------------------
Read first: driver/MVP-PLAN.md; driver/evidence/2026-10-04/phase3-design-v1.txt;
driver/evidence/2026-10-04/registry-txf-run1-19-readout.txt;
driver/evidence/2026-10-04/s00-attempt1-7-readout.txt; and the available
2026-10-05 S01 boot evidence (driver/evidence/2026-10-05/s01-bugcheck-rollback.sh).
Then reviewed StageWriters.c, Policy.c, StageStream.c, Txf.c, BootPolicy.c,
Communication.c, and Filter.c, with StageAlias.c/StageProtocol.c consulted where
their call paths determine alias and ADS behavior.

The 2026-10-04 owner decisions treated the registry as a ledger, not a gate;
scoped Unknown to the narrowest identity; required rename loss to widen to the
instance; allowed pruning only after quiescence; and made the boot invariant
scope-only. The later cutoff decision supersedes the earlier design's
grandfathering caveat: after a scope-adding epoch swap, later paging writes must
not reach disk, and any post-cutoff dirt must prevent promotion.

The S01 artifact records the deterministic 0xEF / wininit exit 14001 failure for
the increments 3–5 build and describes early-boot I/O outside scope being refused
or broken. The checked-in artifact is a rollback script, not a dump or callback
stack, so it does not identify which callback caused that specific failure. The
code below contains concrete scope-blind refusal paths that can produce this
failure class; attribution of S01 to one of them remains unproven. Run 19 covers
increments 1–2 without trusted Free/promotion. S00 is explicitly inconclusive,
and the S01 boot failure prevents treating the VM evidence as a Phase 3 pass.

Findings (highest risk first)
----------------------------

P0-1 — Scope-blind physical mutation fallbacks can refuse unrelated boot I/O
Reachable by a standard user: Yes for ordinary writes/renames/selected FSCTLs
when the callback enters one of the stated fallback conditions; the recorded
wininit failure itself is a system boot path.

Evidence: StageStream.c:2634-2650 initializes the physical-mutation result to
STATUS_ACCESS_DENIED and immediately takes the denial path for any IRP at a
non-PASSIVE IRQL or with IoGetTopLevelIrp() non-NULL. It also denies a failed
name query. The same callback is used for every nonpaging write at
StageStream.c:3229-3232 and for other physical mutators at 3240-3265. The final
path at 2676-2681 always completes with ACCESS_DENIED unless status became
SUCCESS. StageExternalRename at 2698-2707 likewise reaches its default-deny
completion when IRQL/top-level/name resolution prevents it checking source and
destination policy. StageUnownedMutatingFsctl at 2897-2936 denies every selected
mutating FSCTL when classification, name, or alias resolution fails or the
request is paging/top-level/non-PASSIVE.

Failure scenario: BootPolicy contains a prefix only on volume C:. A write or
rename on a known, separate fixed volume D: arrives with a top-level IRP (or a
selected FSCTL on D: cannot resolve its name). These branches do not ask whether
D: can contain any configured scope; they return ACCESS_DENIED. A system boot
component can consequently fail on unrelated I/O. The same issue can deny a
standard user's unrelated file mutation later. On the same volume as a prefix,
an unresolved path may legitimately be “could be in scope”; the defect here is
that the code also refuses when the mounted volume itself rules that out.

Minimal fix: Use a cached, IRQL-safe volume-to-policy-scope result before each
unresolved refusal. Pass operations on volumes proven outside every current,
pending, and boot scope. On a possibly scoped volume, retain a refusal only
when the target remains unresolved as potentially in scope. Do not perform a
new volume-name filesystem query from a top-level/reentrant path.

P0-2 — Paging-write gate opens after the scope transition, allowing a mapped
write to reach disk and then be promoted
Reachable by a standard user: Yes, with a writable view/section opened before
the scope is added.

Evidence: Policy.c:847-869 applies candidate scope state and then clears the
finalizing state/reopens cutoff work. StageRegistryApplyPendingScope marks
matching entries Activating and queues the reclaim worker at StageWriters.c:3255-
3313. In the worker, StageRegistryActivationProcess sets CutoffStarted and
calls CcFlushCache before closing the paging gate (StageWriters.c:2477-2505).
SafeUploadStageWritersPagingWriteBegin does not test CutoffStarted: while the
entry is Activating it admits/increments an in-flight paging write whenever the
gate is still open (StageWriters.c:3185-3219). PagingWriteEnd marks dirt only if
the gate has closed or cutoff is complete (3222-3233).

Failure scenario: After the added scope is accepted and finalizing clears, a
standard user stores new bytes through a pre-existing writable mapping before
the asynchronous activation worker closes the gate. The paging write is
admitted; if it completes before gate closure, it is not marked
DirtyAfterCutoff. The subsequent cache/filter flush can put those bytes on disk.
After the user unmaps/closes and the ordinary H/S/C/T and cache checks pass, the
entry can become Protected. This violates the accepted epoch-swap cutoff and
can put unapproved bytes into a protected file.

Minimal fix: Make paging-write admission and the scope-adding epoch transition
share one atomic cutoff. Writes that start after that boundary must be denied or
make the entry permanently non-promotable even if they finish before the
worker's first flush/gate-close step. Never promote based on a flush that may
have included post-transition writes.

P0-3 — ADS writers lose their file/SOP history; an old ADS mapping bypasses a
later protected scope (and one ADS open can poison promotion)
Reachable by a standard user: Yes, for an ADS on a file the user can write.

Evidence: StageWriters.c:812-815 lets by-ID requests lose tracking, but the
nonservice mutating by-ID path is rejected earlier in StageStream.c:2524-2538;
that particular route is not a standard-user bypass. ADS follows a different
path: ReserveCreate detects ':' in the normalized path and jumps to
RefuseIdentity at StageWriters.c:824-826, then records instance Unknown and
returns with Required=FALSE at 914-929. StageDispatchCore proceeds without a
reservation when Required is false (StageStream.c:3147-3170). Section acquisition
records a slot, but associates a registry entry only when the SOP is already in
RegistrySopSlots (StageWriters.c:2903-2924). Scope expansion walks only
RegistryEntries (3255-3293). PagingWriteBegin returns “not denied” when no
activating registry SOP entry is found (3185-3219).

Failure scenario: Before policy expansion, a standard user opens an ADS for
write, creates a writable section, and maps it. The policy later adds the base
file's directory. There is no ADS entry for ApplyPendingScope to activate and
no SOP binding for PagingWriteBegin to gate. Stores through the old view reach
the ADS on disk although the base file is now in protected scope. Separately,
the successful ADS create itself sets sticky instance Unknown; this lets one
ordinary ADS open prevent future candidate entries on that instance from
promoting, a cheap standard-user denial of service.

Minimal fix: Preserve a bounded stable file-ID plus SOP record for every live
writer/section even when its stream name cannot be indexed. Join that record to
candidate scopes on expansion and gate its paging writes. If identity/path loss
prevents a safe join, keep the affected candidate Unknown and never infer that
an unrepresented writable section is free. Keep ADS loss file-scoped where the
file identity is available rather than poisoning the whole instance.

P0-4 — Hard-link aliases are absent from scope-expansion classification
Reachable by a standard user: Yes when the user can create a hard link in the
future destination directory before that directory is protected.

Evidence: For a link operation, StageExternalRename calls
SafeUploadStageWritersPrepareRename at StageStream.c:2728-2733. If no writer
entry exists yet for that file ID, PrepareRename returns success without
retaining the new alias (StageWriters.c:1080-1101). A later writer open through
another alias records that normalized name as the entry name. ApplyPendingScope
compares only that one retained name against the candidate prefix (3255-3293);
it does not query the file's aliases. The paging path then uses the SOP map and
does not invoke the direct-write alias scanner (StageStream.c:3229-3234;
StageWriters.c:3185-3219).

Failure scenario: Before adding policy, a user creates hard link B inside a
directory they can write, with its other name A outside that directory. The user
opens and maps A, so the writer registry records A. Policy later protects B's
directory. The entry does not become Activating because A is out of scope; the
existing mapping's paging writes bypass the name/alias checks and modify the
protected identity through B.

Minimal fix: Classify each candidate file identity against every current link
name during expansion (or retain aliases as part of the identity history).
Unknown alias enumeration must force an enforced Unknown/Activating state whose
paging writes cannot reach disk; do not treat one unscoped name as proof that
the identity has no protected alias.

P0-5 — Instance-level rename loss is not applied to stale entry names at the
next scope expansion
Reachable by a standard user: Conditional on a rename-tracking failure, such as
the bounded directory-rename record allocation failing under nonpaged-pool
pressure; the underlying directory rename is intentionally allowed to proceed.

Evidence: On a directory rename, failure to allocate the tracking record marks
only the instance Unknown and returns STATUS_SUCCESS (StageWriters.c:997-1019).
The caller ignores PrepareRename's status and leaves the already-computed rename
admission unchanged (StageStream.c:2728-2733). StageRegistryMarkUnknown records
instance state, not per-entry rename reasons (StageWriters.c:372-395). Later,
ApplyPendingScope classifies only each entry's retained name and its own
UnknownReasons bit (StageWriters.c:3261-3293); it never checks the instance's
rename-Unknown state when deciding whether a stale name could have moved.

Failure scenario: A user renames a directory containing an open/mapped file
from A to B while both names are outside current policy. The directory tracking
allocation fails, so the rename succeeds and existing file entries keep names
under A. A later policy adds B. The stale entries do not match and do not become
enforced. A still-live writable mapping can page writes to the newly protected
file without passing a name check.

Minimal fix: Persist an instance rename-loss generation and have expansion
treat every entry/section on that instance as name-unresolved for any candidate
scope that can match its volume; enforce those identities before clearing
finalization. Alternatively, ensure the rename is not committed until the
bounded rewrite is retained, while preserving the owner rule that ordinary
tracking loss alone must not cancel unrelated I/O.

P1-1 — Epoch failure/finalization fallback confuses “a scope exists somewhere”
with “this operation may touch the union”
Reachable by a standard user: Yes during finalization or an admission-token
allocation failure, for paging I/O on a fixed volume outside the configured
prefixes.

Evidence: For an untracked paging SOP, StageEpochOperationTouchesUnion uses
SafeUploadPolicyHasDestinationScopes(kind) at StageStream.c:3042-3058. Its
non-PASSIVE/top-level fallback does the same at 3060-3064. That helper returns
true for any configured prefix regardless of the current fixed volume
(Policy.c:1262-1290). The caller retries or denies when this helper reports a
match (StageStream.c:3347-3363).

Failure scenario: Only C:\SafeUpload is configured. An unresolved paging write
on known fixed volume D: arrives while policy finalization is in progress or
epoch-token allocation fails. The coarse helper returns true because a prefix
exists somewhere, so the out-of-scope operation is retried or access-denied.

Minimal fix: Use a cached per-volume scope possibility check, equivalent in
semantics to MayMatchVolume but safe for the callback's IRQL/top-level context.
An operation on a volume proven outside the current/pending/boot union must pass.

P1-2 — Prototype TxF gate hard-codes a path on every volume
Reachable by a standard user: Yes, for transacted mutation of that relative path
on a volume not covered by policy.

Evidence: StageTxfMatchesBootstrap compares only the volume-relative path to
"\\SafeUpload\\Escopo Monitorado" (Txf.c:32-50). StageTxfNameInScope applies
that result before consulting current/pending policy (75-80); the TxF rename/
link destination path does the same (180-184).

Failure scenario: With policy scoped only to C:, a standard user performs a
transacted write or rename under D:\SafeUpload\Escopo Monitorado. The
prototype-only bootstrap comparison returns true and refuses the operation
although the volume/path is outside scope. This contradicts the accepted rule
that ordinary TxF elsewhere stays available.

Minimal fix: Remove this bootstrap shortcut from runtime scope decisions, or
bind it to the actual boot-policy volume identity and active configured prefix.

Verified correct in the reviewed paths
--------------------------------------
- BootPolicy strictly validates record size/version/prefix slots and checks the
  Parameters and BootPolicy key ACLs for the expected SYSTEM owner and exact
  SYSTEM/TrustedInstaller allow entries before reading scopes (BootPolicy.c:109-
  138, 204-284, 340-367). The code does not infer a missing scope from a corrupt
  value; this follows the owner’s trust and boot-scope decisions.
- Standard-user mutating opens by file ID are rejected before the registry's
  by-ID tracking-loss branch (StageStream.c:2502-2538). This closes the tempting
  by-ID route; ADS and other successful untracked section routes remain finding
  P0-3.
- The successful-path promotion barrier checks writer/transaction/section
  counts, `MmDoesFileHaveUserWritableReferences`, SOP/cache-map emptiness,
  flush-valid data against EOF, current scope, and a final locked state recheck
  (StageWriters.c:2518-2585). The barrier is conservative after a correct
  cutoff; it does not repair the gate timing in P0-2.
- Pruning reopens by the 64-bit NTFS reference, verifies the full 128-bit file
  ID and volume serial, then rechecks live writers, transaction/rename/Unknown,
  paging activity, section slots, and SOP mapping before unlinking
  (StageWriters.c:2137-2170, 2076-2134). It releases history/map references
  outside the locks.
- Instance teardown detaches transaction and section/SOP associations before
  retiring entries, clears each entry's Instance/Volume pointers, and drops
  those Filter Manager references before FltpFreeInstance can wait on them
  (StageWriters.c:1872-1954, 639-678). In the reviewed retirement/prune paths I
  found no retained instance/volume reference past teardown and no double
  release.
- Activation's file-ID reopen and cache I/O occur without RegistryLock or
  PagingWriteLock held; the short SectionLock/PagingWriteLock regions are
  separate from filesystem/cache I/O (StageWriters.c:2256-2281, 2390-2455,
  2477-2513). The reviewed lock paths showed no SectionLock-to-RegistryLock
  nesting cycle and no wait while holding those spin locks.
- Communication-port connection requires a SYSTEM primary token, requests are
  bound to the accepted process ID, and policy/publication/override commands
  additionally require the agent service SID (Communication.c:316-337,
  615-704). A standard user cannot directly replace policy through the port.
- Fast I/O mutations are disallowed for retry as IRP I/O, and an acquired epoch
  token is retained through lower completion; paging-write accounting is
  released from the token path (StageStream.c:3345-3347, 3364-3403; Policy.c:
  265-280).

No P2-only finding was retained: the items above have concrete correctness,
security, or boot-availability consequences. This review did not build, execute,
modify source, or commit. The only intended new file is this report.
