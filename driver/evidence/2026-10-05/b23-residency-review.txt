Disposition
-----------
The b23 PE and matching PDB prove the comparator, cache matcher/query, rename-loss
advance helper, and spin-lock acquire/release helpers are all in nonpaged `.text`.
Signing did not alter any section's raw bytes between the signed feature driver and
its unsigned counterpart. The disassembly confirms the cache matcher calls the
comparator while the query takes/releases the lock around matching. This is compiled
placement evidence, not a live residency/paging test.

The b22 fault stack does not prove that StageAdmit entered at DISPATCH_LEVEL: the
scope-cache spinlock raises IRQL before the cache comparator.
The reported IRQL 2 is therefore the lock-held comparator IRQL. StageAdmit is only
called from the IRP_MJ_CREATE arm of StageDispatchCore, and Microsoft documents
minifilter pre-operation callbacks at PASSIVE_LEVEL or APC_LEVEL. Consequently,
FltGetInstanceContext and FltGetFileNameInformation (both <= APC_LEVEL) are within
their documented bounds on this callback path. Do not treat their lack of an explicit
guard here as a defect. No concrete >APC caller to StageAdmit or the volume-context
lookup was found.

Source-only placement and storage conclusions
----------------------------------------------
The b23 source manifest lists Policy.c hash
c70a58262eb3735aeedf2d7be9c0075f6e28c916489c58af69bb361839416538, matching this
checkout. In Policy.c, SafeUploadVolumeCachePathUnderPrefix is `__declspec(noinline)`
and is not placed in PAGE by the ALLOC_PRAGMA list. The explicit PAGE entries nearby
are policy update/initialization routines and SafeUploadPolicyMayMatchVolume; the
normal raised-IRQL path calls SafeUploadPolicyVolumeCacheQueryNoInline and its cache
matcher, neither of which is assigned to PAGE. The b23 WDK link command merges
`_TEXT` into `.text` and `_PAGE` into `PAGE`. The helper's source/default section
agrees with the exact PDB symbol map below.

The cache arrays and spin lock are static driver storage. Active and pending policy
prefixes, plus boot prefixes, are copied into fixed cache entries before publishing
the cache index under the lock (Policy.c:483-543). Per-instance volume names are
embedded in instance contexts allocated from NonPagedPool (Context.c:321-325,
356-367; Filter.h:264-269). SafeUploadPolicyMayMatchInstanceVolume retrieves the
context before the cache lock and releases it after the query (Policy.c:683-701).
FltGetInstanceContext is documented <= APC_LEVEL; FltReleaseContext permits
DISPATCH_LEVEL for a NonPagedPool context. The call is therefore valid in the
pre-operation callback's documented PASSIVE/APC range, while only the copied context
name is read under the elevated cache lock. The cache comparator itself makes
bounded reads and ASCII arithmetic and invokes no general RTL string function; its
compiled section/RVA and call edges are verified below.

Early-boot raised-IRQL finding
-----------------------------
The lock-held high-IRQL comparator is bounded and conservative: the valid volume name
is compared against cached current/pending/boot prefixes; malformed or unknown volume
identity is treated as potentially scoped according to cache flags/prefixes. ASCII
matching enforces a backslash component boundary, so HarddiskVolume3 does not cover
HarddiskVolume30. Non-ASCII code units yield "may match," which can overclassify but
does not claim OUTSIDE when Unicode case equivalence is unknown.

The prototype callback table registers all operations with flags 0
(Filter.c:135-159); the legacy write callback separately skips paging I/O (163-170).
However, paging I/O does not call StageAdmit: that function is reached only for
IRP_MJ_CREATE in StageDispatchCore (StageStream.c:3186-3197). The b22 captured stack contains
StageAdmit as an ancestor of the lock-held comparator fault;
the stack proves the comparator ran at DISPATCH, but says nothing about the
entry IRQL before the lock was acquired (b22 CPU1 analysis:100-109).

StageAdmit calls FltGetFileNameInformation at StageStream.c:2584 and, if successful,
FltParseFileNameInformation at 2601 before the read-only short-circuit at 2593. The
documented pre-operation range is PASSIVE/APC, and both name APIs allow <= APC_LEVEL,
so this is not an IRQL contract violation on the reachable callback path. References:
https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/writing-preoperation-callback-routines
https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltgetfilenameinformation
https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltparsefilenameinformation
https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltgetinstancecontext
https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltreleasecontext

Directory create and delete-on-close paths use the same name APIs, also within the
pre-operation callback. The TxF helper guards its own PASSIVE-only name-query path
and falls back to volume classification above PASSIVE (Txf.c:41-47, 89-90); this is
additional source evidence that the volume-cache query is the raised-IRQL fallback.

One distinct source question remains: general full-path policy matching calls
SafeUploadPathUnderPrefix -> RtlPrefixUnicodeString (Policy.c:398-419); Microsoft
documents that RTL routine at PASSIVE_LEVEL, while the policy matcher is annotated
<= APC_LEVEL (Policy.c:1762-1785). The general pre-operation documentation allows
APC_LEVEL callbacks, but this review did not establish whether the specific
IRP_MJ_CREATE route can enter StageAdmit at APC_LEVEL or reproduce a call there.
Keep this as an unqualified source-level question, separate from the proven b22
fault, whose caller was the scope-cache matcher under a spinlock. No new acceptance
or runtime claim is made about this adjacent general matcher.

The intended read/image decision is clear in source: on a failed name lookup, a
non-mutating create short-circuits to success (StageStream.c:2586-2599), and the
dispatch comment says the boot snapshot scopes mutation only (3467-3481). A read-only
create classified as non-mutating also does not acquire an admission epoch
(StageEpochOperation at 3076-3099). Since StageAdmit is a pre-operation callback,
the source/docs establish a maximum of APC_LEVEL rather than DISPATCH. Whether the
specific create path can execute at APC and then enter the PASSIVE-only general
matcher above remains unproved here; do not attribute that possibility to the b22
DISPATCH fault.

Paging source behavior is deliberately separate: `StageEpochOperation` covers only
mutating creates and writable-section creates; paging writes are not an epoch
operation. The touched-union helper explicitly bypasses IRP_PAGING_IO at 3112. In
StageDispatchCore, unowned IRP_MJ_WRITE paging requests skip the physical-mutation
gate at 3296-3315, and staged-stream paging requests use StageRoutePaging
(StageStream.c:1958-1964). SET_INFORMATION / SET_EA / SET_SECURITY paging requests
also pass through at 3324-3325 and 3371-3372. This is source-only evidence of the
no-new-volume-scope-paging-refusal intent, not VM proof of the full mapped-I/O
invariant. Staged-stream paging requests are separately routed through
StageRoutePaging and may be refused for a read-only staged stream or rundown failure
(StageStream.c:1845-1914); that is per-stream routing behavior, not the unresolved-name
volume-scope refusal.
