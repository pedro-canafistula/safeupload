Status: bounded source-only draft for independent kernel review. Not built, installed, or runtime-qualified.

Base worktree: `/tmp/safeupload-rv4-w-ledger-20261005`, HEAD `eb6f331133212588e4eddff216cacc1851e23482` (isolated W-ledger source). Existing untracked b29 build/log artifacts in that worktree were not modified by this task.

## Change

The feature-only instance context now retains one aligned 64-bit first-Unknown record: low 32 bits are the reason mask supplied by the first marking call, high 32 bits are its originating `__LINE__`. A single `InterlockedCompareExchange64` makes the reason/site pair indivisible and sticky for the context lifetime. Existing per-instance `RegistryUnknownReasons` continues to accumulate all reasons; the feature-only admission-volume status exports that existing mask together with the first pair. The Inspector prints `instanceRegistryUnknownReasons`, `firstUnknownReason`, and `firstUnknownSite` in feature output.

`StageRegistryMarkUnknown` and `StageRegistryMarkEntryUnknown` now capture the source call line through wrappers. Elevated-IRQL deferred work items carry the original source line through both instance and entry paths; the worker records the caller's site rather than its own line. `SafeUploadStageWritersTrackingLost` similarly captures its originating StageStream caller. No event queue or scan was added; the evidence is bounded per instance. No I/O denial, gate, taint, paging, retry, reset, or lost-tracking semantics changed. Normal build layout is preserved with `SAFEUPLOAD_STAGING_PROTOTYPE` guards around the context/protocol additions; admission status entry size remains 192 bytes normal and is 208 bytes feature-only. W ticket producer/parser records are untouched.

The feature admission JSON can now distinguish a cleanup reason (`SAFEUPLOAD_REGISTRY_UNKNOWN_CLEANUP`, `0x40`) and the exact pinned source callsite, including the two unmatched cleanup branches in `StageWriters.c` (no stream context and stream context/no writer node). It can also identify other instance loss classes. `firstUnknownSite` is a source-line number for this source pin and must be interpreted against the same retained source/PDB; it is not a stable cross-version ABI identifier.

## Limitations and validation

This establishes only a source-level way to identify the first reason/site that records Unknown on the next exact-source boot. It does not retroactively identify the b25 trigger, and no cause is assigned from the earlier boolean-only readiness output. It also does not prove a cause is benign or justify clearing sticky Unknown; any eventual disposition requires the retained first reason/site, same-source build provenance, new-boot readiness, and root/security review. The source line is useful only with the exact source pin.
