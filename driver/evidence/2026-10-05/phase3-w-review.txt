Verdict
-------

No P0 found. The new W ordering is sound for the ordinary tracked-writer paths reviewed, and no double-decrement, underflow path, or context lifetime defect was found. There is one P1 race in the new out-of-scope overflow-marker optimization: a live marker can be classified OUTSIDE while a tracked marker writer is already renaming/linking it, then allow same-instance promotion. Two P2 findings remain: the dynamic section spill list is unbounded, and the separately registered MDL fast-I/O write path bypasses W (the SOP cache check may cover it, but this source does not establish that barrier).

Findings
--------

P1 — A live overflow marker can be cached OUTSIDE during its in-flight rename/link

Standard-user reachability: Yes, conditional on filling the per-instance named and compact writer tiers (1,024 + 4,096 records; Protocol.h:288-293), keeping an overflow writer open, and concurrently renaming/linking that writer's stream into a protected scope while an activation scan runs.

Code path:

- A tracked overflow writer has a writer node with Entry == NULL. BeginMutatingIo increments its SOP slot's SpilledMutatingIoCount and invalidates ScopeClassification (StageWriters.c:2495-2602, especially 2575-2585 and 2513-2519).
- The existing tracked-writer rename/link is allowed by StageExternalRename's `TrackedWriter || ...` condition (StageStream.c:2772-2777). With no registry entry, PrepareRename returns without an entry rename context (StageWriters.c:1640-1648); the tagged marker context then reaches the generic post-operation end path.
- The activation worker can snapshot the marker after BeginMutatingIo has already incremented RegistrySopMapGeneration. It scans hard links and `StageRegistryStoreUnknownSopClassification` publishes OUTSIDE without checking that SpilledMutatingIoCount is zero (StageWriters.c:3141-3179, 3205-3287).
- `StageRegistryUnknownSopMarkersQuiescent` calls the stream-quiescence probe, which correctly returns false for a nonzero SpilledMutatingIoCount. However, the next condition only blocks when the marker is unknown or not outside: `!streamQuiescent && (!classificationKnown || !outside)` (StageWriters.c:3314-3344, particularly 3333-3338). A known-OUTSIDE result therefore lets the scan return quiescent while the rename/link is pending.
- The final promotion serialization compares the marker-map generation and the candidate's own marker counts; it does not recheck every unknown marker's current W count (StageWriters.c:4436-4475, 4516-4541). If the mutation began before the scan's starting generation, that generation remains stable during the scan and promotion can proceed while the tracked rename/link is still below the filter. EndMutatingIoMarker decrements the counter and queues a recheck but does not invalidate ScopeClassification (StageWriters.c:2639-2658). A later scan can reuse the stale OUTSIDE classification for the same policy generation.

This defeats the stated rule that a live overflow marker blocks promotion unless it is provably outside. It also leaves the stream without an entry-level W/H gate after it has moved into scope.

Minimal fix: Treat any marker with SpilledMutatingIoCount != 0 as blocking, even if its cached classification says OUTSIDE. Do not publish or accept an OUTSIDE classification while that count is nonzero. Keep the classification unresolved after W reaches zero so a fresh all-link/ADS scan runs before promotion. Preserve the final generation serialization to close a new mutation that starts after the scan.

P2 — Section spill records make nonpaged memory and spin-lock work unbounded

Standard-user reachability: Yes. The fixed section table is 64 slots (StageWriters.c:2706, 2744). Every acquire after it fills attempts a new nonpaged STAGE_SECTION_SPILL_RECORD allocation and may retain it until matching release or instance teardown (StageWriters.c:5540-5588, 5283-5326). The record path includes read-only acquisitions as well as writable ones so release pairing can distinguish them (2696-2704).

There is no spill-record count limit. A standard user can hold many outstanding section acquisitions/mappings, making SectionSpills grow beyond the fixed ledgers. The list is scanned while SectionLock is held by release matching, snapshots, and promotion checks (5623-5667, 5433-5479, 4448-4464); those scans have no fixed upper bound and can run at DISPATCH_LEVEL. This is a nonpaged-pool exhaustion and high-IRQL lock-latency path. When a spill allocation fails, the code does fail safe for promotion and returns success to lower acquisition (5570-5587); the risk is the successful, unlimited spill path.

Minimal fix: Bound spill records (preferably a small fixed pool). At the cap, mark the exact entry Unknown when identity is known, otherwise mark the instance Unknown, leave the acquire admitted, and stop trying to recover this capacity loss until reboot. Unknown is an acceptable capacity outcome under MVP-PLAN.md:391-398. This keeps the no-false-promotion and no-I/O-refusal guarantees while bounding memory and lock work.

P2 — MDL cached writes are registered but bypass W

Standard-user reachability: Yes, through cached writes on an existing writer file object.

Filter.c registers IRP_MJ_PREPARE_MDL_WRITE and IRP_MJ_MDL_WRITE_COMPLETE (157). StageDispatchCore has no cases for either major function and falls through to SUCCESS_NO_CALLBACK (StageStream.c:3163-3185, 3431-3434). The ordinary IRP_MJ_WRITE fast-I/O path is correctly disallowed before BeginMutatingIo (3275-3281), as are fast-I/O SET_INFORMATION, EA/security, and selected FSCTL paths (3303-3309, 3345-3354, 2957-2964). That does not cover these distinct major operations.

Microsoft documents PREPARE_MDL_WRITE as a fast-I/O cached write that bypasses the IRP write path, and says MDL-write completion marks the byte range for write. The source therefore does not count or pair this mutating path with W. Free(F) also checks SharedCacheMap/DataSectionObject, so this is a coverage/proof gap rather than a source-proven claim that the shared cache map can disappear before MDL completion.

Minimal fix: Disallow the fast-I/O PREPARE_MDL_WRITE and confirm it is reissued through a counted IRP_MJ_WRITE path, or add exact rundown from prepare through completion/abort. Do not treat a missing W ticket as covered until the SharedCacheMap lifetime through MDL_WRITE_COMPLETE is established on the target filesystem/OS.

References: Microsoft [FLT_PARAMETERS for IRP_MJ_PREPARE_MDL_WRITE](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/flt-parameters-for-irp-mj-prepare-mdl-write); [CcMdlWriteComplete](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ccmdlwritecomplete).

W accounting review
-------------------

Verified correct:

- For a registered writer node, BeginMutatingIo holds the stream-context WriterLock while it finds the exact FILE_OBJECT, takes an Entry reference, increments W under Entry.StateLock, and publishes the completion context (StageWriters.c:2543-2594). Cleanup removes the same writer node and decrements H while holding that same WriterLock (2323-2364). Thus a pre-operation that wins first increments W before cleanup can lower H; a cleanup that wins first removes the node before BeginMutatingIo can classify the request as tracked. The latter request goes through the direct name/alias gate.
- Promotion first gates the entry, then rechecks W under Entry.StateLock and serializes the state CAS with SectionLock and RegistrySopMapGeneration (StageWriters.c:4436-4475, 4516-4541). The W count is tested during both the early Free(F) read and the final read (4817-4862).
- Every nonpaging SET_INFORMATION class other than FilePositionInformation takes W, including EOF, allocation, valid-data, disposition, rename, and link classes, before lower dispatch (StageStream.c:3296-3343). Selected mutating USER_FS_REQUEST FSCTLs include SET_ZERO_DATA, SET_SPARSE, DUPLICATE_EXTENTS_TO_FILE and _EX, and the other listed mutation codes (2909-2923); tracked writer FSCTLs take W at 2961-2966. SET_EA and SET_SECURITY are covered at 3345-3364.
- Ordinary nonpaging WRITE takes W and requests a post-operation callback. Every pre-operation rejection after BeginMutatingIo ends the context before returning (StageStream.c:3275-3293, 3308-3333, 3353-3364, 3370-3378). Lower success, failure/cancel, and POST_OPERATION_DRAINING reach EndMutatingIo in post-operation (3509-3524); rename contexts transfer ownership and end W exactly once in CompleteRename (StageWriters.c:1950-1963). Saturation/allocation failure marks entry or instance Unknown before the tracked operation is passed; underflow resets W and marks Unknown rather than enabling promotion (2528-2602, 2614-2635).
- Entry completion contexts carry an extra Entry reference. The entry allocation is nonpaged; teardown clears its Instance/Volume pointers before dropping history references. Marker completion contexts hold only SOP/instance identity tokens and do not take instance/volume references (StageWriters.c:100-149, 2639-2682, 3424-3466). No W context outlives its protected allocation.
- The common FAST_IO_OPERATION write/set-information/EA/security/FSCTL paths are disallowed before incrementing W and retried through IRP handling. Paging IRP_MJ_WRITE bypasses W by design and is not refused: the paging branch does not call the mutating gate, and StagePhysicalMutationEx explicitly passes paging I/O (StageStream.c:2688-2694, 3275-3295). Writable section overflow also returns STATUS_SUCCESS to the lower acquire and records Unknown; it does not deny the section or paging writes (5482-5590).
- TxF set-information and selected mutating FSCTLs in scope are refused before lower dispatch; existing transaction association T is retained through terminal notification. W is not a substitute for T (StageStream.c:3171-3182; T association/notification paths in StageWriters.c:6330-6493 and TxF gates in Txf.c:118-190, 254-307).

I found no reachable double-end or underflow path in the W callers. W may remain positive while an admitted lower operation has not completed; the design correctly cannot treat that request as free. That is an intentional promotion wait, not a counter leak shown by this source. Counter saturation is practically unreachable through ordinary concurrency and degrades to sticky Unknown, not false promotion.

Overflow marker / spill review
------------------------------

Verified correct:

- Marker identity includes volume serial, full FILE_ID_128, stream suffix hash, and SOP identity. Classification reconstructs ADS names and examines every hard-link name; failed or incomplete enumeration stays unresolved. Cache publication checks policy generation before and after the PASSIVE scan (StageWriters.c:3142-3287, 4065-4306).
- Exact marker retirement requires zero writer, section acquire/release, and mutating-I/O counts, identity equality, and a live SOP/cache probe. The file-ID open and all hard-link I/O run after SectionLock is released (3074-3138, 3291-3350). Unknown marker updates are serialized under SectionLock and bump RegistrySopMapGeneration.
- Final lock order is RegistryLock -> volume scope-cache spin lock -> Entry.StateLock -> SectionLock. Writer admission uses WriterLock -> Entry.StateLock; section map updates use RegistryLock -> SectionLock. I found no reverse acquisition path in these reviewed routines and no blocking wait or filesystem I/O while a push/spin lock is held. The marker worker releases SectionLock before file opens and policy classification.
- The spill records retain only non-owning FILE_OBJECT/instance/SOP identity tokens plus their list reference; no instance or volume reference is stored. Acquire failure, release completion, draining, and instance teardown each have cleanup paths. The issue is unbounded count and unbounded scans, not an identified record leak after a completed pair.

Proportionality: concrete safe simplifications
----------------------------------------------

1. Revert the per-marker OUTSIDE-classification optimization in StageWriters.c:3141-3350 and remove its invocation/cache fields at 235-263 and 4837-4843. Keep identity-safe SOP quiescence/retirement, but conservatively block promotion for every nonquiescent unknown marker on the instance. This keeps the safety guarantee and removes the race surface; it loses only the P2 reduction in unrelated same-instance promotion stalls.

2. Delete the dynamic section spill tier at StageWriters.c:2724-2739, 5283-5479, 5540-5588, and the spill-specific branches in 5623-5883 (retain the fixed-slot release/acquire branches). Keep the fixed 64 slots. On fixed-slot capacity loss, set sticky Unknown at entry scope when SOP identity binds, otherwise instance scope, and always pass the acquire. This keeps Free(F) fail-safe and paging I/O admitted; it loses recovery after capacity overflow, which MVP-PLAN.md:391-398 explicitly accepts. A bounded fixed spill pool with the same Unknown fallback is a smaller alternative if exact recovery below the cap is retained.

3. The marker-specific W allocation/count path at StageWriters.c:2495-2602 and 2639-2682 can also be removed if overflow itself immediately becomes sticky instance Unknown and the entryless writer node remains in WriterObjects to preserve existing-writer pass-through. That keeps the ledger-not-gate behavior and prevents promotion; it loses the new per-SOP availability benefit. This change must preserve the W rundown for actual Entry-backed writers.
