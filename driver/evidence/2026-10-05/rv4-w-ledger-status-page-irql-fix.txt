# RV4 W-ledger pageable status-page lock fix

Worktree: `/tmp/safeupload-rv4-w-ledger-20261005`  
Base: detached `937b568cfa7cdbdcf2c46256e914d851b9ede950`  
Scope: source-only correction for the feature-build C28150 reported in the actual b26 WDK logs. No build, VM, Windows execution, or commit was performed.

`SafeUploadStageWritersActivatingStatusPage` remains in PAGE and retains its `PAGED_CODE()` check. Its direct `StageRegistryAcquireStateLock` call is replaced by `StageRegistryActivatingStatusSnapshot`, a resident `__declspec(noinline)` helper annotated `_IRQL_requires_max_(APC_LEVEL)`. The helper acquires/releases the existing state spin lock and copies only the bounded locked sample: volume serial, file ID, activation generation, state, H, and W.

The output buffer passed to the helper is a small local `STAGE_ACTIVATING_LOCKED_SNAPSHOT` on the nonpaged kernel stack. The status page itself is allocated from paged pool by the caller, so the pageable builder copies the completed local snapshot into that page only after the helper has lowered IRQL. The helper touches only the referenced resident registry entry and resident stack snapshot while the lock is held. It adds no lock and preserves the previously documented semantics: W mutations serialize on StateLock; H/state/generation are sampled context and do not become one coherent tuple. Remaining T/S/unknown/name/PID/section snapshots continue after releasing StateLock.

The pageable function still holds `RegistryLock` around its walk, as before. The new helper follows the existing RegistryLock-to-StateLock order used by other registry code; it does not acquire RegistryLock or introduce a new inverse ordering.

The stack snapshot stores its FileId as a `FILE_ID_128` struct; the copy destination is explicitly `&Output->FileId`.
