First Unknown source attribution and limitation

The b31 readiness pair is `firstUnknownReason=0x00000040`, `firstUnknownSite=2333`, with successful instance context (`contextStatus=0`). Thus the recorded source site is specifically a cleanup callback whose stream-context lookup was unsuccessful and whose instance was trusted/not tearing down. It does **not** identify the exact `NTSTATUS`, file ID, FILE_OBJECT, desired access, `FO_*` flags, directory classification, or PID. It is not evidence that the 101 denied opens caused the mark, and it cannot be used to claim that the first missing-context cleanup belonged to a directory or any particular user file. The first-published reason/site is a callsite attribution, not guaranteed chronological first event ordering under deferred/direct publication races.

Bounded cleanup asymmetry found in source

There is a credible source-level directory false-positive path that should be closed or disproven. `SafeUploadStageWritersReserveCreate` excludes `FILE_DIRECTORY_FILE` (`StageWriters.c:1217-1219`); post-create also skips that option and calls `FltIsDirectory` to skip actual directories even when create options did not identify them (`2185-2195`). Those paths create no regular-file writer node/stream context for a directory. In contrast, cleanup only excludes null objects, no `WriteAccess`/`DeleteAccess`, volume opens, and paging files (`2315-2325`). A directory FILE_OBJECT with WriteAccess or DeleteAccess can therefore reach `FltGetStreamContext`; if no context is attached, the trusted missing-context branch marks the entire instance Unknown (`2327-2334`). This is a plausible namespace-object false positive, not a proven explanation of the b31 site.

Minimal correctness fix: make cleanup classification symmetric with post-create. Before interpreting missing stream context as lost regular-file tracking, call the existing `FltIsDirectory(fileObject, instance, &isDirectory)` path. On a successful directory result, return as an intentionally untracked namespace object; if the query fails, retain conservative Unknown for the ambiguous object. Do not suppress missing-context Unknown for a confirmed regular file. This only avoids a false tracking-loss mark for the object class the writer registry already excludes; it does not change write denial/failure policy.

To attribute the next first mark, a bounded feature-only first cleanup-context-miss record should capture lookup `NTSTATUS`, `FltIsDirectory` status/result, FILE_OBJECT flags plus WriteAccess/DeleteAccess, and safe identity/PID fields when available, alongside reason/site/QPC. This is a narrow diagnostic record, not an all-cleanup trace, scan, reset, or taint control. Do not infer that the current b31 mark was a directory from line 2333 alone.
