RV4 upper W trace validator adversarial review
Date: 2026-10-05
Source pins: Validate-StagedWTrace.py SHA-256 E81E488C16A8FAE99C31A32A2241D4F8FBEDF1BC2C11E406E6E06F3230FD3266; Test-Validate-StagedWTrace.py C8E30350707F766D30950AAC48F8824D0481A1C6F3BFAE629C5B1401772A85B3; README 2AF8BE70BFC5CDD263B6134A2451923DF6DDD0672D39598F6C8E241839FC6BD6. Producer pins and mock evidence are recorded in `rv4-w-trace-validator-check.txt`.
Scope: fresh source-only audit against the Inspector formatter, kernel W-ticket producer, fixture design and documentation. No VM, driver, build, or validator self-test execution was performed.

Disposition

The parser is conservative about many structural failures: it rejects duplicate JSON keys, float/constants, malformed IDs, noncontiguous event sequence, loss, unpaired/duplicate tickets, changed request identity/range, wrong registry snapshot flags, and incomplete cursor/count windows. The CLI result always leaves W01, W02, and Phase4 `NOT_QUALIFIED`. This tool remains a mechanical upper-ledger parser; it cannot establish that a supplied file was emitted by the pinned Inspector, that CLEAR happened immediately before the trial, or any lower-filter/raw/runtime outcome. There are blockers before using `upperLedger=PAIRED` as evidence of the specified noncached W01 operation or its result.

Blocking findings

1. The input-size limit has a check/use race. `load_lines` stats the path and then calls unbounded `read_bytes()` (Validate-StagedWTrace.py:65-72). If the file grows or is replaced after `stat`, the process reads and decodes more than MAX_BYTES, contrary to its claimed 8 MiB bound. This is not fixed by the post-read line-count checks.

Minimal fix: open once and read at most `MAX_BYTES + 1` bytes, rejecting overflow based on the bytes actually read; optionally compare `fstat` on the open handle. Keep decode/line bounds after the bounded read. This is a real parser resource-bound gap even though the input is usually a locally saved Inspector dump.

2. The operation checks do not prove a noncached, nonpaging, aligned write. CLI accepts any exact `--irp-flags` value, defaults it to `0x00000000`, and only compares that expected value to the capture (lines 152-160, 207-220). It never requires the noncached IRP bit, rejects the paging-I/O bit, or checks required alignment of offset/length. README lines 20-21 even describes flags `0` as the default for the noncached stimulus. The fixture design requires a noncached IRP_MJ_WRITE and sector-aligned offset/size (phase4-suite-design-v2.txt:167-169, 702-715). A cached/paging or unaligned write with matching caller pins can therefore be labeled a paired W operation for this scenario.

Minimal fix: validate invariant IRP flag bits independently of caller-supplied expected flags (`IRP_NOCACHE` present and `IRP_PAGING_IO` absent), and require offset/length alignment against an explicit externally supplied target alignment (or the agreed fixed fixture alignment). Make the expected flags mandatory or set a semantically correct default. Add negative controls for each missing/wrong bit and unaligned range. These checks still do not prove the fixture opened with `FILE_FLAG_NO_BUFFERING`; retain native fixture/OS receipts for that fact.

3. Pair identity omits the stream's SectionObjectPointer. The Inspector prints `sectionObjectPointer` (main.c:576-580), the protocol carries it (Protocol.h:885), and the W producer captures `FileObject->SectionObjectPointer` into both ticket events (StageWriters.c:2651; later end snapshot retains the event). But `W_FIELDS` (validator :97-103) omits it, and the begin/end identity comparison (:182-186) does not compare it. A W_BEGIN and W_END with different or zero SOPs can still pass while the validator reports `PAIRED`. Exact FileId/file object/callback values do not substitute for the explicit stream identity required by the fixture contract.

Minimal fix: require a nonzero `sectionObjectPointer` field, optionally compare it against an independent externally pinned value, and always require equality across each W pair. Add a changed/zero SOP rejection control. Treat that pointer as an upper-filter identity only; do not infer cross-filter pointer stability from it.

4. W_END checks that status is merely “not pending,” and accepts arbitrary `ioInformation`. At lines 164 and 169-180, the parser validates IoInformation only as U64 and rejects W_END only if `ioStatus == STATUS_PENDING`. Thus access errors, cancellations, other failures, `STATUS_SUCCESS` with zero/short bytes, and implausible byte counts all produce a clean `PAIRED` result. W01 requires actual native completion status and raw bytes to distinguish success/failure/cancel cases (fixture design lines 702-715). The JSON includes those values, but this validator does not use them as an expected result.

Minimal fix: add per-case expected completion status and information semantics (e.g. success plus exact write length for the success row; explicitly enumerated error/cancel statuses and expected information for those rows). Keep a separate outcome-neutral `PAIRED` mode only if its output is clearly described as lifecycle pairing and never used to imply a successful/full write. Add short-success and failing-status negatives. A validator still cannot replace an independent lower-filter completion receipt and raw before/after observation.

Important evidence limitations / narrower checks

- Pairing requires begin pending, end not pending, exact registry flags 3 then 7, and W_BEGIN.W > 0. It does not check the expected isolated counter transition (for a single ticket, e.g. begin W=1/end W=0), nor compare W values across begin/end; `W_END` can carry the same or larger W and pass. Since `POST_RETIRE` means the producer observed decrement-before-snapshot, report the numeric W samples as unchecked context unless the fixture case specifies and validates the expected transition. Do not treat H/W/state/generation as a coherent tuple; the kernel notes explicitly document independent sampling.
- The complete-window rule checks `snapshotSequence` within ring capacity, `cursor == snapshot+1`, `totalEvents == snapshot`, exact record count, no gaps from sequence 1, and `lostEntries == 0` (lines 120-126). This establishes a complete retained sequence under producer assumptions, but no field in this dump proves a preceding CLEAR/reset receipt. README says the rule “models” CLEAR; preserve that wording. If trial isolation is required, require an external controller CLEAR receipt/epoch and bind it to this capture. Otherwise old pretrial records can be included and the validator cannot distinguish that history from a reset window.
- This is a W01 ordinary IRP_MJ_WRITE pair parser only: it hard-requires major 4/minor 0 and operationCode 0 (lines 152-157). README line 21 incorrectly associates it with W02, whose SET_INFORMATION/FSCTL operations have different major/operation codes and draining variants; the tool cannot validate W02. Narrow the README and output claims to this write-only validator.
- Non-W rows are skipped after sequence validation (lines 133-138); this is acceptable for a complete ring containing other event kinds, but there is no explicit event-name allowlist. Unknown future event names are ignored. The summary counters for paging/nonpaging/sections/instance setups are type-checked only, not reconciled with actual rows. Neither behavior should be used to claim absence of foreign activity. This validator rejects any foreign W ticket because it applies one expected target/range to every W row; that strict single-target trial restriction should be explicit.
- The W pair check rejects foreign W events when their ID/request/range differs from the supplied expectation, which is conservative. `callbackData` and `instance` are upper callback pointers; matching them within a pair is not same-IRP proof across filters. README correctly limits callback-data pins and disclaims cross-filter proof.
- The checked-in self-test reports synthetic pass/rejection controls and uses a literal formatter capture modified into a synthetic window. It does not test the size race, NOCACHE/PAGING/alignment, SOP mismatch, error/short completion, W transition, reset receipt, unknown event, or counter reconciliation. This is useful parser regression evidence only; it is not source authenticity or Windows/VM evidence.
- A nested JSON input can raise `RecursionError` outside the caught `JSONDecodeError` handler (lines 80-85), causing an uncaught traceback instead of the documented INCONCLUSIVE JSON result. The 4096-byte line bound limits severity, but catching this is a small parser-hardening fix.

No finding here qualifies W01/W02, proves last-handle cleanup overlap with a pending lower write, proves cross-filter IRP identity, establishes lower hold/release, or verifies raw storage. W01, W02, and Phase 4 must remain NOT_QUALIFIED.
