Adversarial review: simplified Phase 3 activation (Activating + Free(F))
Date: 2026-10-05
Reviewed source: 40a4433b (the source endpoint of 62034e29..40a4433b); HEAD 011c7743 adds evidence only.
Mode: read-only source review. No build, execution, VM, or source edits.

Verdict
-------

No P0 finding. The gate publication and most writer-admission serialization are sound in the audited paths, but the Free(F) proof is incomplete: H counts open writer file objects through cleanup, not writes already dispatched through them. A standard user can have a nonpaging write still outstanding when cleanup drops H; the activation worker can then observe H=T=C=0 and empty S pointers and promote before that write has finished.

Two P2 availability risks also remain at the bounded-ledger edges. A live overflow SOP marker blocks all promotions on its instance without determining whether that stream could be in scope. Capacity-loss Unknown is deliberately fail-safe for protection claims, but a user can make promotion remain unavailable. Neither P2 path promotes a file with an identified live writer.

Findings
--------

P1 — An outstanding nonpaging write can outlive H cleanup and land after promotion

Reachable by a standard user: Yes, with a writer handle admitted before the scope gate, an outstanding asynchronous/direct write, and close of the last handle while that I/O is still outstanding.

Evidence: Tracked writer writes are explicitly passed at StageStream.c:2694-2696. The nonpaging IRP_MJ_WRITE branch calls that check and then SafeUploadPreWrite without adding a registry completion/rundown reference at StageStream.c:3274-3279. StageEpochOperation covers mutating creates and writable section creation, not IRP_MJ_WRITE, at StageStream.c:3075-3099. H is decremented only when the cleanup post-operation callback invokes SafeUploadStageWritersOnCleanup at StageStream.c:3457-3464; that routine removes the exact file-object node and decrements H at StageWriters.c:2227-2243. The worker’s Free(F) checks H, T, RenameInFlight, C, MmDoesFileHaveUserWritableReferences, DataSectionObject, and SharedCacheMap at StageWriters.c:4150-4165, then repeats those checks and promotes at StageWriters.c:4171-4197. There is no in-flight write count in that predicate or an IRP_MJ_WRITE post-operation path that maintains one.

This is a real ordering gap, not an assertion that every close leaves a write pending: Microsoft documents that IRP_MJ_CLEANUP means the last handle is closed while outstanding I/O requests might still exist, and that a driver may receive additional read/write requests while processing cleanup ([IRP_MJ_CLEANUP](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/irp-mj-cleanup), [DispatchCleanup Routines](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/dispatchcleanup-routines)). The filter decrements H after lower cleanup succeeds, but it neither waits for nor counts such admitted write IRPs. A noncached write need not leave a data section or shared cache map, so the S check does not cover this case. A pending write may complete after promotion and change bytes in the now-Protected file.

Minimal fix: Add a per-entry mutating-I/O rundown count. Increment it before passing an existing writer’s mutating IRP below the filter, decrement it in post-operation including draining/failure paths, and require zero in the final promotion serialization. Keep existing writers admitted as decided; delay promotion until their already-admitted operations complete. Cover every mutating operation that can remain outstanding, not only IRP_MJ_WRITE.

P2 — A live overflow SOP marker stalls every candidate on that instance

Reachable by a standard user: Yes, conditionally. The user must hold enough distinct writer identities to exhaust the named and compact tiers on one NTFS instance (up to 1,024 named plus 4,096 compact entries per instance; Protocol.h:288-293), then retain an overflow writer.

Evidence: Capacity overflow keeps the post-create callback and records a narrow SOP marker at StageWriters.c:1273-1306 and StageWriters.c:2092-2113. UnknownWriterCount is incremented for a live marker at StageWriters.c:2558-2569. During promotion, StageRegistryUnknownSopMarkersQuiescent scans markers for the instance and treats any nonzero UnknownWriterCount as live at StageWriters.c:2736-2744; it does not classify that marker’s file ID, ADS, or hard-link names against current/pending scopes. Every candidate that reaches this check then waits at StageWriters.c:4167-4169. Thus one out-of-scope overflow stream with an open writer can keep unrelated scoped entries from reaching Protected. This is availability-only: the worker withholds promotions rather than promoting through the unknown writer.

The plan says promotion waits while a marker is live and not provably out of scope (MVP-PLAN.md:389-390). The implementation never proves a live marker outside; it conservatively treats every live marker as undecidable. This is consistent with fail-safe behavior but makes the same-instance DoS broader than necessary.

Minimal fix: Classify the marker’s exact file identity and all live hard-link names, including its ADS suffix, against the current/pending/boot scope union. Keep blocking on an in-scope or undecidable marker; let a marker proven outside the union stop holding unrelated entries while retaining it until its own exact stream is Free(F).

P2 — Bounded tracking loss can leave an entry or instance Unknown indefinitely

Reachable by a standard user: Yes, if the user can cause 65 retained writable section-acquisition slots, or exhaust the writer tiers. This withholds promotion; it does not itself deny lower I/O.

Evidence: The C ledger is a global 64-slot table (StageWriters.c:2396-2399 and Protocol.h:295). When no slot is available, SafeUploadStageSectionAcquired marks the known registry entry Unknown, or marks the whole instance Unknown when it has no SOP-to-entry binding, then lets the acquire proceed (StageWriters.c:4627-4658). UnknownReasons is ORed into the entry and its state becomes Unknown at StageWriters.c:688-697; Free(F) and final promotion reject nonzero UnknownReasons at StageWriters.c:4144-4148 and 4179-4185. The source has no recovery path that clears a capacity Unknown reason after the section slots drain. Similarly, a matching overflow SOP marker transferred to a newly associated entry transfers its unknown reason at StageWriters.c:2940-2961 and clears the marker’s UnknownWriterCount; cleanup of the old Entry==NULL writer only decrements a slot still marked Unknown at StageWriters.c:2607-2623. That transfer therefore conservatively strands the new entry Unknown.

The 64-slot case is a known bounded-ledger tradeoff, not a false Free(F): an identified entry is withheld from promotion, and an unbound loss widens to the instance. The prior plan explicitly accepted promotion DoS on capacity loss (MVP-PLAN.md:307-315, 366-373); the fix2 review also recorded it. The final simplified activation still has this standard-user availability surface.

Minimal fix: Preserve spill counts per SOP/instance rather than converting a transient capacity shortage into a permanently uncleared bit. When a marker is later bound to an entry, carry its live-writer count/binding so cleanup can retire the loss only after exact H/C/S/T quiescence. If exact recovery is impossible when all bounded stores are full, keep the fail-safe Unknown behavior and document this as an accepted availability limit rather than claiming recovery.

Promotion soundness and admission ordering
-----------------------------------------

- Scope publication is serialized with mutating creates and writable-section creation. SetPolicy publishes the pending union, closes/replaces the epoch, drains tokens, applies the pending scope, and only then finalizes at Policy.c:1009-1049. StageEpochOperation includes mutating create dispositions/access and writable section creation at StageStream.c:3075-3099. Create post-operation commits the reservation before the epoch token is released at StageStream.c:3467-3504. Thus a create that entered before publication cannot disappear between the scope scan and writer accounting.
- For a writable section, C is reserved before name/SOP/policy admission at StageStream.c:3317-3330 and StageWriters.c:4595-4624. A denied or failed acquire rolls back its exact slot at StageStream.c:3327-3330 and 3434-3442; a successful acquire retains it to release. If promotion wins the SectionLock first, the later acquisition still reaches the current/pending protected-name gate and is refused. If acquisition reserves C first, promotion sees C. The 64-slot overflow consequence is Finding 3.
- The alias worker publishes Activating and ActivationEnforced before its first Free(F) read at StageWriters.c:4106-4118. The final decision holds RegistryLock and Entry.StateLock, rechecks generation/name/state/H/T/Rename/C, and CASes state while serializing the SOP-map generation under SectionLock at StageWriters.c:3818-3878. Policy and rename-loss publication use interlocked operations and the scope-cache spin lock; the alias resolution enters the same rename-loss lock before releasing its gate at StageWriters.c:3970-4004. I found no stale-reobservation ordering path that lets a new registered open or writable section slip between the gate and promotion.
- Duplicate or inherited handles share the same FILE_OBJECT. H is charged to the exact writer node and remains until last-handle cleanup; duplicating the handle does not create a second FILE_OBJECT or an early cleanup. A live user-writable mapped view is separately covered by C and MmDoesFileHaveUserWritableReferences, and a nonempty data section/shared cache map blocks promotion.
- A bare ObReferenceObject on a FILE_OBJECT preserves object lifetime but is not itself a write admission. I found no driver in this repository issuing a later write through a stale writer FILE_OBJECT. Microsoft’s FltWriteFile contract requires the FILE_OBJECT to be currently open and says calling it after cleanup asserts on checked builds ([FltWriteFile](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltwritefile)). The outstanding-IRP case above is concrete and separate.
- Cache Manager and image-section boundary: Free(F) checks DataSectionObject and SharedCacheMap twice, but not ImageSectionObject, at StageWriters.c:4158-4165 and 4173-4195. New non-image writable section creation is counted/gated; SEC_IMAGE is expressly exempted at StageStream.c:3032-3035. I found no repository path where a writable image view writes its modified pages back to the backing file, so I do not count ImageSectionObject as a demonstrated content-write bypass. The filter does not wait for a Cache Manager lazy-writer event; it relies on the file system/MM lifecycle represented by the SOP fields. Microsoft says SOP members can change at any time ([SECTION_OBJECT_POINTERS](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ns-wdm-_section_object_pointers)); CcUninitializeCacheMap exposes an event signaled when cached data has flushed ([CcUninitializeCacheMap](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ccuninitializecachemap)). These docs do not establish that NTFS can clear both pointers while a writeback capable of later modifying the file remains outstanding. This is an NTFS/VM qualification item, not a source-proven additional finding. The outstanding IRP finding already demonstrates a supported writer path without relying on cache-manager behavior.
- TxF is counted by T when the create’s post-operation enlists the transaction; failed enlistment marks Unknown. Terminal commit/rollback drops T and queues recheck (StageWriters.c:2121-2127, 5223-5343, 5346-5388). The policy path no longer uses the old bootstrap path; by-ID checks are against configured/current/pending scope.
- Hard links are classified by the PASSIVE worker against all returned links and ADS suffixes; partial/error results stay gated (StageWriters.c:3428-3667). External rename/link admission checks source/destination current+pending scope, tracked-writer rename keeps H live, and retained-name rewrites or rename-loss generations are rechecked before promotion (StageStream.c:2747-2822; StageWriters.c:1404-1578, 1832-1910, 3970-4004). New rename/link into an already protected name is denied. I found no file-ID/SOP reuse path that rebinds a different live stream and promotes it: opens verify full file ID, volume serial, and exact SOP, and association checks identity before transferring marker state (StageWriters.c:2703-2712, 2940-2961).
- By-ID classification is now one bounded PASSIVE attempt, not the earlier 128-pass synchronous loop. Known-outside volumes pass; on a possibly scoped volume, unresolvable high-half IDs or undecidable link enumeration are denied at StageStream.c:2544-2571. This remains a possible standard-user false denial for a highly linked or share-conflicted out-of-scope target, but it is fail-closed and matches the stated one-attempt decision; it does not create a protection bypass.
- Raw volume opens are excluded from the per-file writer ledger at StageWriters.c:1033-1038, but the nonpaging mutation path still performs name/policy classification and denies unresolved operations on a volume that may contain scope at StageStream.c:2683-2714, 3008-3011. FSCTL_MOVE_FILE is not in the selected data-mutating FSCTL set (StageStream.c:2825-2924); Microsoft describes it as moving clusters for defragmentation and requiring a privileged volume-open path ([FSCTL_MOVE_FILE](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_move_file), [File System Control Processing](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/file-system-control-processing)). I found no standard-user content-write path here.
- Reparse creates that return STATUS_REPARSE cancel their reservation rather than committing an identity to the unresolved name (StageWriters.c:2054-2056); the eventual target create is separately filtered. I found no path through junction/reparse normalization that bypasses the current/pending target check.
- Teardown carries nonowning InstanceIdentity in SOP and C slots, detaches both by instance identity, then clears Entry->Instance/Volume before dropping history references at StageWriters.c:2441-2481 and 2816-2865. This closes fix2 finding 7 and avoids holding an instance reference through FltpFreeInstance. The SOP fast path is a 16-probe hash under SectionLock, with tombstone-aware deletion at StageWriters.c:2406-2439; a full/missed probe causes tracking loss/Unknown, not a false Free(F). Full-table enumeration is PASSIVE and split into 64-slot lock holds at StageWriters.c:2719-2757. I found no blocking wait or file/cache I/O under RegistryLock, SectionLock, or Entry.StateLock, and no pageable activation routine reachable from paging/APC write admission.
- A returned table-capacity loss can leave Unknown sticky, but registry loss does not itself cancel lower writes. New opens and writable sections are gated by the current/pending name/SOP path; unresolved paths are refused only on volumes that may contain scope. Known-outside fallbacks pass at StageStream.c:3008-3011, 3064-3070, and 2544-2571. The initial scope-blind boot refusal finding is closed for those cases.

Removed-cutoff audit and earlier findings
-----------------------------------------

No cutoff implementation/status symbols remain in SafeUpload.Minifilter, SafeUpload.Inspector, or driver/scripts: no CutoffStarted, DirtyAfterCutoff, PagingWriteBegin/End, owner flush admission, or paging-write gate reference remains. Protocol.h uses Reserved0/ReservedFlags in the replaced activation status layout (Protocol.h:817-819), and the Inspector reads the new Activating status. Paging IRP_MJ_WRITE does not enter StagePhysicalMutation; the write dispatch breaks/pass-throughs paging I/O at StageStream.c:3274-3279. I found no paging-write refusal path in the simplified activation.

One separate diagnostic remnant remains: StageFence.c is still compiled for the prototype and retains old comments describing an unowned paging-write refusal (StageFence.c:1-22). StageStream.c:2240-2247 says the fence is retained only for diagnostic refresh/status and setup/unload coordination. Outside StageFence.c, SafeUploadStageFenceIsFenced and SafeUploadStageFenceCountPagingDenied have no call sites; the status ABI still exposes PagingWritesDenied (Protocol.h:694-716), but its counter has no increment caller. This is stale/vestigial diagnostic code, not an active paging cutoff or refusal.

Verified correct / no source finding
------------------------------------

- H remains live across duplicate/inherited handles until cleanup of the shared file object; C is reserved before admission and rolled back on failure; user writable mappings and nonempty data/cache sections block promotion.
- Scope gate precedes the first Free(F) observation, and new registered creates/sections cannot pass between that gate and the final state CAS.
- Hard-link/ADS identity, volume serial, full FILE_ID_128, SOP incarnation, rename-loss generation, TxF T accounting, unknown-reason transfer, bounded hash tombstones, and section-slot teardown are present. Their capacity failures fail closed for promotion rather than falsely proving Free(F).
- No source path found for a standard-user raw-volume byte write, a defrag move that changes file contents, an arbitrary ObReferenceObject becoming a write capability, or a kernel component in this repository issuing post-cleanup writes.
- No active cutoff gate or false paging-write denial remains in the reviewed activation path. The known-outside-volume refusal cases that drove the earlier boot finding are corrected.
