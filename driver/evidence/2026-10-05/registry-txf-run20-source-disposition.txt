# Registry TxF run 20 source disposition (read-only)

## Finding

Run 20 does not exercise the boot-trusted C: path. It follows the late-load diagnostic lifecycle: the clean baseline requires the original driver/service stopped, the harness replaces the driver, calls `fltmc load SafeUpload`, then waits for canaries. Provenance pins source/harness commit `6a833c91f4164de9c6aae009ffe7299cd12577de`, b30 feature SHA `5182E4C0...D3689`, Inspector SHA `06090293...C5A18`, `Variant=registry-txf`, `Verifier=True`, and `ExpectedChecks=93`. Baseline says service Manual/Stopped and filter unloaded; the run restored original driver/policy, unloaded the filter, turned Verifier off, removed fixtures/actors, and retained `BaselineClean=True`.

That lifecycle cannot establish boot trust. `Context.c:337-341` sets `TrustState` to CANARY_PENDING only when the setup flag is NEWLY_MOUNTED; otherwise it starts UNTRUSTED (or PENDING_REBOOT in boot-start mode). `StageAdmission.c:374-379` upgrades TrustState on canary success only for a newly-mounted instance. `StageAdmission.c:897-940` nevertheless runs the primitive canary for every eligible attached fixed NTFS volume. Thus `AllVolumeCanaries=PASS;count:2` and each `CanaryState=PASSED` show the create/readback/security/cleanup primitive worked; they do not establish `SafeUploadInstanceIsTrusted`, which requires both TrustState=CANARY_PASSED and CanaryState=PASSED (`Context.c:446-460`). The harness itself records the intended late-load rule in `Test-StagedAdmissionDiagnostic.ps1:4294-4296`: trust-only means `Free=false`, state Unknown, reason `0x80`; real Free/promotion is reserved for boot-start tests.

Run 20's failures therefore cannot be called a boot-trusted product regression. However, the 74/93 failures are not explained solely by expected late-load trust: all sampled rows say `reasons:0x00000084`, whereas the permitted late-load-only reason is `0x80`. The protocol defines `SAFEUPLOAD_REGISTRY_UNKNOWN_IDENTITY=0x04` and `...TRUST=0x80` (`Filter.h:245-252`). In the no-history diagnostic path, the `0x04` is a derived umbrella: `StageWriters.c:6335-6359` sets `unknownInstance` from `WritersUntracked || RegistryUnknownReasons`, and `globalUnknown` from `SafeUploadStageWritersGlobalUnknown`; line 6364 adds the IDENTITY result bit if either is true. It does not prove that the specific fixture's file-ID query failed. The result correctly adds TRUST separately when `SafeUploadInstanceIsTrusted` is false.

The retained `RT_StatusAfterCorpus` reports `registryUnknownReasons=0x10`, `registryInstanceUnknown=1`, `registryIdentityFailures=1`, and `registryRenameFailures=1`; the end capacity control reports `overflowDelta=0;unknownReasons=0x10;instanceUnknown=1`. This confirms additional sticky registry/rename/instance-Unknown state by the end, beyond the expected Trust bit. It does not identify the source instance, first event, or whether that loss preceded the first fixture result. The gate does not retain an admission-volume status / per-instance reason-and-origin record adjacent to the first `0x84` result. The b30 pinned `Filter.h` has `RegistryUnknownReasons` but no `RegistryFirstUnknown`; the exact loss site is therefore unavailable from this run. It is inaccurate to label the 0x04 diagnostic bit as a proven per-file identity-open failure.

The 19 PASS / 74 FAIL total mixes expected untrusted/no-Free outcomes with assertions that require the entry lifecycle; it is an unqualified diagnostic run, not a replacement for the boot-trusted 93-row suite. The per-row `HistoryPresent=False`, H/W/T=0, S=NO samples are consistent with quiet/pruned entries and the test allows pruning for closed quiet entries (`Test-StagedAdmissionDiagnostic.ps1:4302-4304`). They do not by themselves prove lost tracking. The additional Unknown bit is the unresolved signal.

## Comparison and next evidence

The retained run 19 readout says explicitly it was also late-loaded and not a Free/promotion qualification; it passed 93/93 with only trust reason `0x80`, then reported pruning/capacity behavior. Run 20's changed behavior is evidence of a new additional Unknown condition in that execution, but because run 20's evaluated C: context/first reason is not captured at the first failing probe, source/evidence cannot yet distinguish a true product tracking loss (possibly rename/global Unknown) from a run-specific concurrent loss. It is not safe to dismiss it as the lifecycle mismatch.

The narrow lifecycle change needed to preserve the 93 existing functional requirements is a separate boot-start invocation of the same registry-TxF stimulus/assertion body: stage the reviewed feature driver and durable boot policy before reboot; keep SafeUpload boot-start and attached through reboot; require readiness showing C: newly-mounted, canary passed, TrustState trusted, and per-instance `WritersUntracked=0` / reason mask zero before running the registry corpus; then run the existing 93 stimuli and assertions without replacing or late-loading the driver. Keep the late-load version only as the distinct diagnostic that checks trust remains absent and exercises the late-attach pass-through contract. Do not promote/force trust on a late attachment or clear sticky Unknown.

For the unexpected run-20 `0x04`, capture feature admission-volume status immediately before and after the first `RT_NeverWritten_0` evaluation, including C: instance identity, setup flags, canary/trust state, `WritersUntracked`, exact `RegistryUnknownReasons`, first recorded reason/site if present, and global Unknown/reason counters. A repeat in the correct boot-trusted lifecycle is needed before declaring a product regression or closing the run-20 loss. Do not scan, reset, retry, or relax the trust gate.
