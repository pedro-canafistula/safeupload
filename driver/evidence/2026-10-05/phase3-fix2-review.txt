Verdict

The round closes several earlier implementation gaps, but it does not close the cutoff-flush guarantee or the ADS-capacity finding. The owner token admits any paging write for the target SOP that reaches the callback on the worker thread while the flush window is open; it cannot establish that the dirty page was written before the policy cutoff. Separately, compact-overflow SOP markers are not included in scope expansion and are ignored by normal paging admission. A mapped stream that overflowed the compact tier can therefore continue paging writes after a later scope expansion.

The transition gate also rejects paging writes by volume for the entire scope-transition window, including writes for entries already known outside the current/pending union. Those denials permanently set DirtyAfterCutoff for tracked entries. This violates the strict “never refuse I/O outside scope” invariant and can leave later-scoped files permanently gated.

No source path proves a spin-lock cycle, wait or cache/file I/O under a spin lock or RegistryLock, double-free, or dispatch-level call into the pageable activation worker. The by-ID classifier does perform bounded but potentially expensive synchronous work inside a create pre-operation; its reentrancy does not recurse into itself because its internal open is read-only.

Prior findings 1-7: closure assessment

1. By-ID out-of-scope denial — Mostly closed for ordinary low-half IDs. If the volume cannot hold a current, pending, or boot scope, the low-half operation passes. On a possibly scoped volume, successful all-link classification passes an out-of-scope target and refuses an in-scope target. Undecidable classification, non-PASSIVE/top-level calls, and unknown high-half IDs still refuse. The latter is the recorded D6 exception; the former means the literal “never refuse an out-of-scope operation” property remains conditional on resolvability. See Finding 4.

2. Cutoff admission race — The original start/publication race is closed by the shared scope-cache boundary and per-entry in-flight count. The owner exception does not close the required data-age boundary: thread plus nonzero epoch is not proof that a page contains only pre-cutoff stores. See Finding 1.

3. Missing DirtyAfterCutoff store — Closed in the narrow sense: denied tracked paging writes store the sticky bit under PagingWriteLock. The store also runs for the broad volume transition denial, including known-outside entries, and the bit is never cleared. See Finding 3.

4. Cutoff paused during policy update — Closed in source: SafeUploadPolicyActivationCutoffsResume requeues a registry recheck after unpausing. Policy.c:428-434.

5. Name-tier capacity denial of service — The first-tier 1,024-record failure now falls back to compact records while the compact tier has space. The residual accepted capacity DoS remains: a standard user can fill the two tiers, then cause an overflow writer’s unmatched cleanup to mark the instance Unknown. See Finding 5.

6. ADS capacity miss — Closed while a compact reservation can be made. Not closed when compact capacity is exhausted: the SOP-only Unknown record is not visited by scope expansion or normal paging admission, and one known-ADS allocation-failure path records no Unknown at all. See Finding 2.

7. Hard-link work amplification — Improved for the reclaim worker: parent names are deduplicated within a pass and the worker limits each pass to 32 link records, leaving unfinished entries pending. The by-ID pre-create path loops up to 128 such passes synchronously, so the bound is not an equivalent latency bound there. See Finding 4.

Findings

1. P1 — Flush-owner admission cannot distinguish pre-cutoff cache data from post-cutoff stores

Code: StageWriters.c:3451-3489, 3954-3993, 3998-4003, 4800-4804, 4821-4824.

The worker opens owner admission immediately before CcFlushCache and keeps it through FltFlushBuffers. PagingWriteBegin treats a callback as worker-owned when the admission bit is set, the current thread equals CutoffFlushOwnerThread, the epoch is nonzero, and DirtyAfterCutoff is clear. It does not bind admission to a specific I/O request, dirty-page generation, or store time. The epoch is checked against ExpectedEpoch only when disabling admission, not when admitting a paging write.

Scenario: A user already has a writable mapped view when a scope expansion gates the file. After the cutoff, the user stores new bytes into a mapped page. That store does not call PagingWriteBegin and does not set DirtyAfterCutoff. If the worker’s CcFlushCache or FltFlushBuffers submits that page’s paging write through this filter on the owner thread, the write passes the workerFlush test. If the view/cache then becomes quiescent before the final S/cache checks, the worker has no recorded fact that the flush contained a post-transition store and may reach the promotion checks. The checks at 4013-4034 and 4040-4069 inspect current references/cache state and EOF; they do not compare the flushed contents with a pre-cutoff snapshot.

Pageouts arriving on another lazy-writer or mapped-page-writer thread fail the thread test and are denied; that path sets DirtyAfterCutoff. This does not cover the same-thread pageout path. The source proves the admission hole and lack of data-age tracking; whether a particular Windows CcFlushCache request is emitted on the caller thread and whether a particular flush can then reach promotion require the forbidden VM validation.

Reachability: A standard user needs a writable mapping to a file that becomes scoped and must race a mapped store against the worker flush. No policy-administration privilege is needed for the store.

Minimal fix: Do not treat worker thread identity as proof of pre-cutoff data. Add a cache/data boundary that proves the flushed pages predate the cutoff, or keep the candidate non-promotable whenever a writable mapping/cache could have received stores after the cutoff. Promotion must be impossible if the owner flush may include post-transition data.

2. P1 — Compact-overflow SOP Unknown records are invisible to scope activation; ADS allocation loss can be silent

Code: StageWriters.c:1267-1286, 1325-1338, 2070-2075, 2372-2416, 2592-2599, 4703-4722, 4877-4924; StageStream.c:3229-3253, 3480-3492.

When both tiers are full, ReserveCreate sets TrackingLost and PostCreate records the file ID/SOP in RegistrySopSlots as Unknown. But ApplyPendingScope and ReconcileCurrentScope iterate RegistryEntries, not Unknown-only SOP slots. StageRegistryReferenceSop returns only slots with Entry != NULL. Thus a lost stream with only an Unknown slot is neither classified nor bound to a paging-write entry. Outside a transition, PagingWriteBegin receives entry == NULL and admits it. Section acquisition can copy the Unknown marker’s file ID into a section slot, but no expansion path consumes that slot as a candidate.

Scenario: A standard user keeps 1,024 named-tier and 4,096 compact-tier writer identities live on one fixed NTFS instance. The user then opens a writable stream outside the current scope after compact capacity is exhausted, keeps its handle/mapping, and the service expands scope to include its directory. PostCreate records only an Unknown SOP marker. ApplyPendingScope scans the registry list without this identity. After the transition ends, a mapped pageout has no Entry and is admitted. A later cleanup may mark the instance Unknown, but stable paging admission does not use instance Unknown as an I/O gate.

There is a second hole before that overflow path: for a known ADS, RefuseAllocation suppresses instance Unknown when pathResolved is true and streamChars is nonzero (1325-1329), then Cleanup clears Required and ReservationOut (1330-1338). If reservation or node allocation fails, StageStream receives no reservation and its Required fallback at 3248-3250 does not run. The successful physical create proceeds without an SOP marker or registry entry. The same later mapped-pageout path remains untracked.

A late bind also discards the overflow fact: AssociateSectionPointer converts map->Unknown to map->Entry and clears Unknown without copying an Unknown reason (2592-2599).

Reachability: The capacity case costs about 5,120 simultaneously live writer identities on one instance, then one additional target writer/mapping. The allocation-failure variant requires pool/allocation pressure and a known ADS create. Both are user-space paths if the user has write access. The later scope addition is service-controlled.

Minimal fix: Make overflow-only identities enumerable and classify them during scope changes, and transfer the Unknown reason when a slot binds to an Entry. Preserve a fallback record when reservation/node allocation fails before PostCreate can learn the SOP. Reconcile that with D1: a lost identity cannot both remain entirely pageout-admissible and be claimed as protected after expansion.

3. P1 — The volume transition denies known-outside paging writes and permanently taints them

Code: Policy.c:1314-1319, 747-768; StageWriters.c:4791-4824, 3791-3815, 3998-4003; StageStream.c:3480-3491.

Publishing a pending policy sets ScopeTransitionActive for the volume union. PagingWriteBegin denies every write on a volume for which transitionApplies is true: it denies entry == NULL at 4796 and every tracked entry unless it is the flush owner at 4804. It does this before consulting the entry’s ScopeNameClassification, so even an entry already classified OUTSIDE is denied. StageStream completes the paging write with STATUS_MEDIA_WRITE_PROTECTED. Every denied tracked entry gets DirtyAfterCutoff set. No clear of that bit appears in the reset path at 3791-3815; later activation exits when it sees the bit at 3998-4003.

Scenario: A user has a dirty mapped page for file B outside every current, pending, and boot prefix on C:. While the service adds an unrelated C:\protected prefix, C: is a possible-scope volume and the policy transition is active. B’s pageout is refused despite its known-outside classification. Its registry entry becomes permanently dirty. If a later policy adds B’s directory, the entry is activated/gated but cannot finish activation because DirtyAfterCutoff remains set. This is a standard-user availability attack requiring a dirty mapping concurrent with a policy update, not policy privilege.

This source establishes a direct out-of-scope paging denial and sticky state change, not a Windows bugcheck or data-loss outcome. It means “never refuse I/O outside a scope” does not hold during a transition on a mixed scoped volume. The fallback paging-token path has the same volume-wide transition denial (Policy.c:853-864; StageStream.c:3434-3445).

Minimal fix: Apply the cutoff to per-identity candidates and let a proven-outside entry pass. Do not set the permanent dirty marker for a known-outside write denied only by the volume-wide transition. If unresolved entries must fail closed, keep that as a distinct documented exception.

4. P2 — By-ID classification is synchronous, can false-deny on open conflicts, and is not bounded to one worker batch

Code: StageStream.c:2547-2563; Txf.c:97-105; StageWriters.c:3330-3414, especially 3374-3378 and 3399-3405; StageWriters.c:3178-3219.

The ordinary and TxF by-ID pre-create paths call the classifier synchronously at PASSIVE_LEVEL before the caller’s create reaches the filesystem. The helper opens the target by ID and enumerates links; it can then loop 128 times, each pass consuming a 32-link budget. That is up to 4,096 link records/parent-name probes in one create pre-operation, rather than one 32-identity worker batch. If classification fails or exceeds the pass limit, the caller is refused on a possibly scoped volume even if its target is outside scope.

The open uses FILE_READ_ATTRIBUTES, all three share flags, and FILE_COMPLETE_IF_OPLOCKED. The latter avoids waiting for an oplock break; an oplock result or a share-access conflict still makes classification fail and StageAdmit refuses. For example, if a live handle denies read sharing while allowing the requested mutating open’s sharing/access combination, the filter’s extra attributes-only open can fail even though the caller’s requested open would otherwise be allowed. This is the recorded fail-closed “undecidable” behavior, but it remains an out-of-scope false denial.

Reentrancy/deadlock check: this is a same-filter, same-volume open from a create pre-operation. The helper does not hold RegistryLock or the StageNamespaceResource over the file open; StageNamespaceResource is released before classification at StageStream.c:2521-2534. The internal open requests only read attributes, so it does not enter the writable by-ID classification branch again. I found no source path for infinite classifier recursion or a lock cycle. The open can fail conservatively as described.

Reachability: A standard user can request a by-ID mutating open on a possibly scoped volume; hard-link-heavy targets amplify work. A restrictive existing share mode can trigger the failure case. TxF adds a transaction prerequisite.

Minimal fix: Reuse a stable cached identity/classification where possible and avoid a 128-pass metadata scan in the caller’s pre-operation. Keep any undecidable-target policy explicit; do not imply that all known-outside by-ID requests will pass when this open can fail.

5. P2 — Accepted standard-user ledger-capacity denial of service remains; cost is lower than the SOP-table maximum

Code: Protocol.h:288-293; StageWriters.c:1120-1125, 1267-1286, 2070-2075, 2187-2195, 2221-2226, 4898-4903.

A standard user can create and hold 1,024 name-tier plus 4,096 compact-tier writer identities on one instance. An additional writer is recorded only as an SOP Unknown marker. When that untracked writer is cleaned up, the no-context or unmatched-node cleanup path marks the whole instance Unknown. Unknown is sticky; ApplyPendingScope then skips new activations/promotions on that instance. The user needs filesystem write permission and about 5,120 live writer handles, then one overflow create/cleanup; no administrator or policy command is needed.

This is the D2 accepted residual in MVP-PLAN.md. It does not, by itself, make stable paging admission deny I/O: the normal path does not consult instance Unknown. It does stop new protection promotions/activation on that volume until the instance/driver is recreated, and the overflow-only target remains subject to Finding 2.

6. P2 — The global SOP table creates a high-IRQL linear-scan cost at its configured maximum

Code: Protocol.h:293; StageWriters.c:4697-4722, 4775-4794.

RegistrySopSlots can contain 36,864 slots. StageRegistryReferenceSop linearly scans it under SectionLock, which raises to DISPATCH_LEVEL, and PagingWriteBegin invokes that lookup for no-stream-context paging writes. A miss or late-position hit at high occupancy holds the spin lock for the full table scan. The table is bounded, so this is not unbounded allocation or a lock-order deadlock; the source does establish O(table capacity) work at raised IRQL. I did not measure latency or claim a watchdog failure because execution is prohibited.

Reachability/cost: Filling the table requires many distinct live/overflow SOP identities; a user who already exhausted the registry capacities can create the marker pressure. The worst cost is paid repeatedly by paging writes while the table is near full.

Minimal fix: Use a bounded indexed/hash lookup for SOP bindings, or a structure with a strict small upper bound on work while SectionLock is held.

7. P2 — A draining acquire with no Entry leaves a global section slot behind across instance retirement

Code: StageWriters.c:2313-2328, 2358-2369, 2420-2431, 4606-4613, 4635-4645.

The draining release path calls SafeUploadStageSectionAcquireDraining and returns without removing the slot. That is deliberate while the same stream/instance may still exist because the acquire outcome is unknown. However, an overflow-SOP slot has RegistryEntry == NULL, and STAGE_SECTION_SLOT has no instance identity. Instance retirement only removes SectionSlots whose RegistryEntry identifies the retiring instance (2358-2364); clearing Unknown SOP bindings does not clear SectionSlots. Thus, if a draining acquire with no Entry is followed by instance teardown, its fixed-table slot and SectionNow contribution cannot be retired by this code. Repeated such lifecycle cases can consume the 64-slot global table and cause subsequent SectionInFlightOverflow losses.

Reachability: This requires the filter’s post-operation draining path plus an instance teardown, not a standard-user-only action. I found no source-level double-free; this is bounded stale ledger state.

Minimal fix: Record a non-owning instance identity on each section slot and retire/taint slots by instance during teardown without dropping a still-live binding prematurely.

Regression checks and verified-correct paths

• Boot/read safety: StageDispatch skips epoch acquisition for operations outside the mutation union and its comment explicitly preserves early-boot reads/loads/executes (StageStream.c:3414-3426). StageAdmit’s unresolved-name failure only refuses when the operation is classified as a writer and the volume may hold a scope (2576-2591); read-only opens pass. The strict “never refuse any out-of-scope I/O” statement is still not absolute: a mutating name-resolution/parser failure on a mixed scoped volume is refused by volume possibility (2581-2583, 2593-2600), and high-half unknown private IDs remain refused before the volume check (2542-2545, the recorded D6 exception). No source path here establishes the historical boot bugcheck cause.

• Paging ledger semantics: Outside an active transition and absent an entry-specific protection/activation gate, a missing SOP entry is admitted; an Unknown-only SOP slot is not itself an I/O denial. Section acquire overflow records Unknown and returns STATUS_SUCCESS to the lower acquire (StageWriters.c:4518-4555). During an active scope transition, however, missing and tracked entries on a possible-scope volume are denied as stated in Finding 3. Therefore “ledger loss never refuses paging I/O” is true only outside that separate transition/entry protection gate, not literally on every path.

• Cutoff retry/resume: Failed flushes clear the owner admission, retry with bounded count, and become Unknown/gated after the configured limit (StageWriters.c:3494-3518, 4074-4088). Cutoff-pause resume queues a recheck (Policy.c:428-434). This closes the earlier missed-resume path.

• Two-tier accounting/lifetime: Named and compact counts/reservations are separate; reserved capacity is released before existing-key lookup and committed once on insertion (StageWriters.c:818-852, 861-945, 1253-1313). Existing identity lookup is keyed by instance, volume, volume serial, file ID and SOP (763-779). Compact records bind the same reference-counted entry type. Retirement/prune detach map/section references and clear Entry->Instance/Volume before dropping the history ref (2434-2521, 2655-2718); context-held entry refs therefore do not retain instance/volume references through teardown. The compact pool is freed only when every slot has returned; otherwise uninitialization deliberately retains the pool rather than freeing live entries (4428-4445). No use-after-free path is shown by source; a non-returned pool would be a bounded leak fallback.

• File-ID reuse and stream identity: A new SOP for a reused file ID does not join an old entry because the lookup includes SOP. Reopen verifies volume serial, all 128 file-ID bits, and SOP equality (StageWriters.c:2942-2950). Pointer reuse may conservatively rebind/taint stale history (2563-2610), but I found no path that promotes a different live stream on file-ID reuse. Compact ADS stream resolution compares a 64-bit case-folded suffix hash (448-470, 2845-2857); a collision can choose a wrong suffix, but the reopened object must then pass SOP equality (2947-2949). A collision therefore leaves classification Unknown/failing rather than proving an unsafe promotion. No concrete practical collision was generated, and I do not count it as a separate finding.

• Hard-link classification: The PASSIVE worker validates the entire returned link list, deduplicates parent names within its current batch, and leaves partial identities pending (3065-3227 and the remainder of StageRegistryClassifyAllLinkNames). Failed/truncated scans remain unresolved. This is correct for the asynchronous expansion worker; the synchronous by-ID repetition is Finding 4.

• Locks and I/O: The audited nested order is RegistryLock -> scope-cache lock -> entry PagingWriteLock -> SectionLock for promotion, and RegistryLock -> SectionLock for association/prune. Paging admission releases the initial SectionLock lookup before taking scope-cache then PagingWriteLock. Compact-pool access is nested only RegistryLock -> compact free-list lock; no reverse path taking RegistryLock while holding the compact lock was found. File opens, hard-link/stream queries, CcFlushCache, FltFlushBuffers, and waits happen outside RegistryLock and spin locks. No blocking wait or filesystem/cache I/O occurs under the compact free-list lock.

• IRQL/pageability: Activation, by-ID classification, identity/link opens, and drain waits are pageable PASSIVE worker/pre-operation paths. PagingWriteBegin and the spin-lock helpers are resident and annotated for APC_LEVEL paging callbacks; they use resident entry/cache state and return before any pageable activation code. I found no new PAGED routine called from the APC/DISPATCH paging-write path.

• Allocation cleanup: The compact-pool pop resets and marks the static entry; all final references return it through the free list. The inspected compact-stream, identity-open, parent-open, by-ID temporary identity, reservation, and worker error paths release acquired buffers/objects/handles. Aside from the draining SectionSlot retention in Finding 7 and the deliberate non-returned-pool fallback, I found no concrete leak or double-free in the changed paths.

Disposition

Do not mark the second fix round fully closed. Findings 1 and 2 block the promised cutoff/ADS guarantees. Finding 3 violates the strict out-of-scope paging-write contract and creates a sticky availability side effect. Findings 4, 6, and 7 are bounded latency/lifecycle concerns; Finding 5 is the recorded accepted user-space capacity residual. VM validation is still needed for Cache Manager thread behavior, paging-write denial consequences, and actual timing; none was performed here.
