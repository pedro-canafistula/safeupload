# Pre-mutation publication contention retry

The legacy publisher keeps the same durable `Publishing` intent, held exact stage and inspected snapshot during at most six live attempts. It waits 100, 200, 400, 800 and 1,600 ms between attempts using cancellable `Task.Delay`; wall-clock changes do not affect the budget. The publication worker owns the loop and clears it by success, refusal, exhaustion or cancellation. There is no detached timer or restart retry. Existing `Publishing` recovery still requires the native receipt and never repeats a save.

Only a native sharing/lock refusal (Windows errors 32/33) returned by temporary CREATE or destination rename is eligible. A new attempt needs a fresh temporary leaf and freshly authorized permit after the old permit has been revoked. A created temporary must first receive successful same-handle delete disposition and close. Failed cleanup, copy, flush, identity query, authorization, revoke, journal I/O and unknown outcomes retain their existing hold. Cancellation stops the loop. A successful rename permanently ends retry; subsequent handle/permit/journal failures use the existing confirmed-publication bookkeeping.

Before every attempt, reread the exact journal transfer, `Publishing` state, stage identity, sealed length, inspected digest and pending-rename state. Recheck the held stage and snapshot and current policy, including justification and seed export authority when applicable. Reset only the held snapshot stream position for the next copy. A changed/unreadable policy or identity never requests another permit. No retry can approve partial inspection or substitute path/hash equality for object authority.

Interleavings: a lock released during backoff permits a fresh attempt; a lock remaining through attempt six retains the stage and emits one owner-routed `Retained` notice with `PublicationBusy` advice. A policy/journal/generation change during backoff stops publication. A crash/cancellation leaves `Publishing` held. A rename success followed by revoke/record failure cannot retry a mutation. Failed temporary cleanup prevents retry even if the original refusal was sharing-related. The bound V26 dispatcher remains on its separate Facts/ACK/reconciliation contract; its uncertain or accepted operations never enter this legacy retry loop.

The exhausted notice explains that another program is preventing delivery and asks the user to close it and save again. It grants no justification and makes no content-block claim. Component controls cover the loop and protocol/presentation; real Windows CREATE/rename sharing and the full normal/feature × Debug/Release matrix remain delivery checks.
